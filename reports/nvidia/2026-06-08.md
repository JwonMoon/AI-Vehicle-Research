## 차량AI (1건)

### NVIDIA DRIVE AGX로 차량 내 에이전틱 AI 에이전트 구축하기 (클라우드-자동차)

**날짜**: 발행일 미상 | **출처**: [NVIDIA Developer Blog](https://developer.nvidia.com/ko-kr/blog/how-to-build-in-vehicle-ai-agents-with-nvidia-from-cloud-to-car/)

**카테고리**: 차량AI | 자율주행 인프라 | 에지-클라우드 아키텍처  
**키워드**: DRIVE AGX, 에이전틱 AI, 멀티모달, NeMo, TensorRT Edge-LLM, 캐빈 어시스턴트, 하이브리드 아키텍처

#### 한 줄 요약
자동차 콕핏이 규칙 기반 UI에서 추론·계획·행동 가능한 에이전틱 AI 시스템으로 진화하는 방법론.

#### OEM/Tier1 아키텍처 개발자 관점 인사이트

**직면한 설계 딜레마 해결:**
- ✅ **기존 IVI 재설계 불필요**: AI Box 옵션으로 현재 인포테인먼트 SoC 유지하며 독립 AI ECU 추가 가능
- ✅ **자율주행과 캐빈 AI 통합**: DRIVE AGX Thor는 자율주행·캐빈 AI·인포테인먼트를 단일 칩에 중앙화하여 아키텍처 단순화 가능
- ✅ **하이브리드가 정답**: 프라이버시(온디바이스)와 확장성(클라우드) 모두 필요하면 엣지-클라우드 오케스트레이션 필수

**성능 목표 정량화 (설계 명세화 시 중요):**
- LLM 모델 크기: 7B+ 파라미터 로컬 실행
- 사용자 응답 지연: <500ms (음성 인식 → LLM → TTS)
- 디코딩 처리량: 30+ tokens/sec 지속
- 멀티모달: 카메라(실내/실외), 오디오, 차량 텔레메트리 동시 처리

**새 차량 아키텍처 설계 시 반영 항목:**
- 음성 ASR → 에이전트 오케스트레이터(의도 라우팅) → LLM 추론 → TTS 파이프라인 구성
- 로컬/클라우드 에이전트 선택 로직 (네비게이션은 로컬, 실시간 데이터는 클라우드)
- 네트워크 끊김 시 폴백, 인터넷 지연 시 UX 투명성 처리

#### 상세 내용

**세 가지 하드웨어 아키텍처 옵션:**

1️⃣ **AI Box (기존 IVI 유지형)**
   - DRIVE AGX 기반 독립 ECU → 이더넷을 통해 기존 인포테인먼트 SoC와 연동
   - 기존 차량 전자 아키텍처 변경 최소화
   - 업그레이드 주기 독립 (UI 안정성 미영향)

2️⃣ **DRIVE AGX Thor (중앙화형)**
   - Blackwell GPU 아키텍처 → 자율주행 + 캐빈 AI + 인포테인먼트 단일 칩
   - DriveOS 7: QNX/Linux VM 격리로 혼합 중요도 워크로드 안전 분리
   - 설계 복잡도 높으나 성능/비용 최적

3️⃣ **하이브리드 (DRIVE AGX + MediaTek Dimensity AX)**
   - PCIe 연결로 AI와 IVI 도메인 통합
   - 스케일 가능한 옵션 (프리미엄-보급 라인업)

**개발-배포 통합 파이프라인:**

```
클라우드 개발 (DGX/DRIVE AGX)
  ↓ [CUDA/TensorRT 통합]
  ├─ NeMo로 모델 미세조정
  ├─ TensorRT-LLM으로 클라우드 에이전트 최적화
  ├─ NeMo Agent Toolkit으로 오케스트레이터 구축
  ↓
에지 배포 (차량 내 DRIVE AGX)
  ├─ TensorRT Edge-LLM으로 양자화/가지치기
  ├─ 응답 <500ms, 30 tokens/sec 달성
  ↓
피드백 루프 (지속 개선)
```

**멀티모달 에이전트 파이프라인:**
- **입력**: 마이크(ASR) + 실내/실외 카메라(VLM) + 차량 OBD 데이터
- **오케스트레이션**: 사용자 의도 파악 → 로컬 vs 클라우드 에이전트 라우팅
- **컨텍스트 공유**: 클라우드 에이전트가 이미 공유된 정보 재요청 방지
- **폴백**: 인터넷 없을 때 로컬 에이전트 응답, 지연 있을 때 UX 투명성 (예: "음식점 검색 중..." 표시)

**실제 활용 예시:**
- "저 음식당 운영시간은?" → 외부 카메라(vision) + 클라우드 API(영업정보) + LLM(자연어 설명)
- "안내견이 자고 있어" → 실내 카메라 + VLM(객체 인식) → 알람 설정 또는 환기 자동 조절
- "차 이상 진단해줄래?" → 차량 OBD 데이터 + LLM(자연어 진단) → 정비소 추천

**시장 전망:**
- 2025: 에이전틱 AI 탑재 차량 500만 대
- 2035: 7,000만 대 (ABI Research)

**관련도**: `high` — 차량 콕핏 AI 최신 아키텍처 정의 및 구현 사례

## LLM·모델 (2건)

### NVIDIA CUDA Tile: C++ GPU 커널 개발 혁신

**날짜**: 2026-05-29 | **출처**: [NVIDIA Developer Blog](https://developer.nvidia.com/ko-kr/blog/develop-high-performance-gpu-kernels-in-cpp-with-nvidia-cuda-tile/)

**카테고리**: LLM·모델 | 차량 AI 가속  
**키워드**: CUDA 13.3, GPU 커널, 병렬화, 타일 기반 프로그래밍, 메모리 최적화

#### 한 줄 요약
CUDA 13.3부터 C++의 타일(다차원 배열) 기반 GPU 커널로 복잡한 병렬화를 컴파일러가 자동 관리.

#### OEM/Tier1 인사이트

**차량 AI 가속 구현 관점:**
- 기존 SIMT(Single Instruction Multiple Thread) 모델 → 타일 기반으로 마이그레이션하면 **개발 복잡도 50% 감소**
- 컴파일러가 메모리 이동·비동기 처리를 자동 최적화 → 손수 튜닝할 필요 없음
- 벡터 연산(DNN 추론), 행렬 곱셈(LLM 토큰 생성) 등 차량 AI 워크로드에 직접 적용 가능

**개발 선택지:**
- ✅ 신규 프로젝트: CUDA Tile로 처음부터 개발
- ✅ 레거시: 기존 SIMT 커널을 Tile로 포팅 (점진적 마이그레이션)

#### 상세 내용

**타일 기반 프로그래밍 3대 이점:**

1️⃣ **병렬성 자동화**
   - "다차원 배열을 기본 데이터 저장소" → 인덱싱과 데이터 흐름을 명시적으로 표현
   - 컴파일러가 블록 내 병렬성·캐시·메모리 대역폭 자동 분배

2️⃣ **개발 시간 단축**
   - 기존: SIMT에서 warp 레벨 최적화까지 수동 작업 (복잡·오류 가능)
   - Tile: 높은 추상화로 알고리즘 로직에만 집중

3️⃣ **확장성 보장**
   - 타일 크기·그리드 구성만 변경하면 H/W 변화(GPU 세대 업그레이드)에 자동 적응

**코드 예시 흐름:**
```
__tile_global__을 선언 → 파티션 뷰 정의 → 컴파일러가 최적 메모리 배치 결정
```

**차량 AI 적용 사례:**
- DNN 추론: 벡터 덧셈 → 합성곱(Conv) → 행렬 곱셈 (모두 Tile로 가속)
- LLM 토큰 생성: KV-캐시 접근 최적화 → 응답 시간 개선

**관련도**: `medium` — 차량 AI 칩 최적화 담당자/커스텀 커널 개발팀에 필수

### NVIDIA Cosmos 3: 피지컬 AI 통합 모델

**날짜**: 2026-05-29 | **출처**: [NVIDIA Developer Blog](https://developer.nvidia.com/ko-kr/blog/develop-physical-ai-reasoning-world-and-action-models-with-nvidia-cosmos-3/)

**카테고리**: 차량AI | LLM·모델 | 물리 세계 이해  
**키워드**: Cosmos 3, 피지컬 AI, 멀티모달, Mixture-of-Transformers, 로보틱스, 자율주행

#### 한 줄 요약
물리 추론, 월드 모델, 행동 생성을 단일 통합 모델로 구현해 로보틱스/자율주행 AI 파이프라인 단순화.

#### OEM/Tier1 인사이트

**아키텍처 혁신 의미:**
- ✅ **파이프라인 단순화**: 추론 모델 → 세계 모델 → 행동 생성기를 독립적으로 구성하지 않아도 됨
- ✅ **도메인 간 전이**: 로보틱스·자율주행·창고 자동화 데이터 셋으로 학습된 모델을 상호 활용 가능
- ✅ **엣지 배포 가능**: Nano(160억 파라미터)는 워크스테이션급 GPU에서 실시간 추론 (차량용 가능)

**설계 의사결정 포인트:**
- 기존: 여러 특화 모델 조합 → 통합 관리 복잡
- Cosmos 3: 단일 통합 모델 → 버전 관리·재학습·배포 단순화

#### 상세 내용

**Cosmos 3 아키텍처:**

1️⃣ **Mixture-of-Transformers (MoT)**
   - 물리 추론 전문가(expert)
   - 월드 모델(world prediction) 전문가
   - 행동 생성(action generation) 전문가
   - → 각 전문가는 독립 학습, 동적 라우팅으로 효율적 추론

2️⃣ **세 가지 크기 옵션**
   - **Nano (160억 파라미터)**: 워크스테이션/차량용 (실시간)
   - **Standard (200억+ 파라미터)**: 중형 서버
   - **Super (640억 파라미터)**: 데이터센터 (최고 품질)

3️⃣ **오픈소스 생태**
   - 모델 + 학습 코드 + 6개 합성 데이터셋 공개
   - NVIDIA NIM으로 마이크로서비스화

**차량 적용 시나리오:**
- **로보택시 경로 계획**: 센서 입력(카메라·라이다) → 월드 모델(3D 장면 재구성) → 행동(스티어링 제어)
- **주차**: 카메라 영상 → 물리 추론(공간 이해) → 행동(조향/속도)
- **동적 장애물 회피**: 실시간 예측 → 즉시 행동 응답

**주목할 점:**
- 도메인 특화 모델들이 아닌 **통합 아키텍처**로 이동
- 차량 업체가 "여러 모델을 조합"하는 방식 → "단일 통합 모델"로 재고해야 할 시점

**관련도**: `high` — 자율주행 SW 스택 재설계 시 참고 필수

## 인프라·하드웨어 (2건)

### DynoSim: 차량 서빙 스택 고속 시뮬레이션

**날짜**: 2026-05-27 | **출처**: [NVIDIA Developer Blog](https://developer.nvidia.com/ko-kr/blog/dynosim-simulating-the-pareto-frontier/)

**카테고리**: 인프라·하드웨어 | 성능 최적화  
**키워드**: DynoSim, 시뮬레이션, Dynamo, TensorRT, 성능 튜닝, Rust

#### 한 줄 요약
NVIDIA Dynamo 차량 서빙 스택을 이산 사건 시뮬레이션으로 수천 배 가속해 배포 최적화를 설계 단계에서 완료.

#### OEM/Tier1 인사이트

**개발 주기 획기적 단축:**
- ✅ 기존: 프로토타입 → 실제 GPU 테스트 → 튜닝 (주기 길고 비용 높음)
- ✅ DynoSim: "시뮬레이션" 단계에서 수천 개 배포 조합 검증 → 최고 성능 구성 미리 결정
- ✅ **속도 개선**: 1시간 워크로드를 2.41초에 테스트 (~1,500배 가속)

**차량 AI 배포 관점:**
- 캐빈 AI 모델 A vs B → 리소스 사용량/응답시간 트레이드오프 분석 → 최적 선택
- 여러 LLM 크기(7B/13B/30B) → 로컬/클라우드 혼합 배포 시 최고 성능점 찾기
- OTA 업데이트 시뮬레이션 → "로드밸런싱 변화" 영향도 사전 검증

#### 상세 내용

**DynoSim이 해결하는 문제:**

1️⃣ **배포 공간 탐색**
   - 라우팅 정책, 캐시 크기, 스케줄링 알고리즘 등 **파라미터 조합 폭발적 증가**
   - 각 조합을 실제로 테스트? → 시간/비용 불가능
   - DynoSim: 시뮬레이션으로 "파레토 프런티어"(성능-비용 최적 조합) 빠르게 발견

2️⃣ **성능 병목 분석**
   - 라우팅 지연? 스케줄링 비효율? 캐시 미스? → DynoSim이 각 컴포넌트 기여도 정량화
   - 개선 우선순위 명확화

3️⃣ **Rust 기반 구현**
   - 매우 빠른 시뮬레이션 → 개발 이터레이션 주기 단축

**차량 시뮬레이션 적용:**
- 테스트 워크로드: "월요일 출근 시간 + 점심 시간 + 회의 시간" 등 차량별 실제 사용 패턴
- 최적 결과: "모델 A(7B) + 클라우드 백엔드 B" 조합이 응답시간 <500ms, 처리량 최대

**관련도**: `high` — 차량 AI 배포 성능 튜닝 담당자에게 필수

### AI 모델 서빙 파이프라인의 마찰 제거

**날짜**: 2026-05-22 | **출처**: [NVIDIA Developer Blog](https://developer.nvidia.com/ko-kr/blog/how-to-eliminate-pipeline-friction-in-ai-model-serving/)

**카테고리**: 인프라·하드웨어 | 배포 최적화  
**키워드**: TensorRT, ONNX, 양자화, 동적 입력, CI/CD, 프로파일링

#### 한 줄 요약
모델 익스포트·양자화·배포 단계의 4가지 "마찰"(모델-하드웨어 불일치)을 TensorRT와 프로파일링으로 체계적 해결.

#### OEM/Tier1 인사이트

**프로덕션 배포 현실의 문제:**
- ✅ 연구팀: PyTorch로 학습한 7B LLM 모델 ✓
- ❌ 배포팀: ONNX 변환 실패? → 지원 안 되는 연산? → 동적 입력 크기? → 응답 시간 3초? (목표 <500ms)
- 결과: 3개월 지연, 성능 미달성

**4가지 마찰 포인트와 해결책:**

| 마찰 | 원인 | 해결책 |
|------|------|--------|
| **모델 익스포트** | PyTorch → ONNX 호환성 | TensorRT의 ONNX Parser + Early Validation |
| **지원 안 되는 연산** | GPU가 특정 연산 미지원 | TensorRT Custom Plugin으로 구현 |
| **동적 입력 크기** | 입력 토큰 길이 변동 | Dynamic Shape Profile 사전 정의 |
| **버전 불일치** | GPU 드라이버/CUDA 버전 | CI/CD 파이프라인에서 자동 검증 |

#### 상세 내용

**TensorRT 활용 파이프라인:**

```
PyTorch 학습 모델
  ↓
ONNX 중간 포맷으로 변환 (TensorRT ONNX Parser)
  ↓
**Early Validation**: 지원 미확인 연산 즉시 감지
  ↓
Dynamic Shape Profile 정의 (최소/최적/최대 입력 크기)
  ↓
TensorRT 엔진 빌드 (양자화 + 커널 최적화)
  ↓
배포 (차량 GPU 또는 클라우드 서버)
  ↓
지속 모니터링 (trtexec, Nsight Systems 프로파일링)
```

**각 단계 실무 팁:**

1️⃣ **ONNX 변환 단계**
   - 불명확한 연산? → Custom Plugin 미리 예비
   - 예: `torch.roll()` → TensorRT에서 구현 필요

2️⃣ **동적 입력 프로파일**
   - 차량 음성 입력: "안녕하세요"(5 토큰) ~ "내일 서울에서 부산까지 가는 최저 항공료" (20 토큰)
   - 최소/최적/최대 입력 크기 정의 → TensorRT가 각 범위 최적화

3️⃣ **배포 자동화**
   ```
   개발: trtexec로 엔진 성능 검증
   CI/CD: GPU 타입별 테스트 (차량 내 NVIDIA Orin vs 클라우드 H100)
   모니터링: Nsight Systems로 bottleneck 추적
   ```

**차량 AI 적용 시나리오:**
- 7B LLM 배포 전: "응답 <500ms 달성 가능한가?" → 시뮬레이션 + 프로파일링으로 사전 검증
- 양자화 적용: INT8로 압축 → 응답 시간/메모리 트레이드오프 정량화
- OTA 업데이트: 새 모델 배포 전 CI/CD 자동 검증 → 차량에서 오류 최소화
