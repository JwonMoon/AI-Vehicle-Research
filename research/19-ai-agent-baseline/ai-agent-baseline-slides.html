방법

"baseline"을 어떻게 정했나

현장 평균 통계는 공개된 것이 없다. 그래서 baseline은 공개 벤치마크에서 재현 가능한 수준 + 통제 실험이 보여준 구조적 효과로 정의한다.
  • 세 열로 본다 — 현재 최고(리더보드 1위, 운영자 검증 우선) / 널리 쓸 수 있는 수준(제3자가 비용을 통제해 재측정) / 오픈소스로 직접 돌릴 수 있는 수준
  • 근거 우선순위 — 공식 리더보드·사양서 → 논문의 통제 실험 → 벤더 자체 보고(주장으로 표시) → 서베이. 2차 블로그는 쓰지 않았다
  • 분류는 출판된 것만 — 자율성 단계, 멀티 에이전트 구조 분류 모두 논문 원문 표를 그대로 인용
  • 수치마다 함께 적은 것 — 벤치마크 버전, 모델, 하네스, 산출 방식, 비용, 조회일
근거 유형쓰임한계
공식 리더보드축별 수치하네스·버전 의존, 해킹 가능
통제 실험 논문멀티 효과의 방향과 크기문제 수 20~100개
벤더 자체 보고실제 제품 사례시스템 1개, 자체 평가
서베이지형과 공백수치 없음
정의

에이전트란 무엇인가

에이전트 = LLM + 도구 호출 + 반복 루프. 모델이 스스로 다음 행동을 정하며 과업을 끝까지 진행하는 시스템이다.
  • 형식 정의 — 에이전트 시스템 S = (에이전트 집합 A, 환경 E, 통신 구조 C, 조정 정책 Ω). 에이전트가 하나면 단일, 둘 이상이면 멀티 에이전트 시스템
  • 에이전트다운 과업의 세 조건 — 환경과 여러 단계 상호작용 / 부분 정보 속에서 반복 수집 / 피드백에 따라 전략 수정
  • 워크플로우와의 구분 — 흐름을 코드가 미리 정하면 워크플로우, 모델이 매 단계 정하면 에이전트
  • 도구 호출 — 모델은 "이 함수를 이 인자로 불러 달라"는 출력만 내고, 실행은 바깥 코드가 한다
정의

자율성에는 단계가 있다 — "에이전트"라는 말의 범위

수치를 말할 때는 어느 단계의 이야기인지 밝혀야 한다. 코딩·터미널 벤치마크는 "다단계 에이전트" 단계, 고객 응대는 "사용자와 협력·자문" 단계를 잰다.
멀티 에이전트 분류

멀티 에이전트는 다섯 가지 구조로 나뉜다

핵심 차이는 "중앙 검증자가 있는가"와 "에이전트끼리 통신하는가"다. 이 둘이 성능과 오류 증폭을 가른다.
  • Single-Agent — 하나가 모든 단계를 순차로
  • Independent — 여럿이 통신 없이 병렬 수행, 끝에 결과만 합침
  • Centralized — 지휘자가 작업자에게 위임하고 종합(지휘자-작업자)
  • Decentralized — 서로 직접 통신해 합의(토론·투표)
  • Hybrid — 계층 감독 + 피어 간 통신
  • 프레임워크 수준에서는 "제어 흐름을 누가 쥐나"로 다시 나뉜다: 개발자가 그래프로 / 에이전트가 역할로 / 환경이 상태로
벤치마크

무엇을 재는 벤치마크들인가

축마다 표준으로 굳은 벤치마크가 하나씩 있다. 각 벤치마크는 서로 다른 능력을 재므로 점수를 섞어 비교하면 안 된다.

벤치마크

리더보드 점수를 읽을 때 꼭 확인할 다섯 가지

리더보드 점수는 모델 점수가 아니라 "모델 + 하네스 + 벤치마크 버전"의 점수다. 비용과 조회일 없는 점수는 비교에 쓸 수 없다.
  • 하네스(AGENT 열) — 모델을 돌리는 에이전트 코드. 같은 모델도 하네스에 따라 점수가 다르다. 리더보드가 MODEL과 AGENT를 따로 적는 이유
  • 버전 — Terminal-Bench는 4.1, τ-bench는 2.0. 버전이 다르면 문제 집합이 달라 비교 불가
  • pass@1 vs pass^k — 1번 성공한 비율 vs k번 모두 성공한 비율. 신뢰성은 후자
  • 비용·토큰 — 같은 점수대에서 비용이 10배 넘게 갈린다
  • 자체 보고 vs 운영자 검증 — SWE-bench Verified 180행 중 운영자 검증은 60행뿐

정량 baseline — 코딩

SWE-bench: 점수만큼 비용을 봐야 한다

해결률 72~77% 구간에 모델이 몰려 있고, 같은 구간에서 문제당 비용은 $0.07에서 $0.75까지 10배 넘게 갈린다.
읽는 법: 자체 보고 행(79.2%)은 운영자 실행 1위(76.8%)보다 높지만 검증되지 않았다. 전체 보드의 최신 등록은 2026-02로, 최신 모델이 빠져 있을 수 있다.
정량 baseline — 범용 보조·함수 호출

제3자 재측정과 기본기 벤치마크

제3자가 비용을 통제해 다시 돌리면 GAIA 1위는 74.6%다. 자체 제출 리더보드의 94%와 20%p 차이가 난다.
HAL 공지: 신규 모델 등록 일시 중지, 2026-10 일부 비용·토큰이 2배 과대 표기된 이슈 있음.
정량 baseline — 컴퓨터 조작

OSWorld: GUI 조작은 수치상 사람을 넘었다

운영팀 통일 설정 평가에서 모델 단독 86.0%, 에이전트 프레임워크 포함 90.2%. 2024년 논문의 사람 기준선은 72.4%였다.
  • 무엇을 재나 — 실제 OS에서 크롬·오피스·VS Code·파일 관리 같은 앱을 조작해 과업을 끝내는지
  • 조건 — 최대 100단계 허용. 단계 제한이 적으면 점수가 내려간다
  • 뜻: "사람처럼 화면을 보고 마우스·키보드로 일을 끝내는" 능력이 1년 사이 급격히 올라왔다
  • 주의: 이 벤치마크는 해킹 가능성 감사에서 취약점이 확인된 13개에 포함된다(뒤 슬라이드)
정성 baseline — 신뢰성

한 번은 되지만 매번은 안 된다

같은 과업을 반복할수록 "모두 성공" 비율은 가파르게 떨어진다. 고객 응대 통신 도메인: 1회 34% → 4회 연속 19%. 사용자와 함께 일해야 하면 혼자 할 때보다 18~25%p 더 떨어진다.
  • pass^k — k번 독립 시도해 모두 성공한 비율. 매번 같은 품질이 필요한 서비스의 진짜 지표
  • 긴 과업일수록 0에 수렴 — 필요한 행동 수·하위 문제 수가 늘수록 성공률이 떨어져 많은 단계가 필요한 과업에서는 거의 0
  • 사람과 함께 하는 비용 — 사용자에게 행동을 안내해야 하는 조건(dual-control)에서 pass^1이 gpt-4.1 18%p, o4-mini 25%p 하락
  • 뜻: 리더보드의 1회 성공률만 보고 배치 신뢰성을 판단하면 과대평가한다
멀티 에이전트 연동 baseline

멀티 에이전트는 "기본 업그레이드"가 아니다

도구·프롬프트·연산을 통일한 260개 구성 실험에서 단일 대비 효과는 −70%에서 +80.8%까지 갈렸고 평균은 −0.3%. 과업의 구조가 결과를 결정한다.
  • 이득인 과업 — 조각으로 나눠 따로 조사해 합칠 수 있는 과업(금융 질의 응답) +80.8%
  • 손해인 과업 — 앞 단계 결과가 다음 단계에 꼭 필요한 과업(순차 계획) −70%. 코드 수정도 −15~−2%
  • 능력 포화 — 단일 에이전트가 이미 45% 이상 잘하는 과업은 에이전트를 더해도 손해
  • 도구가 많을수록 — 조정 비용이 불균형하게 커진다(16개 도구 업무 워크플로우에서 뚜렷)
  • 뜻: "몇 개의 에이전트를 쓰나"가 아니라 "과업을 나눌 수 있나"를 먼저 물어야 한다
멀티 에이전트 연동 baseline

비용과 오류: 나눌수록 비싸고, 검증자가 없으면 틀린 것이 커진다

토큰 1천 개당 성공 수는 단일 67.7 → 멀티 13.6~42.4. 통신 없이 결과만 합치는 구조는 오류를 17.2배, 중앙 검증 구조는 4.4배 증폭한다.
  • 턴 수 — 단일 7.2턴 → Hybrid 44.3턴. 오버헤드 58~515%
  • 오류 증폭률 — 한 에이전트의 실수가 최종 결과에 몇 배로 반영되나. Independent 17.2 / Decentralized 7.8 / Hybrid 5.1 / Centralized 4.4
  • 실제 제품 사례(Anthropic 리서치) — 지휘자-작업자 구조로 단일 대비 +90.2%(자체 평가). 대신 채팅 대비 15배 토큰. 병렬 조사에는 맞고 코딩에는 안 맞는다고 스스로 평가
  • 뜻: 멀티로 가려면 중앙 검증자를 두고, 성능 향상이 3~5배 비용을 정당화하는지 먼저 계산해야 한다
멀티 에이전트 전용 측정

협업의 질과 프레임워크 설계를 따로 재기 시작했다

멀티 전용 표준 벤치마크는 아직 없다. 대신 협업 과정을 재는 MARBLE과 모델을 고정하고 프레임워크 설계만 바꿔 재는 MAFBench가 나왔다.
  • MARBLE — 연구 제안서·건축·DB 분석·코딩·게임·협상 6개 시나리오. 과업 점수 외에 마일스톤 기여도와 통신·계획 점수를 잰다. 결론: 성공의 1차 요인은 여전히 모델 능력, graph 토폴로지가 가장 좋고 tree가 가장 나쁨, 토론(group discussion)은 모든 지표에서 최악
  • MAFBench — 9개 프레임워크를 같은 모델로 비교. 오케스트레이션만으로 지연 1.1배~62배, 형식을 강제하는 계획 인터페이스는 약한 모델의 정확도를 최대 32점 하락(형식 위반 84.7%), 토폴로지가 안 맞으면 조정 성공률 90% 이상 → 30% 미만
  • 뜻: 프레임워크 선택이 모델 선택만큼 성능을 좌우할 수 있다. 어느 프레임워크도 메모리를 "지우는" 기능은 없었다
실패 유형

왜 실패하나: 모델보다 설계가 문제다

공개 멀티 에이전트 시스템 7개의 궤적 1,642개를 분석한 결과, 실패의 44.2%는 시스템 설계 결함, 32.3%는 에이전트 간 불일치, 23.5%는 검증 문제였다. 실패율은 41~86.7%.
  • 가장 흔한 넷 — 단계 반복 15.7% / 추론과 행동 불일치 13.2% / 종료 조건 인지 실패 12.4% / 과업 사양 불이행 11.8%
  • 멀티에서만 생기는 실패 — 알면서 안 알려줌, 상대 입력 무시, 과업 이탈 같은 "에이전트 간 불일치" 6종
  • 검증자는 은탄환이 아니다 — 검증 실패는 성공한 실행에서도 자주 나타난다
  • 설계 수정 효과 — 역할 프롬프트 정비 +9.4%p, 종료 조건을 바꾼 토폴로지 +15.6%p. 토폴로지가 프롬프트보다 효과적이지만 둘 다 근본 해결은 아님
  • 뜻: 실패를 보면 "모델이 못 푼 것인가, 사양·역할·종료·검증 설계가 빠진 것인가"를 먼저 묻는다

음성은 두 가지 방식으로 만든다

캐스케이드(음성인식 → LLM → 음성합성)는 성숙하고 감사 가능하지만 느리고 억양을 잃는다. speech-to-speech는 빠르고 자연스럽지만 도구 호출이 덜 성숙하다. 2026년에 "듣는 중에도 말하는" 전이중 모델이 상용화됐다.
  • 캐스케이드 — 각 블록을 골라 조합. 텍스트 기록이 남아 감사 가능. 단계마다 지연이 쌓이고, 억양·감정이 LLM에 전달되지 않음
  • speech-to-speech — 모델 하나가 음성을 직접 음성으로. 지연이 가장 짧고 표현력 내장. 전사가 늦고 대본 음성 불가
  • 전이중(full-duplex) — 사용자가 말하는 중에도 듣고 끼어들기·맞장구를 처리. 턴 감지를 모델이 스스로
  • 중립 프레임워크(LiveKit)의 권고: "대부분의 프로덕션 에이전트에는 캐스케이드가 기본값, 지연·표현력이 더 중요하면 realtime"

주의

벤치마크 점수는 해킹될 수 있다

UC Berkeley RDI가 자동 감사 에이전트로 13개 벤치마크를 점검한 결과 13개 전부에서 과업을 풀지 않고 점수를 얻을 수 있었다(작동하는 해킹 45건). 앞 슬라이드의 BFCL·GAIA·Terminal-Bench·τ-bench·OSWorld가 포함된다.
  • 가장 흔한 원인 — 채점기와 피평가 코드가 같은 프로세스·컨테이너·파일시스템을 공유. WebArena는 812개 정답이 담긴 파일이 에이전트가 읽을 수 있는 곳에 있었다
  • 약한 테스트 — "함수가 존재하는지"만 확인하고 호출하지 않는 테스트
  • 이미 벌어진 일 — 한 모델이 SWE-bench 궤적의 24.4%에서 git log로 정답 커밋을 베껴 점수가 교정됨. OpenAI는 Verified 감사 문제의 59.4%에 결함 테스트를 발견한 뒤 보고를 중단
  • 뜻: 점수를 볼 때 "채점기가 격리되어 있나, 제출물·궤적이 공개되나, 운영자가 검증했나"를 함께 본다. 믿을 수 있는 벤치마크는 속이는 것이 푸는 것보다 어려워야 한다
리서치 방향

핵심 질문 4개와 미해결 문제 4개

핵심 질문

  • Q1. 어떤 일을 나눠 시키면 좋아지나, 미리 알 수 있나? 결과는 −70~+81%로 갈리는데 예측식의 설명력은 0.4
  • Q2. 에이전트끼리 무엇을 공유하고, 기억은 어떻게 나누나? 통신 없으면 오류 17배, 메모리는 모두 쌓기만 하고 지우지 못함
  • Q3. "다 했습니다"를 어떻게 믿나? 4회 연속 성공률 급락, 검증 실패는 성공한 실행에도 존재, 벤치마크 13개 전부 해킹 가능
  • Q4. 사람은 언제 끼어들어야 하나? 규격은 "입력 대기" 상태를 두지만, 언제 물을지는 열린 질문. 사용자와 함께 하면 18~25%p 하락

미해결 문제

  • P1. 반복·장기 신뢰성 — 매번 성공하지 못하고, 긴 과업은 0에 수렴. 공개 멀티 시스템 실패율 41~87%
  • P2. 비용 대비 효과의 기준 부재 — 토큰 효율 3~5배 차이인데 비용을 재는 표준이 없음. 제3자 비용 통제 리더보드는 7개 벤치마크뿐
  • P3. 신뢰할 수 있는 평가와 안전 — 멀티 표준 벤치마크 없음, 기존 벤치마크 해킹 가능, 안전 평가 공백
  • P4. 연동 규격의 미성숙 — MCP 비호환 변경, A2A 1.0 직후, 프레임워크별 지원 제각각
마무리

한 줄 결론

단일 에이전트는 코딩·화면 조작에서 과업의 4분의 3 이상을 한 번에 끝내는 수준에 왔지만 반복 신뢰성과 비용은 미해결이다.
멀티 에이전트는 과업 구조에 따라 득실이 갈리는 조건부 기술이며, 실패의 대부분은 모델이 아니라 설계에서 온다.
음성은 인식과 대화의 자연스러움은 포화했고, 과업 완수가 텍스트를 뒤따르는 중이다.
