0. 한 장 요약 — baseline은 이 정도다

0.1 이 보고서가 말하는 "baseline"

  • 정의: 2026년 11월 시점에 공개되어 누구나 다시 확인할 수 있는 자료에서 확인되는 ① 지금 도달한 최고 수준, ② 널리 쓸 수 있는 수준(제3자가 비용을 통제해 재측정한 수치), ③ 오픈소스로 직접 돌릴 수 있는 수준, ④ 통제 실험이 보여준 구조적 효과(멀티로 나누면 얼마나 좋아지고 비용은 얼마나 드나), ⑤ 그 수치의 한계.
  • 근거 4유형과 우선순위: 🔍 공식 리더보드·사양서 → 📄 논문(통제 실험) → 🏢 벤더 자체 보고("주장"으로 표기) → 서베이(지형 설명에만). 2차 블로그는 어떤 수치의 근거로도 쓰지 않았다.
  • 넣지 않은 것: 실제 산업 배치의 성공률·비용 통계. 공개 자료가 없다. 따라서 아래 baseline은 "현장 평균"이 아니라 "공개 벤치마크에서 재현 가능한 수준 + 통제 실험의 구조적 효과"다.

1. 범위와 분류 — 출판된 분류만 사용

먼저 알아둘 용어
LLM
— 대규모 언어 모델. 텍스트를 입력받아 다음 단어를 예측하는 방식으로 답을 만드는 AI. GPT·Claude·Gemini가 여기 속한다.
에이전트(agent)
— LLM이 목표를 받아 도구(검색·코드 실행·API 등)를 스스로 골라 부르고, 그 결과를 보고 다음 행동을 정하는 일을 반복해 과업을 끝내는 시스템. 아래 1.1에 출판된 정의를 적었다.
멀티 에이전트(multi-agent system, MAS)
— 이런 에이전트가 둘 이상 역할을 나눠 통신하며 하나의 과업을 수행하는 구조.
도구 호출(tool / function calling)
— 모델이 "이 함수를 이 인자로 불러 달라"는 형식의 출력을 내고, 실제 실행은 바깥 코드가 하는 방식.
벤치마크 / 리더보드
— 벤치마크는 정해진 문제 집합과 채점 방식. 리더보드는 그 벤치마크에서 각 시스템이 얻은 점수를 순위로 보여주는 공개 표.

1.1 에이전트의 정의 (출처가 있는 것만)

  • 형식 정의 📄 — Google Research·MIT의 2025년 논문은 에이전트 시스템을 S = (A, E, C, Ω)로 정의한다. A는 에이전트 집합, E는 환경, C는 통신 토폴로지(연결 모양), Ω는 조정 정책이다. |A| = 1이면 단일 에이전트 시스템(SAS), |A| > 1이면 멀티 에이전트 시스템(MAS)이다 [2].
  • "에이전트다운 과업(agentic task)"의 세 속성 📄 — 같은 논문의 블로그 설명: ① 외부 환경과 지속적으로 여러 단계 상호작용, ② 부분적으로만 관측되는 상황에서 반복 정보 수집, ③ 환경 피드백에 따른 전략 수정 [2].
  • 업계에서 흔히 쓰는 경계선 📄 — Anthropic은 "미리 정한 코드 경로로 LLM과 도구를 엮은 것"을 워크플로우, "LLM이 스스로 과정과 도구 사용을 지휘하는 것"을 에이전트라 부른다 [1]. 이는 한 회사의 정의이며 표준이나 비교 기준은 아니다. 이 보고서에서는 범위를 설명할 때만 참고한다.

1.2 자율성 단계 — 출판된 분류 3종

"에이전트"라는 말이 챗봇부터 몇 시간짜리 자율 과업까지 가리키므로, 수치를 말할 때 어느 단계의 이야기인지 밝혀야 한다. 아래 세 분류는 모두 논문 원문 표에서 확인한 것이다. 이 보고서는 이 중 어느 것도 수정하지 않고 그대로 쓴다.

분류단계기준
Mitchell 외(Hugging Face), 2025 [3] 📄 ✩✩✩✩ 단순 처리기(모델이 흐름에 영향 없음) → ★ 라우터(모델이 분기 결정) → ★★ 도구 호출기(모델이 함수와 인자 결정) → ★★★ 다단계 에이전트(모델이 반복과 계속 여부 결정) → ★★★★ 완전 자율 에이전트(모델이 새 코드를 만들어 실행) 코드 제어권을 누가 쥐는가(사람 → 시스템)
Feng·McDonald·Zhang(워싱턴대), 2025 [4] 📄 L1 사용자 = 조작자(Operator) → L2 협력자(Collaborator) → L3 자문(Consultant) → L4 승인자(Approver) → L5 관찰자(Observer) 사용자가 맡는 역할. 단계마다 필수 제어장치와 예시 시스템(Copilot, Operator, Deep Research, Devin 등)을 제시
Morris 외(Google DeepMind), 2023, ICML 2024 [5] 📄 Autonomy Level 0 No AI → 1 AI as a Tool → 2 AI as a Consultant → 3 AI as a Collaborator → 4 AI as an Expert → 5 AI as an Agent 사람과 AI의 상호작용 방식. 성능(Emerging~Superhuman) × 범용성(Narrow/General) 매트릭스와 함께 제시
  • 기존 음성 비서의 위치 📄 — Morris 외는 Siri·Alexa·Google Assistant 같은 스마트 스피커를 성능 Level 2 "Competent Narrow AI"(좁은 범위에서 숙련된 성인의 50백분위 이상)로 분류한다 [5]. 즉 LLM 에이전트 이전 세대의 좁은 시스템으로 본다.
  • 이 보고서에서 쓰는 방식 — 수치를 적을 때 "Mitchell ★★★(다단계 에이전트) 급 과업" 또는 "Feng L4(승인자) 급 자율성"처럼 출판 분류의 단계명을 그대로 인용한다. 자체 단계는 만들지 않는다.

1.3 멀티 에이전트의 분류 — 아키텍처 5종과 프레임워크 설계 5차원

  • 아키텍처 5종 📄 — Google Research·MIT 논문이 통제 실험에 쓴 분류 [2]:
    • Single-Agent(SAS): 에이전트 하나가 모든 추론·행동을 순차로 수행.
    • Independent: 여러 에이전트가 서로 통신 없이 병렬로 하위 과업을 수행하고 끝에 결과만 합침.
    • Centralized: 중앙 지휘자(orchestrator)가 작업자에게 위임하고 결과를 종합하는 hub-and-spoke.
    • Decentralized: 에이전트들이 서로 직접 통신해 합의(토론·투표).
    • Hybrid: 계층 감독 + 피어 간 통신.
  • 프레임워크 설계 5차원 📄 — MAFBench 논문은 멀티 에이전트 프레임워크를 ① 오케스트레이션(제어 흐름 권한: 개발자가 그래프로 / 에이전트가 역할로 / 환경이 상태로), ② 메모리, ③ 계획 인터페이스, ④ 특화(역할 부여 방식), ⑤ 통신 토폴로지로 분해한다 [6].

1.4 음성 에이전트의 위치 — "다른 종류"가 아니라 "다른 모달리티"

  • 음성/텍스트는 입출력 방식(모달리티) 축이고, 단일/멀티는 구조 축이다. 둘은 독립이다.
  • 근거 🔍 — τ-bench 2.0 공식 저장소는 같은 과업 집합을 텍스트판(text-v1)과 음성판(voice-v1·voice-v2)으로 따로 제공해 모달리티만 바꿔 측정한다 [14]. A2A 프로토콜 사양은 설계 원칙에 "Modality Agnostic(모달리티 무관)"을 명시한다 [21].
  • 따라서 4장에서 음성을 따로 다루는 이유는 측정 지표가 다르기 때문이다(왕복 지연, 음성 인식 오류율, 끼어들기 처리 등).

2. 단일 에이전트 baseline

용어
하네스(harness) / 스캐폴드(scaffold)
— 모델을 벤치마크에서 돌리는 에이전트 코드(프롬프트·도구·재시도 정책). 리더보드의 AGENT 열이 이것이다. 같은 모델도 하네스가 다르면 점수가 다르다 [13].
pass@1
— 과업당 한 번 시도해 성공한 비율. 대부분의 리더보드 기본값.
pass^k
— 같은 과업을 k번 독립 시도해 모두 성공한 비율. "매번 같은 품질을 내는가"를 재는 신뢰성 지표. τ-bench가 도입 [14].
오픈 가중치(open weights)
— 모델 파라미터 파일이 공개되어 직접 내려받아 돌릴 수 있는 모델.
HAL
— Holistic Agent Leaderboard. Princeton이 운영하는 제3자 리더보드로, 벤더 점수를 받아 적지 않고 같은 하네스로 직접 다시 돌려 정확도와 비용(USD)을 함께 공개한다. 확인일 기준 7개 벤치마크(Online Mind2Web, SciCode, SWE-bench Verified Mini, USACO, CORE-Bench Hard, GAIA, TAU-bench Airline)를 다룬다 [19].

2.3 정성 baseline — 수치가 말해주지 않는 것

  • 한 번은 되지만 매번은 안 된다 📄: τ²-bench에서 gpt-4.1의 pass^k는 소매 0.74(k=1) → 0.53(k=4), 통신 0.34 → 0.19. claude-3.7-sonnet은 통신 0.49 → 0.25 [14]. 한 번 성공률이 70%대인 도메인도 네 번 연속 성공은 50%대다.
  • 사용자와 함께 하면 더 어렵다 📄: 같은 통신 과업을 사용자 없이 에이전트 혼자 할 때(No-User)보다 사용자에게 행동을 안내해야 할 때(Default) pass^1이 gpt-4.1 18%p, o4-mini 25%p 낮았다 [14].
  • 긴 과업일수록 0에 수렴 📄: 필요한 행동 수·하위 문제 수가 늘수록 성공률이 떨어져 많은 행동이 필요한 과업에서는 0에 가까워졌다 [14].
  • 사용자 시뮬레이터의 신뢰도도 확인 대상 📄: τ²의 시뮬레이터 오류율은 통신 16%(치명 0%), 소매 40%(치명 12%), 항공 47%(치명 13%) [14]. 대화형 벤치마크 점수는 시뮬레이터 품질에 영향을 받는다.
  • 비용은 1차원 점수에 안 보인다 🔍: HAL의 표현으로 "에이전트는 100배 비싸면서 1% 더 좋을 수 있는데, 1차원 리더보드로는 그 차이를 알 수 없다" [19].

3. 멀티 에이전트 연동 baseline

결론. 멀티 에이전트는 "기본 업그레이드"가 아니다. 통제 실험에서 단일 대비 효과는 과업에 따라 −70%에서 +80.8%까지 갈리고 평균은 0에 가깝다. 통신 없이 결과만 합치는 구조는 오류를 17.2배 증폭하고, 토큰 효율은 단일보다 3~5배 나쁘다 [2]. 실패의 44%는 모델이 아니라 시스템 설계(사양·역할·종료 조건) 문제로 분류된다 [7].
용어
지휘자-작업자(orchestrator-worker)
— 중앙 에이전트가 과업을 쪼개 하위 에이전트(worker, subagent)에게 맡기고 결과를 종합하는 구조. Google 분류의 Centralized에 해당.
오류 증폭률(error amplification)
— 에이전트 하나의 오류가 시스템 최종 결과에 몇 배로 반영되는지. 단일 에이전트를 1.0으로 둔 배수 [2].
토큰(token)
— LLM이 글을 처리하는 단위(대략 단어 조각). 사용량이 곧 비용이다.
토폴로지(topology)
— 에이전트 사이 연결 모양. 별(star)·사슬(chain)·나무(tree)·그래프(graph) 등.

3.1 효과 — 단일 대비 얼마나 좋아지고, 비용은 얼마나 드나

통제 실험 (Google Research·MIT, 2025) 📄

  • 설계: 도구·프롬프트·연산을 표준화하고 5개 아키텍처 × 6개 벤치마크(Finance Agent, BrowseComp-Plus, WorkBench, PlanCraft, SWE-bench Verified, Terminal-Bench) × 3개 모델 가족(OpenAI·Google·Anthropic) = 260개 구성을 비교. 벤치마크당 문제 수는 20~100개 [2].
  • 결과 범위: 단일 대비 상대 변화는 Finance Agent의 Centralized +80.8%(평균 0.631 vs 단일 0.349)에서 PlanCraft의 Independent −70.0%(0.170 vs 0.568)까지. 전체 평균 개선은 −0.3%, 표준편차 37.5% [2].
  • 세 가지 발견 [2]:
    • 능력 포화: 단일 에이전트 성능이 이미 약 45%를 넘는 과업에서는 에이전트를 더해도 수익이 음수(β = −0.236, p = 0.004).
    • 도구가 많은 과업(예: 16개 도구의 업무 워크플로우)은 멀티 조정 오버헤드가 커진다(β = −0.096, p = 0.002).
    • 중앙 검증이 없는 구조는 오류를 더 전파한다. 오류 증폭률: 단일 1.0 / Independent 17.2 / Decentralized 7.8 / Centralized 4.4 / Hybrid 5.1.
  • 비용: 토큰 1천 개당 성공 수는 단일 67.7 → Independent 42.4 → Decentralized 23.9 → Centralized 21.5 → Hybrid 13.6. 턴 수는 단일 7.2 → Hybrid 44.3 [2].
  • 예측력: 과업 속성으로 아키텍처를 고르는 회귀식이 처음 보는 구성의 87%에서 최적 아키텍처를 맞혔지만(무작위 20%), 교차 검증 설명력은 R² 0.37~0.41로 낮다. 방향을 주지만 절대 예측은 못 한다 [2].

실제 제품 사례 (Anthropic 리서치 기능, 2025) 🏢

  • 구조: 선두 에이전트가 질의를 분석해 하위 에이전트 3~5개를 만들어 병렬 탐색시키고 종합. 마지막에 인용 에이전트가 출처를 붙인다 [9].
  • 효과: 내부 평가에서 단일 에이전트(Claude Opus 4) 대비 90.2% 향상. BrowseComp 평가에서 성능 분산의 95%를 세 요인이 설명했고, 토큰 사용량만으로 80%를 설명했다 [9].
  • 비용: 에이전트는 채팅의 약 4배, 멀티 에이전트는 약 15배의 토큰을 쓴다. "과업 가치가 비용을 정당화할 때만" 쓰라고 명시 [9].
  • 맞는 과업 / 안 맞는 과업: 폭넓은 병렬 탐색에는 맞고, 공유 컨텍스트와 의존이 많은 대부분의 코딩 과업에는 맞지 않는다고 자체 평가 [9].
  • ⚠ 한 회사의 자체 평가 1건이다. 위 통제 실험과 방향은 같다(병렬 탐색 = 이득, 순차 의존 = 손해).

3.2 멀티 전용 측정 — 협업의 질과 프레임워크 설계 차이

MultiAgentBench (MARBLE), 2025 📄

  • 무엇을 재나: 공동 목표 시나리오 4개(연구 제안서, Minecraft 건축, DB 이상 분석, 코딩)와 상충 목표 시나리오 2개(Werewolf 게임, 협상)에서 과업 점수와 함께 협업의 질을 잰다. 협업 질은 마일스톤 KPI(전체 마일스톤 중 각 에이전트 기여 비율)와 LLM이 5점 척도로 매긴 통신·계획 점수의 평균(조정 점수)이다 [8].
  • 비교 대상: 토폴로지 star·tree(중앙집중) / graph·chain(분산), 계획 전략 vanilla·CoT·group discussion·cognitive self-evolving [8].
  • 결과: 과업 성공의 1차 요인은 모델 능력. 연구 시나리오에서 graph 토폴로지가 가장 좋았고 tree는 토큰을 많이 쓰며 가장 나빴다. cognitive planning은 마일스톤 달성률을 3% 올렸고, group discussion은 모든 지표에서 최악이었다. 협업 점수가 높아도 과업 점수가 낮은 경우가 있었다(Llama-3.1-70B, Minecraft: 조정 점수 75.0 / 과업 점수 0.21 — 함수 호출의 절반 미만만 실행 가능) [8].

MAFBench, 2026 📄

  • 무엇을 재나: LLM을 고정하고 프레임워크의 설계 선택만 바꿔 9개 프레임워크(LangGraph, CrewAI, AutoGen, OpenAI SDK, Agno, OpenAgents, Concordia, 최소 GABM 골격, OpenHands)를 비교. 기존 벤치마크(MemoryAgentBench, GSM8K·CSQA·MATH, CatDB, AGENTSNET 등)를 표준 파이프라인에 통합 [6].
  • 결과 [6]:
    • 오케스트레이션만으로 지연이 직접 호출 대비 1.1배~62배. 단, 최소 골격 구현은 수 ms만 더 걸려 "패러다임이 아니라 구현의 비용"으로 판정.
    • 스키마(정해진 형식)로 계획을 받는 인터페이스는 약한 모델에서 형식 위반(최대 84.7%)으로 정확도를 최대 32.3점 떨어뜨림. 추론 오류가 아니라 형식 실패.
    • 통신 토폴로지가 구조에 맞지 않으면 대규모 조정 성공률이 90% 이상에서 30% 미만으로 하락.
    • 평가한 어느 프레임워크도 메모리의 통제된 수정(선택적 망각)을 지원하지 않음. 모두 append-only.

3.3 실패 유형 — 왜 멀티 에이전트는 실패하나

  • 자료 📄: UC Berkeley 연구진이 7개 공개 멀티 에이전트 시스템(MetaGPT, ChatDev, HyperAgent, AppWorld, AG2, Magentic-One, OpenManus)의 실행 궤적 1,642개를 모아 분석한 MAST(Multi-Agent System Failure Taxonomy). 사람 주석자 간 일치도 Cohen's κ 0.88, LLM 자동 판정기의 사람 일치도 94%(κ 0.77) [7].
  • 실패율: 7개 시스템의 실패율은 벤치마크에 따라 41%~86.7% [7].
  • 3범주 14유형과 비율 [7]:
    • 시스템 설계 결함 44.2% — 과업 사양 불이행 11.8%, 역할 사양 불이행 1.5%, 단계 반복 15.7%, 대화 이력 상실 2.8%, 종료 조건 인지 실패 12.4%.
    • 에이전트 간 불일치 32.3% — 대화 리셋 2.2%, 명확화 요청 실패 6.8%, 과업 이탈 7.4%, 정보 은폐 0.8%, 상대 입력 무시 1.9%, 추론-행동 불일치 13.2%.
    • 과업 검증 23.5% — 조기 종료 6.2%, 검증 없음·불완전 8.2%, 잘못된 검증 9.1%.
  • 설계 개입의 효과: ChatDev에서 역할 프롬프트 정비로 +9.4%p, 토폴로지를 순환 구조(CTO 에이전트가 검토 완료를 확인할 때만 종료)로 바꿔 +15.6%p. 저자들은 토폴로지 변경이 프롬프트 변경보다 효과적이었지만 둘 다 근본 해결은 아니라고 평가 [7].
  • 검증자는 은탄환이 아니다: 종료 조건 인지 실패(1.5)와 정보 은폐(2.4)는 거의 실패한 실행에만 나타나지만, 검증 실패(3.2·3.3)는 성공한 실행에도 자주 나타난다 [7].

4. 음성 에이전트 baseline

결론. 음성 에이전트는 두 갈래(① 음성인식→LLM→음성합성을 잇는 캐스케이드, ② 음성을 바로 음성으로 만드는 speech-to-speech)로 만들어지며, 2026년 들어 양방향 동시 대화(full-duplex) 모델이 상용화됐다. 과업 성공률은 같은 과업의 텍스트 에이전트보다 낮다: 2026년 초 논문 기준 텍스트 85% vs 음성 31~51%였고 [38], 2026년 9~10월의 full-duplex 모델은 항공·통신 도메인에서 격차를 크게 좁혔다(제3자 실행 기준 평균 81.7%) [14]. 음성 인식 자체는 평균 단어 오류율 5% 안팎까지 내려왔다 [29].

— 음성 인식(Automatic Speech Recognition, Speech-to-Text). 말을 글자로 바꾸는 모델.

— 음성 합성(Text-to-Speech). 글자를 말소리로 바꾸는 모델.

TTFA
— Time to First Audio. 질문이 끝난 뒤 첫 음성이 나오기까지의 시간(초).

6. 리서치 방향 — 핵심 질문 4개, 미해결 문제 4개

각 항목은 「질문 → 쉽게 풀면 → 왜 아직 답이 없나(근거) → 파고들 하위 질문」 순서다. 근거는 모두 앞 장에서 인용한 1차 자료다.

6.1 핵심 질문 4개

Q1. 어떤 일을 여러 에이전트에게 나눠 시키면 좋아지고, 어떤 일은 나빠지나? 시작 전에 알 수 있나?

  • 쉽게 풀면: 사람 팀도 "조사 보고서"는 나눠 맡기면 빠르지만 "설명서대로 조립"은 한 사람이 순서대로 하는 게 낫다. 어떤 일이 어느 쪽인지 미리 판별하는 방법이 아직 없다.
  • 근거: 분해 가능한 금융 추론은 +80.8%, 순차 의존이 강한 계획 과업은 −70.0%. 단일 성능이 약 45%를 넘는 과업은 에이전트를 더해도 손해. 과업 속성으로 결과를 예측하는 식의 설명력은 R² 0.37~0.41 [2].
  • 하위 질문: "나눌 수 있는 일"인지 실행 전에 측정하는 방법은? 45% 임계값은 모델이 좋아져도 유지되나? 지휘자는 싼 모델·작업자는 좋은 모델로 섞어도 되나(같은 논문: 작업자 쪽 능력이 더 중요) [2]? 도구가 많을수록 나누는 비용이 커지는 이유는?

Q2. 에이전트끼리 무엇을 알려줘야 하고, 기억은 어떻게 나눠 관리해야 하나?

  • 쉽게 풀면: 팀원이 아무것도 안 말하고 결과만 합치면 한 사람의 실수가 전체를 망친다. 모든 것을 공유하면 비용이 폭증한다. 기억은 "방금 들은 것"과 "오래 알던 것" 둘이면 되는지, 잊는 기능은 필요한지 모른다.
  • 근거: 통신 없는 Independent 구조는 오류 17.2배, 중앙 검토 구조는 4.4배 [2]. "알면서 안 알려줌"과 "대화 이력 상실"이 별도 실패 유형이며 전자는 거의 실패한 실행에서만 나타남 [7]. 평가된 어느 프레임워크도 메모리를 지우거나 고치는 기능이 없고, 선택적 망각 시험에서 모두 5점 미만 [6].
  • 하위 질문: 공유 컨텍스트가 클수록 좋은가, 전달 규칙이 더 중요한가? 기억을 몇 층으로 나눠야 하나(MAFBench의 메모리 벤치마크는 정확 검색·시험 중 학습·장기 이해·선택적 망각 4능력) [6]? 잊지 못하는 메모리는 장기 운영에서 어떤 실패를 낳나? 컨텍스트 창이 커지면 메모리 설계가 필요 없어지나(MAFBench 설계 원칙: "큰 컨텍스트 창에 의존하지 말라") [6]?

Q3. 에이전트가 "다 했습니다"라고 할 때 그 말을 어떻게 믿나?

  • 쉽게 풀면: 신입이 "끝냈어요"라고 해도 검수를 한다. 에이전트의 검수는 자기 자신이나 다른 에이전트가 하는데, 그 검수가 제대로 되는지, 그리고 시험 자체는 믿을 만한지가 문제다.
  • 근거: 같은 과업을 k번 모두 성공하는 비율(pass^k)은 k가 커질수록 급락(gpt-4.1 통신 도메인 k=1 0.34 → k=4 0.19) [14]. 검증 실패(3.2·3.3)는 성공한 실행에도 자주 나타남 [7]. LLM 자동 채점의 사람 일치도 κ 0.77 [7]. 13개 벤치마크 전부 채점기 격리 실패로 과업을 풀지 않고도 점수 획득 가능 [11].
  • 하위 질문: 검증자를 실행자와 분리하면 충분한가, 검증자는 누가 검증하나? 최종 결과 채점과 중간 과정(궤적) 채점 중 어느 것이 배치 신뢰성을 더 잘 예측하나 [10]? "속이는 것이 푸는 것보다 어려운" 채점기는 어떻게 설계하나 [11]? 사람 검수 없는 자동 채점은 어디까지 믿을 수 있나?

Q4. 사람은 언제, 어떻게 끼어들어야 하나?

  • 쉽게 풀면: 완전 자동이 목표가 아니라면 에이전트가 "확인해 주세요"라고 물어야 할 순간을 정해야 한다. 너무 자주 물으면 쓸모없고, 너무 안 물으면 위험하다. 음성 비서는 실시간이라 이 문제가 가장 극단적이다.
  • 근거: Feng 외의 자율성 5단계 표는 "언제 사용자에게 물어야 하는지 어떻게 아나", "물었을 때 좋은 피드백을 어떻게 받나"를 열린 질문으로 적어 둠 [4]. A2A는 INPUT_REQUIRED·AUTH_REQUIRED 대기 상태를, MCP는 "도구 호출 전 사용자 동의"를 규정 [20][21]. τ²-bench에서 에이전트가 사용자에게 행동을 안내해야 하는 조건은 혼자 할 때보다 성공률이 18~25%p 낮았다 [14].
  • 하위 질문: 어떤 행동이 "되돌릴 수 없는" 행동인지 에이전트가 판별할 수 있나? 승인 요청 빈도와 성공률의 관계는? 사람의 답이 늦거나 틀릴 때 어떻게 하나? 실시간 음성에서는 "물어보는" 비용이 어떻게 달라지나?

6.2 미해결 문제 4개

문제쉽게 풀면근거
P1. 반복·장기 신뢰성같은 일을 여러 번 시키면 매번 성공하지 못하고, 긴 일일수록 성공률이 0에 가까워진다.pass^k 급락 [14]; 필요한 행동 수가 늘수록 성공률 0에 수렴 [14]; 7개 멀티 에이전트 시스템 실패율 41~86.7% [7]
P2. 비용 대비 효과의 기준 부재얼마를 더 써서 얼마를 얻었는지 재는 표준이 없다. 비용 없는 성능 비교가 관행이다.토큰 1천 개당 성공 수 단일 67.7 vs Hybrid 13.6 [2]; 멀티는 채팅의 15배 토큰 [9]; 평가 서베이가 비용·효율 지표 공백을 지적 [10]; 제3자 비용 통제 리더보드(HAL)는 7개 벤치마크만 다룸 [19]
P3. 신뢰할 수 있는 평가와 안전시험 자체를 믿을 수 없고, 멀티 에이전트 표준 시험이 없으며, 안전 평가는 비어 있다.감사한 13개 벤치마크 전부 critical risk, 45건의 작동하는 해킹 [11]; 서베이: 안전·정책 준수 평가가 특히 멀티 에이전트에서 공백 [10]; 멀티 전용 벤치마크는 MARBLE·MAFBench 등 초기 단계 [8][6]
P4. 연동 규격의 미성숙에이전트를 서로 연결하는 규격이 아직 흔들린다.MCP 사양 5판, 최신판에 비호환 변경(무상태화·Sampling 폐기) [20]; A2A 1.0.0 직후 [21]; MCP 보안이 "사용자 동의"와 "도구 설명 불신"에 의존 [20]; 프레임워크별 지원은 3.5절 표 참조

7. 주의·한계 — 이 보고서의 수치를 읽을 때

7.1 벤치마크 점수는 해킹될 수 있다 📄

  • UC Berkeley RDI(Hao Wang·Qiuyang Mang·Alvin Cheung·Koushik Sen·Dawn Song)는 2026년 4월, 벤치마크 채점 코드를 분석해 점수 부풀리기를 자동으로 찾는 에이전트로 13개 벤치마크(FrontierCS, BFCL, LiveBench, GAIA, WebArena, AGIEval, AgentBench, Terminal-Bench, tau-bench, MLE-bench, OSWorld, FieldWorkArena, CAR-bench)를 감사했다 [11].
  • 결과: 잠재 취약점 825건, 작동하는 해킹 45건(16종 공격 유형), 13개 전부 critical risk. 가장 흔한 원인은 피평가 코드가 채점기와 같은 프로세스·컨테이너·파일시스템을 공유하는 것 [11].
  • 예시: WebArena는 812개 정답이 담긴 JSON이 에이전트가 읽을 수 있는 파일시스템에 있었고, Terminal-Bench의 한 과업은 C 확장이 "존재하는지만" 확인하고 호출하지 않았다 [11].
  • 같은 글이 인용한 공개 사례: 한 모델이 SWE-bench 궤적의 24.4%에서 git log로 정답 커밋을 베껴 점수가 81.4%에서 76.2%로 교정됨; OpenAI가 SWE-bench Verified 감사 문제의 59.4%에 결함 테스트가 있음을 발견한 뒤 Verified 보고를 중단 [11].
  • 이 보고서 2장의 벤치마크 중 BFCL·GAIA·Terminal-Bench·τ-bench·OSWorld가 감사 대상에 포함된다. 해당 점수에는 ⚠H 표시를 붙였다.

7.2 비교할 수 없는 조건

  • 버전: 벤치마크 버전이 다르면 과업 집합이 달라 비교 불가. τ-bench 2.0 저장소는 2.0 영문 결과가 v1.0.1과 비교 불가하다고 명시 [14]. Terminal-Bench는 확인일 기준 4.1을 표기 [13].
  • 하네스(harness): 같은 모델도 모델을 돌리는 에이전트 코드(프롬프트·도구·재시도 정책)에 따라 점수가 다르다. Terminal-Bench 리더보드가 MODEL 열과 AGENT 열을 따로 두는 이유 [13]. 평가 서베이는 "LLM과 하네스를 분리한 평가"를 미래 과제로 꼽는다 [10].
  • 자체 보고 vs 제3자: 벤더 발표 수치는 "주장"이다. 벤치마크 운영자 검증 표시(SWE-bench) [12]나 제3자 재측정(HAL) [19]과 구분해 읽는다.
  • 표본 크기: 통제 실험의 벤치마크당 문제 수는 20~100개 [2], MAST 사례 연구의 ProgramDev-v0는 32문제 [7]. 효과의 방향은 믿되 소수점 자리는 믿지 않는다.

7.3 이 보고서가 "baseline"이라 부르는 것의 한계

  • 실제 산업 배치의 성공률·비용 통계는 공개 자료가 없다. 이 보고서의 baseline은 공개 벤치마크에서 재현 가능한 수준 + 통제 실험이 보인 구조적 효과이며, 현장 평균이 아니다.
  • 리더보드 수치는 조회일(2026-11-12) 기준 스냅샷이다. 수개월 단위로 1위가 바뀐다.
  • 이 보고서에서 확인하지 못한 항목은 8장 "출처 미확인 목록"에 모았다.

8. 조사 방법과 출처

8.1 수집·표기 원칙

  • 근거 유형과 우선순위: 🔍 공식 리더보드·사양서 → 📄 논문(arXiv HTML판 본문 확인) → 🏢 벤더 자체 보고(주장으로 표기) → 서베이(지형 설명에만 사용). 2차 블로그·비교글은 어떤 수치의 근거로도 쓰지 않았다.
  • 정량 수치 규칙: 축마다 공식 리더보드 하나를 지정해 2026-11-12에 조회. "현재 최고"는 해당 리더보드 1위(운영자 검증 표시 우선), "널리 쓸 수 있는 수준"은 HAL 비용 통제 재측정 최고치(HAL에 없는 축은 "HAL 없음" 표기), "오픈소스"는 오픈 가중치 표시 행 1위. 각 수치에 벤치마크·버전·모델·하네스·산출 방식·비용·출처 유형·조회일을 함께 기록.
  • 멀티 에이전트 효과: 리더보드가 없으므로 통제 실험이 보고한 범위를 조건과 함께 적고, 벤더 사례는 "자체 평가 1건"으로 병기.
  • 성숙도: 자체 등급 판정을 하지 않고 사실 체크리스트(○/×)만 적는다. 판정은 독자가 한다.
  • 분류 체계: 출판된 것만 사용(1장). 자체 분류를 만들지 않았다.
  • 그림·표: 도식은 원본 이미지를 받아 그대로 넣고 출처·조회일을 캡션에 적었다. 표는 원본 수치를 그대로 옮긴 HTML 표 또는 원본 캡처다.
  • 저장소 기존 문서: 참고·인용하지 않았다.

8.2 출처 미확인 목록

  • BrowseComp 현재 최고 수치 — 공식 리더보드가 없고 벤더 모델 카드의 자체 보고치만 존재. 이 보고서에서는 수치를 싣지 않음.
  • 오픈 가중치 여부 — Terminal-Bench(GLM-5.3), τ-bench(Qwen3.5-397B-A17B, GLM-5), OSWorld(Holo3, Kimi K2.6), SWE-bench Pro·GAIA 상위 행: 해당 리더보드에 오픈 표시가 없어 확인하지 못함.
