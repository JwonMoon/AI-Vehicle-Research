## 들어가기 전에 — 자료 전체를 관통하는 "미리 답" 7개

처음 보는 사람이 이 일곱 줄만 외우고 들어가도 된다. 각 줄의 근거는 괄호 안 자료다.

1. **에이전트 = LLM + 도구 호출 + 반복 루프.** 흐름을 모델이 정하면 에이전트, 코드가 정하면 워크플로우다. 단순한 쪽에서 시작한다. (§2, §1, §3)
2. **멀티 에이전트는 기본 업그레이드가 아니다.** 병렬화 가능한 과업에서 크게 좋아지고 순차 과업에서 나빠진다. 평균 개선은 0에 가깝고 분산이 크다. (§14, §12, §15)
3. **멀티는 토큰을 훨씬 많이 쓴다.** 채팅 대비 약 15배, 단일 대비 3~5배의 토큰 효율 저하. 비용을 안 적은 비교는 비교가 아니다. (§12, §14, §27)
4. **실패의 다수는 모델이 아니라 설계·사양 문제다.** 14가지 실패 유형 중 가장 흔한 것은 단계 반복·추론-행동 불일치·종료 조건 인지 실패·과업 사양 불이행이다. (§13)
5. **벤치마크 점수는 "모델 + 하네스 + 버전" 점수다.** 리더보드가 MODEL 열과 AGENT 열을 따로 두는 이유다. 그리고 채점기와 피평가 코드가 격리되지 않은 벤치마크는 해킹된다. (§17, §16, §28)
6. **MCP는 도구용, A2A는 에이전트용.** 수직과 수평. 둘 다 공식 문서가 서로를 보완재로 명시한다. (§29, §30)
7. **프레임워크 선택은 모델 선택만큼 성능을 좌우할 수 있다.** 같은 모델·과업에서 오케스트레이션 구현만으로 지연이 60배 넘게 벌어졌다. (§25, §2)

## 1. Lilian Weng, "LLM Powered Autonomous Agents" (2023-06-23) 📄 🟢

**무슨 자료인가.** OpenAI 연구자의 개인 블로그 글(읽기 31분 표기). LLM을 "두뇌"로 두고 **계획·메모리·도구 사용** 세 요소로 에이전트를 분해한 최초의 널리 읽힌 지도다. 2023년 글이지만 구조와 용어가 지금도 그대로 쓰인다 [1].

**무엇을 보고 공부해야 하나.**
- 맨 위 그림 "Overview of a LLM-powered autonomous agent system"과 그 아래 세 항목(Planning / Memory / Tool use) 요약. 이 한 장이 전체 지도다.
- Component One: Planning — Task Decomposition(CoT, Tree of Thoughts, LLM+P)과 Self-Reflection(ReAct, Reflexion, Chain of Hindsight). ReAct 절의 "Thought / Action / Observation" 형식만은 외운다.
- Component Two: Memory — 사람 기억 분류(감각·단기·장기)를 LLM에 대응시킨 표(단기 = in-context learning, 장기 = 외부 벡터 저장소)와 MIPS(근사 최근접 탐색: LSH·ANNOY·HNSW·FAISS·ScaNN) 비교 그림.
- Component Three: Tool Use — MRKL·TALM·Toolformer·ChatGPT 플러그인·HuggingGPT·API-Bank 순서로 "도구 사용"의 진화.
- 마지막 Challenges 절 세 항목.

**미리 답하자면.**
- 에이전트의 구성 요소는 계획·메모리·도구 사용 셋이고, 나머지는 각 요소의 구현 기법이다.
- 2023년에 꼽은 난제 세 가지 — 유한한 컨텍스트 길이, 장기 계획·과업 분해의 어려움, 자연어 인터페이스의 신뢰성 — 는 지금도 연구 주제다.
- 사례 연구(ChemCrow·Generative Agents·AutoGPT)는 "그 시절 데모"로 읽되, Generative Agents의 메모리 스트림·반성·계획 구조는 지금도 교과서다.

**다음 방향.** 이 글의 ReAct 절을 보고 §3(ReAct 원논문)으로, Generative Agents 절에서 §11로. 세 요소를 알았으니 §2에서 "그 요소를 어떻게 엮는가(패턴)"로 넘어간다.

## 2. Anthropic, "Building effective agents" (2024-12-19) 📄 🟢

**무슨 자료인가.** Anthropic 엔지니어링 블로그. 수십 개 팀과 에이전트를 만든 경험을 정리해 **워크플로우와 에이전트를 구분**하고, 기본 블록(augmented LLM)과 다섯 가지 워크플로우 패턴, 그리고 "에이전트"를 그림으로 정의했다. 2026년 현재 가장 많이 인용되는 용어 기준점이다 [2]. 페이지 상단에 "이후 도구가 많이 바뀌었다"는 안내가 붙어 있으니 도구 이름은 신경 쓰지 말고 개념만 가져간다.

**무엇을 보고 공부해야 하나.**
- "What are agents?" — 워크플로우(미리 정한 코드 경로) vs 에이전트(LLM이 스스로 과정과 도구 사용을 지휘)의 정의.
- "When (and when not) to use agents" — 가장 단순한 해법에서 시작하라는 원칙.
- "Building blocks, workflows, and agents" — 그림 8장: The augmented LLM / Prompt chaining / Routing / Parallelization / Orchestrator-workers / Evaluator-optimizer / Autonomous agent / 코딩 에이전트 흐름. 각 그림을 손으로 다시 그려 본다.
- Appendix 2 "Prompt engineering your tools" — 도구 정의(ACI)를 프롬프트만큼 설계하라는 절.

**미리 답하자면.**
- 성공 사례들은 복잡한 프레임워크가 아니라 단순하고 조합 가능한 패턴을 썼다. 프레임워크는 프롬프트와 응답을 숨기므로 처음엔 API를 직접 쓰라고 권한다.
- 에이전트는 개방형 과업에 맞지만 비용·지연·오류 누적이 크다. 샌드박스 테스트와 가드레일이 필수다.
- 핵심 원칙 셋: 단순성, 투명성(계획 단계를 드러내기), 도구 문서화·테스트.

**다음 방향.** 다섯 패턴 중 Orchestrator-workers가 실제 제품에서 어떻게 돌아가는지 §12로. 루프의 원형은 §3. "언제 에이전트를 쓰지 말아야 하나"는 §15와 §14가 데이터로 답한다.

## 3. Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models" (2022-10) 📄 🟡

**무슨 자료인가.** 추론(chain-of-thought)과 행동(도구 호출)을 **번갈아 생성**하게 한 논문. 추론 흔적이 계획을 세우고 예외를 처리하며, 행동이 외부 지식원과 상호작용해 정보를 모은다. 오늘날 에이전트 루프의 원형이다 [3].

**무엇을 보고 공부해야 하나.**
- 초록과 Figure 1 — 같은 문제를 Standard / CoT only / Act only / ReAct로 풀 때의 궤적 비교. "Thought → Act → Obs"가 반복되는 형식을 눈에 익힌다.
- HotpotQA·FEVER(지식 과업)와 ALFWorld·WebShop(의사결정 과업)의 결과표 — CoT만 쓸 때의 환각·오류 전파가 ReAct에서 어떻게 줄었는지.
- 실패 분석 절 — ReAct도 "추론이 반복 루프에 빠지는" 실패가 있다는 대목. §13의 FM-1.3(단계 반복)과 연결된다.

**미리 답하자면.**
- 추론만(CoT)은 환각과 오류 전파에, 행동만은 계획 부재에 약하다. 둘을 섞으면 서로의 약점을 보완한다.
- 의사결정 과업에서 ReAct는 당시 모방학습·강화학습 기법을 큰 폭으로 앞섰다(초록 기준).
- 궤적이 사람이 읽을 수 있어 해석·신뢰가 쉬워진다 — 이것이 이후 "trace를 보고 실패를 분류하는" 연구(§13)의 전제가 된다.

**다음 방향.** 루프가 어떻게 자기 개선하는지는 §5(Reflexion), 도구 사용을 학습으로 익히는 쪽은 §4(Toolformer). 루프를 여러 개 엮는 쪽은 §6~9.

## 4. (선택) Schick et al., "Toolformer: Language Models Can Teach Themselves to Use Tools" (2023-02) 📄 🟡

**무슨 자료인가.** 모델이 **어느 API를 언제 어떤 인자로 부르고 결과를 어떻게 쓸지**를 자기지도 방식으로 학습하게 한 논문. 계산기·QA·검색·번역·캘린더 도구를 소수 예시만으로 익혔다 [4].

**무엇을 보고 공부해야 하나.** 초록과 방법 그림(API 호출을 텍스트 안에 삽입하고, 손실을 줄이는 호출만 남기는 필터링). 결과표는 "작은 모델이 도구로 큰 모델에 근접한다"는 것만 확인.

**미리 답하자면.** 도구 사용은 프롬프트로도, 학습으로도 넣을 수 있다. 현재 상용 모델의 function calling은 이 두 흐름이 합쳐진 결과다.

**다음 방향.** 함수 호출 정확도를 재는 §22(BFCL)로.

## 5. (선택) Shinn et al., "Reflexion: Language Agents with Verbal Reinforcement Learning" (2023-03) 📄 🟡

**무슨 자료인가.** 가중치를 갱신하지 않고 **언어로 된 자기 반성**을 에피소드 메모리에 쌓아 다음 시도를 개선하는 틀. 코딩(HumanEval)·의사결정·추론 과업에서 효과를 보였다 [5].

**무엇을 보고 공부해야 하나.** Figure(Actor·Evaluator·Self-reflection 세 모듈 구조)와 "반성 텍스트를 최대 몇 개까지 메모리에 두는가" 같은 설계 선택. 초록의 HumanEval 수치는 당시 기준이므로 참고만.

**미리 답하자면.** "실패 → 왜 실패했는지 말로 적기 → 다음 시도에 반영"이 evaluator-optimizer 패턴(§2)의 원형이고, MARBLE의 cognitive planning(§24)도 이 아이디어를 쓴다.

**다음 방향.** §2의 Evaluator-optimizer 그림을 다시 보고, §24에서 멀티 에이전트 계획 전략으로 확장된 모습을 본다.

## 6. Li et al., "CAMEL: Communicative Agents for 'Mind' Exploration of Large Language Model Society" (2023-03) 📄 🟡

**무슨 자료인가.** 두 에이전트(예: AI 사용자 / AI 보조자)에게 **역할을 부여**하고 "inception prompting"으로 사람 개입 없이 대화하며 과업을 끝내게 하는 **role-playing** 틀을 제안한, 멀티 에이전트 패턴의 가장 이른 논문 중 하나 [6].

**무엇을 보고 공부해야 하나.** 역할 부여 프롬프트 구조(과업 명세자 → 사용자 역할 → 보조자 역할)를 보여주는 그림과, 대화가 어떻게 역할 이탈·반복 없이 진행되는지 다루는 절. 부록의 대화 예시 한 편을 끝까지 읽어 본다.

**미리 답하자면.** 역할만 잘 주면 LLM 둘이 꽤 긴 협업을 자율로 끝낸다. 동시에 역할 뒤바뀜·무한 대화·조기 종료 같은 실패가 처음부터 관찰됐다 — §13의 FM-1.2(역할 사양 불이행)·FM-1.5(종료 조건)의 원조다.

**다음 방향.** 역할을 "사람 조직의 절차"로 체계화한 §7(MetaGPT)로.

## 7. Hong et al., "MetaGPT: Meta Programming for A Multi-Agent Collaborative Framework" (2023-08) 📄 🟡

**무슨 자료인가.** 사람 조직의 **표준 운영 절차(SOP)** 를 프롬프트 순서로 인코딩하고 조립 라인처럼 역할(제품 관리자·아키텍트·엔지니어 등)을 배정해, LLM을 단순히 이어 붙일 때 생기는 "연쇄 환각(cascading hallucinations)"을 중간 산출물 검증으로 줄인 논문 [7].

**무엇을 보고 공부해야 하나.** 아키텍처 그림(역할 간에 자연어가 아니라 **구조화된 문서**(PRD·설계도·API 명세)를 넘기는 "publish-subscribe" 흐름)과, "왜 자유 대화가 아니라 구조화 산출물이어야 하는가"를 설명하는 절. 소프트웨어 생성 벤치마크 결과표.

**미리 답하자면.** 멀티 에이전트의 품질은 통신 **형식**에 크게 달린다. 구조화된 중간 산출물은 환각 전파를 줄인다. 이 교훈은 §25(MAFBench)의 "스키마 제약 인터페이스가 약한 모델엔 해가 된다"와 함께 읽어야 균형이 잡힌다.

**다음 방향.** 같은 소프트웨어 팀 시뮬레이션을 "대화"로 푼 §8(ChatDev)과 비교. §13의 Figure 9(ChatDev vs MetaGPT 실패 분포)가 둘의 차이를 수치로 보여준다.

## 8. Qian et al., "ChatDev: Communicative Agents for Software Development" (2023-07) 📄 🟡

**무슨 자료인가.** 설계·코딩·테스트 단계의 전문 에이전트들이 **chat chain**(무엇을 말할지)과 **communicative dehallucination**(어떻게 말할지)으로 안내받으며 대화로 소프트웨어를 만드는 가상 회사 [8].

**무엇을 보고 공부해야 하나.** chat chain 그림(단계 → 하위 과업 → 두 역할의 대화)과 dehallucination 절(답하기 전에 되묻게 하는 규칙). "자연어는 설계에, 프로그래밍 언어는 디버깅에 유리하다"는 관찰.

**미리 답하자면.** 대화형 협업은 유연하지만 되묻기·검증 규칙이 없으면 환각이 전파된다. §13은 ChatDev를 사례 연구로 삼아 역할 프롬프트와 토폴로지를 바꾸면 성공률이 각각 +9.4%p·+15.6%p 오름을 보였다.

- 각 행의 "% Resolved" 정의, 오픈 가중치 표시, "SWE-bench 팀이 직접 수행·검증" 표시.
- 논문 초록 — 2023년 발표 당시 최고 모델(Claude 2)이 1.96%만 풀었다는 출발점. 3년 사이 어디까지 왔는지는 리더보드에서 직접 본다(점수는 적지 않는다).

**미리 답하자면.**
- 같은 모델도 하네스(agent)에 따라 점수가 다르다. 리더보드의 한 행은 "모델+하네스" 조합이다.
- Verified는 결함 문제를 걸러낸 판이지만, Berkeley RDI(§28)는 OpenAI가 감사 문제의 59.4%에 결함 테스트가 있음을 발견해 Verified 보고를 중단했다고 전한다. 그래서 Pro·Bash Only 같은 후속 판이 생겼다.
- 저장소별 분해(Resolved by repository)를 보면 벤치마크가 특정 저장소에 편중돼 있음을 알 수 있다.

**다음 방향.** 비용 축을 더 엄격하게 다룬 §27(HAL)로. "테스트가 정말 과업을 검증하나"는 §28.

## 18. τ-bench (2024-06) · τ²-bench (2025-06) — 논문 📄 🟢 · 공식 저장소 🔍 🟢(README·용어집)

**무슨 자료인가.** 항공·소매(τ)와 통신(τ²) 도메인에서, 에이전트가 **도메인 정책을 지키며 LLM 시뮬레이터 사용자와 대화하고 도구를 써서** 과업을 끝내는지 재는 벤치마크. 대화 끝의 DB 상태를 목표 상태와 비교해 채점하고, 신뢰성 지표 **pass^k**를 도입했다. τ²는 사용자도 도구(모의 휴대폰)로 세계 상태를 바꾸는 **dual-control** 설정을 추가했다 [18].

**무엇을 보고 공부해야 하나.**
- τ-bench 초록 — pass^k의 동기("일관되게 행동하는가")와 당시 최고 함수 호출 에이전트가 과업의 50% 미만, 소매에서 pass^8 25% 미만이었다는 출발점.
- τ²-bench **Figure 1·2** — dual-control 그림과 통신 도메인 예시 궤적(에이전트가 로밍을 켜면 사용자 폰 상태가 바뀜). **Table 1** — 세 도메인의 DB 크기·도구 수·과업 수(통신 114개, 전체 2,285개 중 샘플).
- τ² 4.2절 ablation — **No-User(사용자 없이 에이전트가 혼자 수행) vs Default(사용자 안내)**: gpt-4.1 18%p, o4-mini 25%p 하락. "사용자를 안내하는 일" 자체가 큰 비용이라는 증거.
- τ² Table 2 — 사용자 시뮬레이터의 오류율(통신 16%, 치명 0%; 소매·항공 40~47%). 시뮬레이터가 믿을 만한가를 먼저 확인하는 습관.
- 저장소 용어집의 pass^k 정의 한 줄: "k회 시도 모두 통과한 과업의 비율". README는 2.0 영문 결과가 v1.0.1과 비교 불가라고 명시한다.

**미리 답하자면.**
- pass@k(한 번이라도)와 pass^k(모두)는 다른 지표다. 고객 응대처럼 매번 같은 품질이 필요한 곳의 진짜 지표는 pass^k이며, k가 커질수록 가파르게 떨어진다.
- 사용자와 협력해야 하는 과업은 혼자 하는 과업보다 약 20%p 어렵다(τ² 측정). 통신 도메인 pass^1은 당시 최고 모델들도 34~49%였다(논문 보고 수치).
- 필요한 행동 수·하위 문제 수가 늘수록 성공률은 0에 가까워진다 — 장기 과업의 신뢰성은 아직 미해결이다.

**다음 방향.** "사용자도 행동하는 환경"은 사실상 2-에이전트 시스템이다. §24의 협상·Werewolf 시나리오로 이어진다. 자기 실험(로드맵 4단계)에서 τ² 한 도메인을 쓸 수 있다.

## 29. Model Context Protocol (MCP) — 공식 사이트·사양 2026-07-28·아키텍처 개요 🔍 🟢

**무슨 자료인가.** 에이전트(LLM 애플리케이션)가 **도구·데이터·프롬프트 템플릿**을 표준 방식으로 가져다 쓰게 하는 오픈 프로토콜. JSON-RPC 2.0 기반이며 Language Server Protocol에서 영감을 받았다. 확인일 기준 최신 사양은 2026-07-28판 [29].

**무엇을 보고 공부해야 하나.**
- 아키텍처 개요 페이지 "Participants" — **Host**(여러 MCP 클라이언트를 조정하는 AI 애플리케이션), **Client**(서버 하나와 연결을 유지하는 구성요소), **Server**(컨텍스트를 제공하는 프로그램). "호스트는 서버마다 클라이언트 하나를 만든다"는 문장.
- "Layers" — 데이터 계층(JSON-RPC 프로토콜)과 전송 계층(stdio = 같은 머신의 프로세스 간, Streamable HTTP = 원격, HTTP POST + 선택적 SSE, OAuth 권장).
- "Primitives" — 서버 기본 요소 셋: **Tools**(모델이 실행할 함수), **Resources**(사용자·모델이 쓸 데이터), **Prompts**(사용자용 템플릿). 클라이언트 기본 요소: **Elicitation**(서버가 사용자에게 추가 정보를 요청). 2026-07-28판에서 **Sampling(서버가 클라이언트 LLM에 생성 요청)과 Logging은 폐기(deprecated)** 되었다.
- 사양 "Key Details" — 이 판의 큰 변화: **무상태(stateless)** 프로토콜로 전환, 모든 요청이 버전·능력을 `_meta`에 담음, 필수 `server/discover`, 알림은 `subscriptions/listen`으로 opt-in.
- "Security and Trust & Safety" — "호스트는 어떤 도구를 호출하기 전에도 명시적 사용자 동의를 얻어야 한다", "도구 설명(annotations)은 신뢰된 서버가 아니면 신뢰하지 말라".
- 아키텍처 페이지의 예시 JSON(tools/list → tools/call → notifications)을 한 번 따라 읽는다.

**미리 답하자면.**
- MCP는 "에이전트 ↔ 도구" 연결의 사실상 표준이다. 서버를 한 번 만들면 어느 호스트에서든 쓸 수 있다는 것이 가치다.
- 사양은 살아 있다 — 2024-11 → 2025-03 → 2025-06 → 2025-11 → 2026-07 다섯 판이 나왔고, 최신판은 무상태화와 Sampling 폐기라는 비호환 변화를 담았다. 블로그의 "MCP 기본 요소 = tools·resources·prompts·sampling·roots" 설명은 구판 기준일 수 있다.
- 보안 모델의 핵심은 "사용자 동의"와 "서버 불신"이다. 도구 설명 자체가 공격 벡터가 될 수 있다.

**다음 방향.** 에이전트가 **다른 에이전트**에게 일을 맡기는 층은 §30. 프레임워크가 MCP 클라이언트를 어떻게 품는지는 §31~36의 MCP 페이지에서만 확인.

## 30. Agent2Agent (A2A) Protocol — 공식 사이트·사양 1.0.0·Key Concepts·"A2A and MCP" 🔍 🟢

**무슨 자료인가.** 서로 다른 에이전트가 **발견·협상·위임**으로 함께 일하게 하는 오픈 표준. Linux Foundation 산하(Apache 2.0, "Agentic AI Foundation" 합류 공지)이고 확인일 기준 사양 1.0.0이다. 핵심 설계 원칙은 Simple·Enterprise Ready·Async First·Modality Agnostic·**Opaque Execution**(원격 에이전트 내부를 몰라도 위임) [30].

**무엇을 보고 공부해야 하나.**
- Key Concepts 페이지의 표 "Fundamental Communication Elements" — **Agent Card**(정체·능력·엔드포인트·스킬·인증을 적은 JSON, `/.well-known/agent-card.json`으로 발견), **Task**(고유 ID와 생애주기를 가진 상태 있는 작업 단위), **Message**(한 턴, 역할 user/agent), **Part**(텍스트·파일·구조화 데이터 중 하나를 담는 기본 컨테이너), **Artifact**(과업 산출물). 그리고 contextId(관련 Task 묶기).
- 사양 4.1.3 **TaskState** — SUBMITTED → WORKING → COMPLETED/FAILED/CANCELED/REJECTED(종결), 중간의 INPUT_REQUIRED·AUTH_REQUIRED(중단 상태). 종결 상태의 Task에는 메시지를 더 보낼 수 없다.
- 3.1 Core Operations — Send Message / Send Streaming Message / Get Task / List Tasks / Cancel Task / Subscribe / Push Notification Config / Extended Agent Card. 3.5 — 스트리밍(SSE)과 푸시 알림(웹훅) 두 갱신 경로.
- 9~11장 — 세 바인딩: JSON-RPC 2.0 over HTTP(S), gRPC, HTTP+JSON/REST. 5.3 Method Mapping 표로 셋이 기능적으로 동등함을 확인.
- **"A2A and MCP" 페이지** — "MCP는 수직(에이전트를 깊게), A2A는 수평(에이전트들을 연결)" 문단과 **자동차 정비소 예시**(고객 에이전트 → A2A → 정비소 에이전트 → MCP 도구 `scan_vehicle_for_error_codes`·`get_repair_procedure`·`raise_platform`). 사양 Appendix B "Relationship to MCP"도 같은 내용.

**미리 답하자면.**
- A2A는 에이전트를 **블랙박스 서비스**로 취급한다. Agent Card만 보고 Task를 보내고, 상태를 폴링·스트리밍·푸시로 받는다. 장기 비동기 과업과 사람 개입(INPUT_REQUIRED)이 1급 개념이다.
- 공식 문서 표현: "A2A는 에이전트들이 과업에서 **협력**하는 것, MCP는 에이전트가 **능력을 사용**하는 것. 둘을 함께 쓰라."
- 보안은 표준 웹 인증(API Key·HTTP Auth·OAuth2·OIDC·mTLS)을 Agent Card에 선언하는 방식이며, Agent Card 서명 체계가 있다.

**다음 방향.** 프레임워크들이 A2A 서버/클라이언트를 공식 지원하는지는 **각 프레임워크의 공식 문서에서만** 확인한다(2차 글은 상충). §31~36.

<a id="31"></a>
## 31. LangGraph — 공식 문서 (docs.langchain.com) 🔍 🟡

**무슨 자료인가.** 에이전트 시스템을 **노드(처리 함수)와 엣지(제어 흐름)의 방향 그래프**로 모델링하는 LangChain의 프레임워크. 상태 관리·체크포인트·사람 개입(interrupt)·서브그래프가 1급 개념이다. 구 주소(langchain-ai.github.io/langgraph)는 "문서가 이전됐다" 안내만 남아 있다 [31].

**무엇을 보고 공부해야 하나.** Overview → 핵심 개념(State·Node·Edge·Graph) → Persistence/Checkpointing → Human-in-the-loop(interrupt·resume) → Subgraphs(멀티 에이전트 구성) → MCP 연동 페이지. 같은 예제 과업을 그래프로 그려 본다.

**미리 답하자면.** 제어 흐름을 개발자가 명시하는 "그래프형" 패러다임의 대표. MAFBench(§25)는 이를 graph-based로 분류하고, 오케스트레이션 오버헤드가 직접 호출 대비 작음(p50 548ms vs 495ms)을 측정했다. 자유도가 큰 대신 그래프 설계를 사람이 해야 한다.

**다음 방향.** 반대편 패러다임(역할·태스크 선언)인 §32와 같은 과업으로 비교.

<a id="32"></a>
## 32. CrewAI — 공식 문서 🔍 🟡

**무슨 자료인가.** 역할·목표를 가진 에이전트들의 **크루(crew)** 와 이벤트 기반 **flows**를 선언해 협업시키는 역할 기반 프레임워크. 공식 문서는 "collaborative AI agents, crews, and flows — production ready from day one"을 표방한다 [32].

**무엇을 보고 공부해야 하나.** Introduction → Agents / Tasks & Processes / Flows 개념 페이지 → 계획(planning) 기능이 어떤 **스키마**로 계획을 받는지 → MCP·A2A 지원 페이지. 내부 라우팅이 어디까지 보이는지(관측 가능성)를 확인.

**미리 답하자면.** 빠른 프로토타이핑에 강한 "역할형" 패러다임의 대표. MAFBench(§25)는 CrewAI의 **스키마 제약 계획 인터페이스**가 약한 모델에서 형식 위반으로 정확도를 크게 떨어뜨렸고(최대 84.7% 위반), 도구 결과마다 모델 호출을 한 번 더 쓴다고 보고했다(Table 4). 역할 이름만 주는 특화는 효과가 없고 절차를 줘야 한다는 P4 원칙도 이 계열에 해당한다.

**다음 방향.** 모델사 SDK 쪽(§33·§36)은 패턴을 강제하지 않는 쪽으로 간다 — 비교.

## 33. OpenAI Agents SDK — 공식 문서 🔍 🟡

**무슨 자료인가.** 에이전트·도구 호출·**handoffs**·guardrails 같은 기본 요소를 제공하고 오케스트레이션 패턴을 강제하지 않는 OpenAI의 경량 SDK. 문서 첫 페이지가 "Why use the Agents SDK"와 **"Agents SDK or Responses API?"** 를 먼저 묻는다 [33].

**무엇을 보고 공부해야 하나.** 첫 페이지의 두 질문 → Hello world → Handoffs(에이전트 간 주도권 이전의 1급 개념) → Guardrails → Tracing → MCP 페이지. "SDK 없이 API만으로 충분한 경우"를 문서가 어떻게 정의하는지.

**미리 답하자면.** 핸드오프는 "대화를 통째로 다른 에이전트에게 넘기는" 방식으로, 지휘자-작업자(§12)와 다른 멀티 에이전트 구성법이다. MAFBench(§25)는 이 SDK의 메모리를 "누적형(accumulation)"으로 분류하고 컨텍스트가 커질수록 런타임이 가파르게 느는 것을 보였다(Figure 4).

**다음 방향.** 같은 "벤더 SDK" 범주의 §34·§36과 핸드오프/위임 개념을 비교.

## 34. Google Agent Development Kit (ADK) — 공식 문서 (adk.dev) 🔍 ⚪

**무슨 자료인가.** Google의 에이전트 개발 키트. 문서 주소가 google.github.io/adk-docs에서 adk.dev로 이전했고, 이 환경에서는 새 호스트를 열지 못했다 [34].

**무엇을 보고 공부해야 하나.** (일반 안내) 에이전트 유형(LLM 에이전트·워크플로우 에이전트·커스텀)과 멀티 에이전트 구성 페이지, 그리고 **A2A 페이지** — 2차 글들은 ADK의 A2A 지원이 가장 성숙하다고 주장하므로 공식 문서로 확인한다. MCP 도구 연동 페이지.

**미리 답하자면.** (요지 기준) Google이 A2A를 주도했으므로 ADK가 A2A 서버/클라이언트를 가장 먼저 지원했을 가능성이 크지만, 이 문서에서는 확인하지 못했다 — 출처 미확인.
