# AI 에이전트 · 멀티 에이전트 연동 — 처음 시작하는 사람의 학습 로드맵

> **작성일**: 2026-11-11
> **문서 성격**: 학습 **순서표**다. 무엇을 어떤 순서로 보고, 각 단계가 끝났을 때 무엇을 설명할 수 있어야 하는지를 정한다. 개념 설명은 [`primer.md`](primer.md)(요약본), 자료마다 "무슨 내용·어디를 봐야 하나·미리 답하자면"은 [`reading-guide.md`](reading-guide.md)(자료 가이드)에 있다. 이 문서의 `[번호]`는 [`reference/references.md`](reference/references.md)의 출처 번호다.
> **출처 원칙**: 사실 문장에는 `[번호]` 출처를 붙인다. 벤치마크 **점수는 적지 않는다**. 점수는 주 단위로 바뀌므로 "어디서, 어떻게 읽는가"만 가르친다. 등급: 🔍 공식 · 📄 논문·기술 블로그 · 📰 언론·서드파티.
> **범위**: 텍스트 기반 단일 에이전트 기초 → 멀티 에이전트 연동·평가·프로토콜·프레임워크. 음성 에이전트와 차량 도메인 응용은 범위 밖(상위 폴더의 baseline 조사가 다룬다).
> **비참고 원칙**: 저장소의 기존 문서는 참고·인용하지 않고 외부 공개 자료만 썼다.

## 0. 이 로드맵이 답하려는 질문

> "AI 에이전트·멀티 에이전트 연동의 **현존 기술 수준(baseline)** 을 정량·정성으로 파악하려면 무엇을 봐야 하나?"

답의 전제는 하나다. **"현존 기술 수준"은 숫자 하나가 아니라 세 층이다.**

| 층 | 묻는 것 | 어디서 재나 | 로드맵 단계 |
|---|---|---|---|
| ① 단일 에이전트 능력 | 모델 하나가 도구를 들고 과업을 끝까지 해내는가 | 공개 벤치마크 리더보드 (코딩·터미널·고객응대·웹·컴퓨터 조작) [16–22] | 2단계 |
| ② 멀티 에이전트 협업 효과 | 여러 에이전트로 나누면 단일보다 **얼마나, 언제** 나아지나 (그리고 비용은) | 통제 실험 논문 [12][14], 멀티 전용 벤치마크 [24][25], 실패 분류 [13] | 1·2단계 |
| ③ 연동 기술 성숙도 | 프레임워크·프로토콜이 무엇을 표준화했고 무엇이 아직 제각각인가 | 공식 문서·사양서 [29–36] | 3단계 |

세 층을 섞어서 "멀티 에이전트가 SWE-bench에서 몇 점"처럼 말하면 반드시 틀린다. 층을 나눠 보는 습관이 이 로드맵의 첫 목표다.

**총 예상 기간**: 주 5~8시간 기준 **6~9주**. 각 단계 끝의 체크리스트를 통과하면 다음으로 넘어간다.

```
 0단계 선행 점검 (며칠)
   │
 1단계 개념 뼈대 (1~2주) ── 에이전트 = LLM + 도구 + 루프 / 멀티 패턴 4종 / 언제 도움·언제 해악 / 실패 유형
   │
 2단계 정량 baseline (2~3주) ── 벤치마크 지도 / 리더보드 읽는 법 / 멀티 평가의 현실 / 점수 함정
   │
 3단계 정성 비교 (1~2주) ── MCP·A2A 사양 / 프레임워크 6종 비교 축
   │
 4단계 직접 측정 (2주) ── 소규모 실험: 단일 vs orchestrator-worker vs 토론형, 성공률·토큰·지연·실패 유형
```

### 2.2 1단계 체크리스트 (설명할 수 있으면 통과)

- [ ] 워크플로우와 에이전트의 차이를 한 문장으로, 그리고 Anthropic 기본 패턴 5종(prompt chaining · routing · parallelization · orchestrator-workers · evaluator-optimizer)의 그림을 손으로 그릴 수 있다 [2]
- [ ] ReAct 루프의 세 단계와, 루프가 끝나는 조건이 왜 중요한지 말할 수 있다 [3][13]
- [ ] 멀티 에이전트 기본 패턴 4종(orchestrator-worker · 역할 분담 · 토론 · 계층/핸드오프)의 차이와 각각의 원류 논문을 짝지을 수 있다 [6–10][12]
- [ ] "멀티 에이전트는 기본 업그레이드가 아니다"를 **근거 두 개**(비용 배수 [12], 과업 유형별 증감 [14])와 함께 말할 수 있다
- [ ] MAST 실패 3범주의 이름을 대고, 각 범주에서 예 하나씩을 들 수 있다 [13]

## 3. 2단계 — 정량 baseline: 벤치마크 지도 (2~3주)

**목표**: 리더보드를 **스스로 읽고 기록**할 수 있게 된다. 점수를 외우는 것이 아니라 "이 숫자가 무엇을 재고 무엇을 안 재는지"를 판별하는 능력이 목표다. 먼저 [`primer.md`](primer.md) 4~5장을 읽는다.

### 3.1 벤치마크 지도 — 무엇이 무엇을 재는가

### 3.2 리더보드 읽기 규칙 — 점수 하나를 기록할 때 반드시 같이 적는 것

| 항목 | 왜 필요한가 | 근거 |
|---|---|---|
| 벤치마크 **이름과 버전** | 버전이 다르면 비교 불가. Terminal-Bench는 확인일 기준 사이트가 4.1을 표기할 정도로 자주 바뀐다 | [17] |
| **모델과 하네스(scaffold/agent)** | 리더보드 자체가 MODEL 열과 AGENT 열을 따로 둔다. 같은 모델도 하네스에 따라 점수가 다르다 | [17][16] |
| **점수 산출 방식** | pass@1인지, 몇 회 시도인지, pass^k(k회 모두 성공)인지 | [18] |
| **비용·토큰·지연** | 멀티 에이전트 비교의 실질 지표. 비용 없는 비교는 비교가 아니다 | [12][14][27] |
| **출처 유형** | 벤더 자체 보고(주장)인지, 벤치마크 운영자 검증인지, 제3자 재측정인지 | [16][27] |
| **조회 날짜** | 수개월 단위로 1위가 바뀐다 | — |

### 3.3 점수 함정 — 2단계에서 반드시 읽는 경고

- **벤치마크 해킹 가능성** [28]: Berkeley RDI가 2026년 4월 자동 감사 에이전트로 13개 벤치마크를 점검해 45건의 작동하는 점수 부풀리기와 16종의 공격 유형을 확인했고, 모든 벤치마크를 "critical risk"로 분류했다. 채점기와 피평가 코드가 같은 프로세스·컨테이너·파일시스템을 공유하는 것이 가장 흔한 원인이다.
- **데이터 오염·결함 있는 테스트** [28]: 같은 글은 한 모델이 SWE-bench 궤적의 24.4%에서 git log로 정답 커밋을 베껴 점수가 교정된 사례와, OpenAI가 Verified 감사 문제의 59.4%에 결함 테스트가 있음을 발견해 보고를 중단했다는 사실을 인용한다.
- **하네스 효과**: 동일 모델도 하네스 차이로 점수가 달라지므로, 모델 비교는 같은 하네스 안에서만 한다 [17][27].

### 3.4 2단계 체크리스트

- [ ] 단일 에이전트 벤치마크 6종이 각각 "무슨 능력"을 재는지 한 줄씩 말할 수 있다
- [ ] pass@k와 pass^k의 차이를 설명하고, 왜 고객응대 에이전트에 pass^k가 중요한지 말할 수 있다 [18]
- [ ] 리더보드 한 줄을 §3.2 표의 6개 항목으로 완전히 기록해 봤다 (벤치마크 2개 이상)
- [ ] "멀티 에이전트 전용 표준 벤치마크는 아직 없다"가 왜 사실인지, MARBLE·MAFBench가 각각 무엇을 보완하는지 말할 수 있다 [24][25][26]
- [ ] 벤치마크 점수가 부풀려질 수 있는 경로 두 가지를 예와 함께 말할 수 있다 [28]

## 4. 3단계 — 정성 비교: 프로토콜·프레임워크 (1~2주)

**목표**: 공식 사양·문서만으로 프레임워크 간 차이를 **6개 축**으로 정리할 수 있게 된다. 먼저 [`primer.md`](primer.md) 6장과 8장을 읽는다.

### 4.1 프로토콜 — 사양서를 직접 읽는다

| 프로토콜 | 연결하는 것 | 읽을 페이지 | 가이드 |

### 4.2 프레임워크 — 6개 축으로 같은 표를 채운다

| 축 | 질문 | 어디서 확인 |
|---|---|---|
| 상태·제어 흐름 표현 | 그래프인가, 역할·태스크 선언인가, 코드 안의 루프인가 | 각 문서의 "개념/Concepts" 장 |
| 핸드오프·위임 | 에이전트 간 작업 넘김이 1급 개념인가, 도구 호출로 흉내 내는가 | OpenAI Agents SDK "handoffs", LangGraph 서브그래프, CrewAI flows |
| 사람 개입(HITL) | 중단·승인·재개가 내장인가 | LangGraph interrupt, 각 SDK의 approval |
| 관측 가능성 | 모든 프롬프트·응답을 추적할 수 있는가 | tracing 장 |
| 내구성 | 장시간 실행·재시작·체크포인트 | checkpoint/persistence 장 |
| 프로토콜 지원 | MCP 클라이언트? A2A 서버/클라이언트? | 공식 문서의 MCP/A2A 페이지 **만** 신뢰 |

대상: LangGraph [31] · CrewAI [32] · OpenAI Agents SDK [33] · Google ADK [34] · Microsoft Agent Framework [35] · Claude Agent SDK [36]. 각 1~2시간, 같은 예제 과업(예: "두 출처를 조사해 비교표 작성")을 각 프레임워크 Quickstart 스타일로 어떻게 짜게 되는지만 본다. 블로그 비교글은 사양 확인용으로 쓰지 않는다 — 프로토콜 지원 여부는 글마다 상충한다(확인: 2026-11 웹 검색).

### 4.3 3단계 체크리스트

- [ ] MCP의 세 참여자(host·client·server)와 서버 기본 요소 3종을 말하고, A2A의 Agent Card·Task·Message·Artifact가 각각 무엇인지 말할 수 있다 [29][30]
- [ ] "MCP는 도구용, A2A는 에이전트용"이 왜 경쟁이 아니라 보완인지, A2A 공식 문서의 설명을 인용해 말할 수 있다 [30]
- [ ] 프레임워크 6종을 §4.2 표로 채웠고, 각 칸에 공식 문서 URL이 붙어 있다
- [ ] AutoGen이 왜 신규 학습 대상에서 빠졌는지(Microsoft Agent Framework로의 통합) 말할 수 있다 [35]

## 5. 4단계 — 직접 측정: 내 baseline 만들기 (2주)

읽기만 하면 숫자가 남지 않는다. 작은 실험 하나가 논문 수십 편보다 "멀티가 언제 도움이 되는지"를 몸에 남긴다.

### 5.1 실험 설계

| 요소 | 선택 | 근거 |
|---|---|---|
| 과업 | τ²-bench 한 도메인 20~30개 **또는** SWE-bench Lite 20~30개 | 전자는 pass^k 측정, 후자는 코딩. 둘 다 공식 하네스가 있다 [16][18] |
| 비교 조건 | ① 단일 에이전트 ② orchestrator-worker ③ 토론형(peer debate + voting) | [14]가 비교한 아키텍처 중 가장 대비가 큰 세 가지 |
| 고정 | 모델·도구·프롬프트 템플릿·총 추론 토큰 예산 | [14]의 통제 원칙(도구·프롬프트·연산 표준화) |
| 지표 | 성공률(pass@1, 가능하면 pass^3), 총 토큰, 벽시계 시간, 실패 유형 | 실패 유형은 MAST 14종으로 라벨링 [13] |
| 기록 | §3.2 표 6개 항목 + 실패 유형 분포 | — |

### 5.2 예상되는 결과와 해석 틀 (미리 답하자면)

- 병렬로 쪼갤 수 있는 과업(여러 출처 조사)에서는 orchestrator-worker가 단일보다 좋아질 수 있지만 토큰은 수 배 늘어난다 [12][14].
- 순차 의존이 강한 과업(코드 수정)은 멀티가 오히려 나빠지기 쉽다 [14][12].
- 실패의 다수는 모델 능력이 아니라 사양·역할·종료 조건·검증 설계에서 온다 [13]. 실험에서 FC1(시스템 설계)·FC3(검증) 라벨이 많이 나오면 프롬프트·토폴로지 수정으로 개선 여지가 있다는 뜻이다 [13].

### 5.3 4단계 체크리스트

- [ ] 세 조건의 성공률·토큰·시간을 한 표에 적었다
- [ ] 실패 사례 10개 이상에 MAST 라벨을 붙였고, 가장 많은 범주를 안다
- [ ] "이 과업에서 멀티는 (이득/손해)였고, 그 이유는 과업의 (병렬성/순차성/도구 비중) 때문"이라는 문장을 쓸 수 있다
