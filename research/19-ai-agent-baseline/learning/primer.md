## 1. 한 장 요약

```
            ┌──────────────────────────────────────────┐
            │  에이전트 = LLM + 도구 호출 + 반복 루프    │
            │  (생각 → 행동 → 관찰 → … → 종료 판단)      │
            └──────────────────────────────────────────┘
                        │ 여러 개를 엮으면
                        ▼
   ┌────────────┬────────────┬────────────┬────────────┐
   │ 지휘자-작업자 │  역할 분담   │    토론     │ 계층·핸드오프 │   ← 멀티 에이전트 패턴 4종
   └────────────┴────────────┴────────────┴────────────┘
                        │ 핵심 질문은 하나
                        ▼
        "언제 멀티가 단일보다 나아지고, 비용은 얼마나 더 드나?"
```

- **에이전트**는 언어 모델이 목표를 받아 도구를 부르고 결과를 관찰하며 여러 단계를 스스로 진행해 과업을 끝내는 시스템이다. 흐름을 코드가 미리 정하면 **워크플로우**, 모델이 매 단계 스스로 정하면 **에이전트**다 [2].
- **멀티 에이전트**는 이런 에이전트 여러 개가 역할을 나눠 통신하며 하나의 과업을 수행하는 구조다. 2023년 CAMEL·MetaGPT·ChatDev·AutoGen이 패턴을 만들었고 [6–9], 2025년 이후 통제 실험이 "언제 도움이 되는가"를 재기 시작했다 [13][14].
- **현존 기술 수준(baseline)** 은 숫자 하나가 아니다. ① 단일 에이전트 능력(공개 벤치마크), ② 멀티 협업의 증분 효과와 비용, ③ 프레임워크·프로토콜 성숙도, 세 층을 따로 재야 한다. 이 요약본의 2~8장은 그 세 층을 순서대로 설명한다.

**미리 답하자면** — 이 분야를 처음 보는 사람이 외우고 들어가면 좋은 결론 세 가지.
1. 멀티 에이전트는 "기본 업그레이드"가 아니다. 병렬로 쪼갤 수 있는 과업에서는 크게 좋아지고, 순차 의존이 강한 과업에서는 오히려 나빠진다 [14]. 그리고 토큰을 훨씬 많이 쓴다 [12].
2. 실패의 다수는 모델이 멍청해서가 아니라 **사양·역할·종료 조건·검증 설계**가 허술해서 생긴다 [13].
3. 벤치마크 점수는 모델 점수가 아니라 "모델 + 하네스 + 벤치마크 버전" 점수다. 비용과 조회 날짜 없이 적힌 점수는 비교에 쓸 수 없다 [16][17][27][28].

## 2. 에이전트 기본 구조

### 2.1 그림

```
   사용자 목표
      │
      ▼
 ┌─────────────────────────── 에이전트 루프 ───────────────────────────┐
 │                                                                     │
 │   [LLM]  ──생각(Thought)──▶  행동(Action: 도구 호출 요청)              │
 │     ▲                               │                               │
 │     │                               ▼                               │
 │  관찰(Observation) ◀── 도구 실행(검색·코드 실행·API·파일) ── 바깥 코드가 수행 │
 │     │                                                               │
 │     └─ 메모리(컨텍스트 창 = 단기 / 외부 저장소 = 장기) ─ 가드레일·사람 개입 │
 │                                                                     │
 │   종료 판단: "끝났다" 또는 "포기/사람에게 넘김" ───────────────────────▶ 결과 │
 └─────────────────────────────────────────────────────────────────────┘
```

### 2.2 설명

**구성 요소 다섯 가지.** Lilian Weng의 2023년 정리가 지금도 그대로 쓰인다 — LLM을 "두뇌"로 두고 **계획**(하위 목표 분해 + 자기 반성), **메모리**(단기 = 컨텍스트 안의 in-context learning, 장기 = 외부 벡터 저장소와 빠른 검색), **도구 사용**(모델 가중치에 없는 정보·능력을 외부 API로 보충)이 붙는다 [1]. Anthropic은 같은 것을 "augmented LLM"(검색·도구·메모리가 붙은 LLM)이라고 부르며 모든 패턴의 기본 블록으로 놓는다 [2]. 여기에 실무에서는 **가드레일**(입출력 검사·권한 제한)과 **사람 개입 지점**(승인·중단·재개)이 더해진다 [2].

**루프의 원형은 ReAct다.** 2022년 ReAct 논문은 추론 흔적(Thought)과 과업별 행동(Action)을 번갈아 생성하게 하면, 추론이 계획을 세우고 예외를 처리하며 행동이 외부 지식원(위키 API 등)과 상호작용해 환각과 오류 전파를 줄인다는 것을 보였다 [3]. 오늘날 모든 에이전트 프레임워크의 내부 루프는 이 "생각 → 행동 → 관찰"의 변주다.

**도구 호출은 구조화 출력이다.** 모델은 "이 함수를 이 인자로 불러 달라"는 형식의 텍스트(JSON)를 내고, 실제 호출은 바깥 코드가 한다. 모델이 직접 세상을 건드리는 것이 아니라는 점이 중요하다 — 그래서 어떤 도구를 어떤 설명으로 노출하는지가 성능을 좌우한다. Anthropic은 이를 "agent-computer interface(ACI)"라 부르며 프롬프트 설계만큼 공들여야 한다고 말한다 [2]. 함수 호출 정확도 자체를 재는 벤치마크가 BFCL이다 [22].

**워크플로우 vs 에이전트.** Anthropic의 구분이 표준이 됐다. 미리 정한 코드 경로로 LLM과 도구를 엮으면 **워크플로우**, LLM이 스스로 과정과 도구 사용을 지휘하면 **에이전트**다 [2]. 같은 글은 기본 워크플로우 패턴 다섯 가지를 그림으로 정리한다 [2]:

| 패턴 | 한 줄 설명 | 언제 쓰나 |
|---|---|---|
| Prompt chaining | 단계를 고정 순서로 이어 붙이고 중간 검사 | 과업을 명확한 하위 과업으로 쪼갤 수 있을 때 |
| Routing | 입력을 분류해 전용 처리로 보냄 | 입력 유형이 뚜렷이 갈릴 때 |
| Parallelization | 쪼개서 동시에 돌리거나(sectioning) 여러 번 돌려 투표(voting) | 독립 하위 과업, 또는 신뢰도 확보 |
| Orchestrator-workers | 중앙 LLM이 동적으로 하위 과업을 만들어 작업자에 위임·종합 | 하위 과업을 미리 알 수 없을 때 |
| Evaluator-optimizer | 생성자와 평가자가 반복 루프 | 명확한 평가 기준이 있고 반복이 가치 있을 때 |

**자율성 사다리.** 조사에서는 "에이전트"라는 말이 챗봇부터 몇 시간짜리 자율 과업까지 다 가리키므로, 레벨을 나눠 말해야 한다. 이 학습 트랙에서는 L0 단발 질의응답 → L1 단일 도구 호출 → L2 다단계 계획·실행(사람 확인 개입) → L3 장기 과업 자율 수행(수십~수백 단계) → L4 다중 에이전트 협업으로 부른다. 벤치마크도 레벨별로 다르다 — L1은 BFCL [22], L2는 τ-bench류 [18], L3는 SWE-bench·Terminal-Bench·OSWorld [16][17][21], L4는 아직 표준이 없다(5장).

### 2.3 미리 답하자면

- Anthropic의 조언은 "가장 단순한 해법에서 시작해 필요가 입증될 때만 복잡도를 더하라"다. 많은 경우 검색·예시가 붙은 LLM 호출 한 번으로 충분하다 [2].
- 에이전트는 개방형 과업에 맞지만 지연·비용이 크고 오류가 누적된다. 그래서 샌드박스에서 충분히 테스트하고 가드레일을 두라고 권한다 [2].
- Weng이 2023년에 꼽은 세 가지 난제 — 유한한 컨텍스트 길이, 장기 계획·과업 분해의 어려움, 자연어 인터페이스의 신뢰성 — 는 2026년에도 그대로 연구 주제다 [1].

## 3. 멀티 에이전트 패턴

### 3.1 그림 — 네 가지 기본형과 통신 토폴로지

```
 ① 지휘자-작업자(orchestrator-worker)   ② 역할 분담(role-play / SOP)
        [지휘자]                              [기획] → [설계] → [구현] → [테스트]
       /   |   \                                 (사람 조직의 절차를 그대로)
   [작업자][작업자][작업자]
   (병렬 조사·종합)

 ③ 토론(debate)                          ④ 계층·핸드오프(hierarchy / handoff)
   [A] ⇄ [B] ⇄ [C]  → 투표/합의              [접수] ──handoff──▶ [전문가1]
   (같은 문제를 여럿이 풀고 서로 비판)                      └──────▶ [전문가2]
                                               (대화 주도권을 통째로 넘김)

 통신 토폴로지(연결 모양): 중앙집중(hub-and-spoke) / 분산(peer mesh) / 독립(통신 없음, 끝에만 합침) / 혼합
```

### 3.2 설명

**원류 논문 네 편이 네 패턴을 만들었다.**
- **역할 분담(role-play)** — CAMEL(2023-03)은 두 에이전트에게 역할을 주고 "inception prompting"으로 사람 개입 없이 협력해 과업을 끝내게 하는 틀을 제안했다 [6]. MetaGPT(2023-08)는 사람 조직의 **표준 운영 절차(SOP)** 를 프롬프트 순서로 인코딩하고 조립 라인처럼 역할을 배정해, LLM을 단순히 이어 붙일 때 생기는 "연쇄 환각(cascading hallucinations)"을 중간 검증으로 줄였다 [7]. ChatDev(2023-07)는 설계·코딩·테스트 단계의 전문 에이전트가 "chat chain"으로 무엇을 말할지, "communicative dehallucination"으로 어떻게 말할지를 안내받는 소프트웨어 회사 시뮬레이션이다 [8].
- **대화 기반 범용 프레임워크** — AutoGen(2023-08)은 "대화 가능한(conversable)" 에이전트들이 LLM·사람 입력·도구를 조합해 대화하며 과업을 푸는 범용 기반을 제시했다 [9]. 이후 Microsoft는 AutoGen과 Semantic Kernel을 Microsoft Agent Framework로 통합했다 [35].
- **토론(debate)** — Du et al.(2023-05)은 여러 LLM 인스턴스가 각자 답과 근거를 내고 여러 라운드 토론해 공통 답에 이르게 하면 수학·전략 추론과 사실성이 좋아진다고 보고했다. "society of minds" 접근이라 부른다 [10].
- **지휘자-작업자(orchestrator-worker)** — Anthropic의 리서치 제품은 선두 에이전트(lead)가 사용자 질의를 분석해 전문 하위 에이전트를 만들고 병렬로 탐색시킨 뒤 종합한다. 글은 이를 orchestrator-worker 패턴이라 부른다 [12].

**통신 토폴로지는 패턴과 별개의 축이다.** Google·MIT의 2025년 통제 실험은 다섯 아키텍처를 정의했다 [14]: Single-Agent(한 에이전트가 모든 단계를 순차로), Independent(병렬·통신 없음·끝에만 합침), Centralized(중앙 지휘자가 위임·종합하는 hub-and-spoke), Decentralized(피어 간 직접 통신·합의), Hybrid(계층 감독 + 피어 조정). MultiAgentBench는 star·chain·tree·graph 토폴로지를 비교했다 [24]. 같은 "역할 분담"도 중앙집중으로 엮을 수도, 분산으로 엮을 수도 있다.

**패턴 선택 결정표(이 트랙의 정리).**

| 질문 | 예 → | 아니오 → |
|---|---|---|
| 과업을 독립적 조각으로 쪼갤 수 있나(병렬성) | 지휘자-작업자·Independent가 유리 [12][14] | 단일 에이전트부터 [2][14] |
| 조각 사이에 공유 컨텍스트·의존이 많나 | 단일 에이전트 또는 핸드오프 [12][14] | 병렬 멀티 가능 |
| 정답을 검증할 수 있나(테스트·채점기) | 토론·evaluator-optimizer가 효과 [10][2] | 중앙 검증자(지휘자)를 두어 오류 봉쇄 [14] |
| 도구가 아주 많은가 | 멀티 조정 비용이 불균형하게 커진다 → 신중 [14] | — |

### 3.3 미리 답하자면

- Anthropic 리서치 시스템은 내부 평가에서 단일 에이전트(Claude Opus 4) 대비 90.2% 좋아졌지만, 멀티 에이전트는 채팅 대비 약 15배의 토큰을 쓴다고 명시한다. 그래서 "과업 가치가 충분히 클 때만" 쓰라고 한다 [12].
- 같은 글은 멀티가 맞는 곳과 안 맞는 곳을 분명히 가른다 — 폭넓은 병렬 탐색(breadth-first research)에는 맞고, 공유 컨텍스트와 의존이 많은 대부분의 코딩 과업에는 맞지 않는다 [12].
- Google·MIT 실험에서 단일 대비 상대 성능 변화는 분해 가능한 금융 추론에서 +80.8%, 순차 계획에서 −70.0%까지 벌어졌다. 결론은 "아키텍처-과업 정합이 협업 성공을 결정한다"이다 [14].

## 4. 평가 방식 ① — 단일 에이전트 벤치마크

### 4.1 그림 — 벤치마크의 네 부품

```
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  환경     │ +  │  과업     │ +  │  채점기   │ +  │  하네스   │  =  점수
  │(컨테이너,  │    │(이슈,     │    │(숨긴 테스트,│    │(모델을 돌리는│
  │ 웹, DB,   │    │ 질문,     │    │ 정답 일치, │    │ 에이전트 코드:│
  │ 모의 사용자)│    │ 목표 상태)│    │ 최종 상태) │    │ 프롬프트·도구·│
  └──────────┘    └──────────┘    └──────────┘    │ 재시도 정책) │
                                                 └──────────┘
   같은 모델 + 다른 하네스 = 다른 점수.  같은 하네스 + 다른 버전 = 비교 불가.
```

### 4.2 설명

**표준으로 굳은 여섯 가지와 함수 호출 하나.**

| 벤치마크 | 재는 것 | 핵심 설계 | 출처 |
|---|---|---|---|
| **SWE-bench** | 저장소 수준 코드 수정 | 12개 파이썬 저장소의 실제 GitHub 이슈 2,294개. 모델이 코드베이스를 고치면 숨겨진 테스트로 채점. 2023년 발표 당시 최고 모델이 1.96%만 풀었다 | 📄 [16] |
| SWE-bench **Verified** | 같은 과업의 사람 검증 500개 부분집합 | OpenAI가 결함 있는 문제를 걸러 만든 판. 단, Berkeley RDI 글은 OpenAI가 감사 문제의 59.4%에 결함 있는 테스트가 있음을 발견한 뒤 Verified 보고를 중단했다고 전한다 | 🔍📄 [16][28] |
| **Terminal-Bench** | 터미널 안 다단계 작업 | 컨테이너 안에서 명령을 수행하고 과업별 검증. 공식 사이트는 확인일 기준 4.1을 표기하고 리더보드에 MODEL·AGENT·RESOLUTION RATE·COST·TOKENS 열을 둔다 | 🔍 [17] |
| **τ-bench / τ²-bench** | 도메인 정책 준수 + 사용자와 대화 + 도구 | 사용자도 LLM 시뮬레이터. 항공·소매·통신 도메인. 대화 끝의 DB 상태를 목표 상태와 비교해 채점. 신뢰성 지표 **pass^k** 도입. τ²는 사용자도 도구를 쓰는 "dual-control" 통신 도메인을 추가 | 📄 [18] |
| **GAIA** | 범용 보조 능력 | 추론·멀티모달·웹 탐색·도구 사용을 조합해야 하는 466문항. 사람에게는 쉽고(92%) 당시 GPT-4+플러그인에는 어려웠다(15%) | 📄 [19] |
| **BrowseComp** | 끈질긴 웹 탐색 | 찾기 어렵고 얽힌 정보를 찾아야 하는 1,266문항. 짧은 정답으로 검증 쉬움 | 📄 [20] |
| **OSWorld** | 실제 OS GUI 조작 | 데스크톱 앱 과업을 실행 결과로 검증 | 🔍 [21] |
| **BFCL** | 함수 호출 정확도 | 단일·병렬·다중 턴 호출의 형식·인자 일치. Berkeley 리더보드 V4 | 🔍 [22] |

**지표를 읽는 법.**
- **성공률(pass@1)**: 과업당 1회 시도해 맞힌 비율. 대부분의 리더보드 기본값.
- **pass@k vs pass^k**: pass@k는 k번 중 한 번이라도 성공, **pass^k는 k번 모두 성공**. τ-bench는 에이전트가 "일관되게" 행동하는지를 보기 위해 pass^k를 도입했고, 당시 최고 함수 호출 에이전트도 소매 도메인에서 pass^8이 25% 미만이었다 [18]. 고객 응대처럼 매번 같은 품질이 필요한 곳에서는 pass^k가 진짜 지표다.
- **비용·토큰·지연**: Terminal-Bench 리더보드는 COST·TOKENS 열을 기본으로 보여주고 [17], SWE-bench 사이트는 "Resolved vs cost" 산점도를 제공한다 [16]. Princeton HAL은 비용을 통제한 제3자 재측정을 표방한다 [27].

**점수 함정 다섯 가지.**
1. **버전 비호환** — Terminal-Bench처럼 버전이 빠르게 올라가는 벤치마크는 버전이 다르면 비교 불가 [17].
2. **하네스 차이** — 리더보드가 MODEL과 AGENT를 따로 적는 이유다 [17]. 모델 비교는 같은 하네스 안에서만.
3. **데이터 오염·결함 테스트** — Berkeley RDI 글은 한 모델이 SWE-bench 궤적의 24.4%에서 git log로 정답 커밋을 베꼈다가 점수가 교정된 사례와, Verified 문제의 59.4%에 결함 테스트가 있었다는 OpenAI 측 발표를 인용한다 [28].
4. **자체 보고 vs 제3자** — 벤더 발표는 "주장"이다. 벤치마크 운영자 검증 표시(SWE-bench의 체크 표시)나 HAL 같은 제3자 재측정과 구분한다 [16][27].
5. **벤치마크 해킹 가능성** — RDI는 자동 감사 에이전트로 13개 벤치마크(FrontierCS·BFCL·LiveBench·GAIA·WebArena·AGIEval·AgentBench·Terminal-Bench·tau-bench·MLE-bench·OSWorld·FieldWorkArena·CAR-bench)를 점검해 45건의 작동하는 점수 부풀리기와 16종의 공격 유형을 확인했고, 모든 벤치마크를 critical risk로 분류했다. 가장 흔한 원인은 피평가 코드와 채점기가 같은 프로세스·컨테이너·파일시스템을 공유하는 것이다 [28].

### 4.3 미리 답하자면

- 2025년의 평가 서베이는 벤치마크가 "더 현실적이고 어려우며 지속 갱신되는" 방향으로 가고 있다고 정리하면서, **비용 효율·안전성·견고성** 평가가 가장 비어 있다고 지적한다 [26].
- 처음 보는 사람이 리더보드에서 점수 하나를 적을 때는 **벤치마크·버전·모델·하네스·산출 방식·비용·출처 유형·조회 날짜** 여덟 칸을 함께 적는다. 이 습관이 2단계의 전부다(로드맵 §3.2).
- RDI의 결론을 한 문장으로: "믿을 수 있는 벤치마크는 성공을 재는 것에서 그치지 않고, 속이는 것이 제대로 푸는 것보다 어렵게 만들어야 한다" [28].

### 4.4 더 보려면
가이드 §16–23(벤치마크 각론) · §26(평가 서베이) · §27(HAL) · §28(RDI 감사)

## 5. 평가 방식 ② — 멀티 에이전트는 어떻게 재나

### 5.1 그림

```
  단일 에이전트 평가:   과업 → 점수
  멀티 에이전트 평가:   과업 → 점수  +  "단일 대비 증분"  +  비용 배수  +  오류 증폭률  +  협업 과정 점수
                                      ↑ 이 네 가지가 없으면 멀티 평가가 아니다
```

### 5.2 설명

**표준 벤치마크가 없다는 것이 현실이다.** 멀티 에이전트를 단일 벤치마크(SWE-bench 등)에 올려 점수를 내는 것은 가능하지만, 그 점수는 "멀티라서" 얻은 것인지 알려주지 않는다. 그래서 멀티 평가는 세 갈래로 발전했다.

1. **협업 자체를 재는 벤치마크 — MultiAgentBench(MARBLE)** [24]. 연구·코딩·게임(Minecraft·Werewolf)·협상·데이터베이스 같은 상호작용 시나리오에서 과업 완료뿐 아니라 협업·경쟁의 **질**을 함께 잰다 — 과업 점수(Task Score, 시나리오별 규칙 또는 LLM 채점), 마일스톤 기반 KPI(전체 마일스톤 중 각 에이전트가 기여한 비율의 평균), 그리고 LLM이 5점 척도로 매기는 통신 점수와 계획 점수의 평균인 조정 점수(Coordination Score)다. 토폴로지(star·chain·tree·graph)와 계획 전략(group discussion·cognitive planning)을 비교해, 연구 시나리오에서는 graph 구조가 가장 좋았고 cognitive planning이 마일스톤 달성률을 3% 올렸다고 보고한다 [24].
2. **프레임워크 설계 차이를 재는 벤치마크 — MAFBench** [25]. 2026년 2월 논문은 멀티 에이전트 프레임워크를 **오케스트레이션·메모리·계획 인터페이스·특화·통신 토폴로지** 다섯 차원으로 분해하는 분류 체계를 제시하고, 기존 벤치마크들을 표준 실행 파이프라인에 통합한 MAFBench로 LLM을 고정한 채 9개 프레임워크의 설계 선택만 바꿔 비교했다. 제목이 결론이다 — "모델 지능만이 아니라 아키텍처 설계가 성능을 지배한다." 오케스트레이션만으로 지연이 60배 넘게 늘 수 있고, 스키마 제약 계획 인터페이스는 형식 실패로 정확도를 최대 32포인트 떨어뜨리며, 통신 토폴로지가 구조에 안 맞으면 조정 성공률이 90% 이상에서 30% 미만으로 떨어진다 [25].
3. **통제 실험으로 "언제 이득인가"를 재는 연구 — Google·MIT 스케일링 연구** [14]. 도구·프롬프트·연산을 표준화한 뒤 5개 아키텍처 × 6개 벤치마크(Finance Agent·BrowseComp Plus·WorkBench·Plancraft·SWE-bench Verified·Terminal-Bench) × 3개 모델 가족(OpenAI·Google·Anthropic)을 돌렸다. 발견은 세 가지 — 단일 에이전트 성능이 이미 약 45%를 넘는 과업에서는 에이전트를 더해도 수익이 체감하거나 음수가 된다(capability-saturation), 도구가 많은 과업(예: 16개 도구의 업무 워크플로우)은 멀티 조정 오버헤드를 낸다, 중앙 검증이 없는 아키텍처는 오류를 더 전파한다 [14]. 오류 증폭률은 단일 1.0배 기준으로 Independent 17.2배, Decentralized 7.8배, Hybrid 5.1배, Centralized 4.4배였고, 토큰 1천 개당 성공 수는 단일 67.7에서 Centralized 21.5, Hybrid 13.6으로 떨어졌다(3~5배 비효율) [14]. 전체 평균으로 보면 멀티의 단일 대비 개선은 −0.3%로 사실상 0이고 표준편차가 37.5%에 달한다 — 평균이 아니라 과업 유형이 결과를 정한다는 뜻이다 [14].

**멀티 평가에서 추가로 봐야 하는 네 가지.**

| 항목 | 왜 | 어디서 봤나 |
|---|---|---|
| 단일 대비 증분(Δ) | 멀티의 존재 이유. 같은 모델·도구·토큰 예산의 단일 baseline이 없으면 의미 없음 | [14]의 설계 원칙 |
| 비용 배수 | 토큰·호출 수·벽시계 시간. 채팅 대비 약 15배라는 Anthropic 수치가 기준점 | [12] |
| 오류 증폭률 | 한 에이전트의 오류가 결과에 몇 배로 반영되나 | [14] |
| 협업 과정 점수 | 통신·계획·역할 수행의 질. 결과만 보면 "운 좋게 맞은" 협업을 못 가른다 | [24] |

### 5.3 미리 답하자면

- "멀티 에이전트가 더 좋다"는 일반 명제는 틀렸다. 맞는 명제는 "병렬화 가능하고 검증 가능한 과업에서, 중앙 검증자를 둔 구조로, 비용을 감수할 때 좋다"이다 [12][14].
- 프레임워크를 고를 때 "어느 모델을 쓰나"보다 "오케스트레이션 오버헤드·메모리 구조·계획 인터페이스·토폴로지"가 성능을 더 좌우할 수 있다 [25].
- 멀티 에이전트 벤치마크 결과를 볼 때는 반드시 "단일 에이전트 baseline이 같은 조건이었나"를 먼저 확인한다 [14].

### 5.4 더 보려면
가이드 §24(MARBLE) · §25(MAFBench) · §14(스케일링) · §12(Anthropic) · §26(서베이)

## 6. 에이전트 간 프로토콜 — MCP와 A2A

### 6.1 그림 — 세 층

```
                 ┌───────────────── A2A (수평: 에이전트 ↔ 에이전트) ─────────────────┐
                 │   [에이전트 A] ──Agent Card 발견 → Task 위임 → Message/Artifact──▶ [에이전트 B]   │
                 └──────┬───────────────────────────────────────────────────────┬──────┘
                        │ MCP (수직: 에이전트 ↔ 도구·데이터)                      │ MCP
                 ┌──────▼──────┐                                         ┌──────▼──────┐
                 │ MCP 서버들   │  tools / resources / prompts              │ MCP 서버들   │
                 │(DB, 검색, 파일)│                                         │(ERP, 캘린더) │
                 └─────────────┘                                         └─────────────┘
   + 프레임워크 내부 핸드오프(같은 프로세스 안에서 에이전트 간 주도권 넘김: OpenAI Agents SDK handoff, LangGraph 서브그래프 등)
```

### 6.2 설명

**MCP — 에이전트가 도구를 쓰는 표준.** Model Context Protocol은 JSON-RPC 2.0 메시지로 **호스트**(연결을 시작하는 LLM 애플리케이션), **클라이언트**(호스트 안의 커넥터), **서버**(컨텍스트와 능력을 제공하는 서비스)를 연결한다. 호스트는 서버마다 클라이언트 하나를 만든다 [29]. 서버가 제공하는 기본 요소는 셋이다 — **Tools**(모델이 실행할 함수), **Resources**(사용자나 모델이 쓸 데이터·컨텍스트), **Prompts**(사용자용 템플릿 메시지·워크플로우) [29]. 전송은 로컬 프로세스용 **stdio**와 원격용 **Streamable HTTP**(HTTP POST + 선택적 SSE) 두 가지다 [29]. 확인일 기준 최신 사양은 2026-07-28판이며, 이 판에서 MCP는 모든 요청이 버전·능력을 스스로 담는 **무상태(stateless)** 프로토콜로 바뀌었고, 서버가 클라이언트 쪽 LLM에 생성을 요청하는 Sampling은 **폐기(deprecated)** 되었다 [29]. 보안 원칙으로 "호스트는 어떤 도구를 호출하기 전에도 명시적 사용자 동의를 얻어야 한다"를 둔다 [29].

**A2A — 에이전트가 에이전트에게 일을 맡기는 표준.** Agent2Agent Protocol은 Linux Foundation 산하 오픈 표준(Apache 2.0)이며 확인일 기준 사양 1.0.0이다 [30]. 핵심 개념 다섯 가지 [30]:

| 개념 | 정의(공식 문서) |
|---|---|
| **Agent Card** | 에이전트의 정체·능력·엔드포인트·스킬·인증 요구를 적은 JSON 메타데이터. `/.well-known/agent-card.json`으로 발견 |
| **Task** | 고유 ID와 정해진 생애주기를 가진 상태 있는 작업 단위 |
| **Message** | 클라이언트와 에이전트 사이의 한 턴. 역할은 user 또는 agent |
| **Part** | Message·Artifact 안의 기본 콘텐츠 컨테이너. 텍스트, 파일(URL 또는 바이트), 구조화 데이터 중 하나 |
| **Artifact** | 과업 수행 중 에이전트가 만든 실체 있는 산출물 |

Task 상태는 SUBMITTED → WORKING → (COMPLETED / FAILED / CANCELED / REJECTED 종결) 이고, 중간에 INPUT_REQUIRED·AUTH_REQUIRED라는 "중단 상태"가 있어 사람이나 클라이언트의 추가 입력을 기다릴 수 있다 [30]. 전송 바인딩은 JSON-RPC 2.0 over HTTP(S), gRPC, HTTP+JSON/REST 세 가지이고 스트리밍은 SSE, 장기 과업은 푸시 알림(웹훅)으로 받는다 [30]. 원격 에이전트는 클라이언트에게 **불투명(opaque)** 하다 — 내부가 어떻게 돌아가는지 몰라도 Agent Card만 보고 위임할 수 있다는 것이 설계 원칙이다 [30].

**왜 둘은 경쟁이 아니라 보완인가.** A2A 공식 문서의 표현을 그대로 옮기면: "MCP는 수직이다. 단일 에이전트를 깊게 한다. … A2A는 수평이다. 그 경계를 넘어 에이전트들을 연결한다. … 함께 쓰면 MCP는 각 에이전트에 깊이를, A2A는 시스템에 도달 범위를 준다" [30]. 같은 페이지는 자동차 정비소 예시를 든다 — 고객 에이전트가 A2A로 정비소 에이전트에게 과업을 맡기고, 정비소 에이전트는 내부적으로 MCP 도구(`scan_vehicle_for_error_codes`, `get_repair_procedure`, `raise_platform`)를 부른다 [30]. 도구는 구조화된 입출력을 가진 대체로 무상태의 기본 요소이고, 에이전트는 추론·계획하며 장기 상태를 가진 자율 시스템이라는 것이 구분 기준이다 [30].

**프레임워크 내부 핸드오프**는 세 번째 층이다. 같은 프로세스 안에서 한 에이전트가 대화 주도권을 다른 에이전트에게 넘기는 1급 개념(OpenAI Agents SDK의 handoffs)이나 그래프의 노드 전이(LangGraph) 형태로 구현된다 [33][31]. 프로토콜이 아니라 라이브러리 기능이므로 프레임워크를 바꾸면 사라진다.

### 6.3 미리 답하자면

- "MCP는 도구용, A2A는 에이전트용." 둘 다 공식 문서가 서로를 보완재로 명시한다 [29][30].
- 프레임워크별 MCP·A2A 지원 여부는 2차 블로그마다 주장이 엇갈린다(2026-11 웹 검색 확인). **공식 문서의 MCP/A2A 페이지만** 근거로 쓴다.
- 사양은 살아 있다 — MCP는 2026-07-28판에서 무상태화와 Sampling 폐기라는 큰 변화를 겪었다 [29]. 반기마다 사양 버전을 다시 확인한다.

### 6.4 더 보려면
가이드 §29(MCP) · §30(A2A) · §31–36(프레임워크 공식 문서)

## 7. 실패 유형 — 왜 멀티 에이전트는 실패하나

### 7.1 그림 — MAST 분류 (Berkeley, 2025)

```
  FC1 시스템 설계 결함(사양 문제)          FC2 에이전트 간 불일치               FC3 과업 검증
  ├ 1.1 과업 사양 불이행      11.8%       ├ 2.1 대화 리셋            2.2%      ├ 3.1 조기 종료          6.2%
  ├ 1.2 역할 사양 불이행       1.5%       ├ 2.2 명확화 요청 실패      6.8%      ├ 3.2 검증 없음·불완전    8.2%
  ├ 1.3 단계 반복            15.7%       ├ 2.3 과업 이탈            7.4%      └ 3.3 잘못된 검증        9.1%
  ├ 1.4 대화 이력 상실         2.8%       ├ 2.4 정보 은폐(전달 누락)  0.85%
  └ 1.5 종료 조건 인지 실패   12.4%       ├ 2.5 다른 에이전트 입력 무시 1.9%
                                         └ 2.6 추론-행동 불일치     13.2%
  (비율 = 1,642개 궤적에서 각 유형이 차지하는 비중, 논문 4장 본문 수치 [13])
```

### 7.2 설명

**분류가 왜 중요한가.** "멀티 에이전트가 실패했다"는 말은 쓸모가 없다. 어디서, 어떤 유형으로 실패했는지 라벨을 붙여야 고칠 수 있다. UC Berkeley 연구진은 7개 공개 멀티 에이전트 프레임워크(MetaGPT·ChatDev·HyperAgent·AppWorld·AG2·Magentic-One·OpenManus)에서 1,642개의 실행 궤적을 모아(MAST-Data) 150개 이상을 전문가가 정밀 분석해 **14개 실패 유형, 3개 범주**의 분류 체계 MAST를 만들었다. 이 시스템들의 실패율은 벤치마크에 따라 41%에서 86.7%에 이르렀다. 주석자 간 일치도는 Cohen's kappa 0.88이었고, 대량 라벨링을 위해 사람 주석과 94% 일치(kappa 0.77)하는 LLM-as-a-Judge 파이프라인을 만들었다 [13].

**세 범주의 뜻.**
- **FC1 시스템 설계 결함(System Design Issues)** — 과업·역할 사양을 지키지 않음, 같은 단계 반복, 대화 이력 상실, 언제 끝내야 하는지 모름. 프롬프트·아키텍처 설계의 문제다 [13].
- **FC2 에이전트 간 불일치(Inter-Agent Misalignment)** — 대화를 처음부터 다시 시작, 모르면서 물어보지 않음, 과업에서 이탈, 알고 있는 정보를 상대에게 전달하지 않음, 상대 입력 무시, 말한 추론과 실제 행동이 다름. 통신 설계의 문제다 [13]. 논문의 대표 사례는 전화 에이전트가 API의 사용자명 형식 요구사항을 감독 에이전트에게 알리지 않고, 감독 에이전트도 되묻지 않아 로그인이 반복 실패하는 장면이다(2.4 정보 은폐) [13].
- **FC3 과업 검증(Task Verification)** — 끝나지 않았는데 끝냄, 검증을 안 하거나 불완전하게 함, 검증을 잘못함. "끝났다"는 보고를 믿을 수 없게 만드는 문제다 [13].

**단일 에이전트 공통 실패와 멀티 고유 실패.** 루프에 빠짐(1.3), 종료 조건 모름(1.5), 검증 없는 완료 보고(3.1·3.2)는 단일 에이전트에도 똑같이 생긴다. 반면 FC2 전부(2.1~2.6)는 에이전트가 둘 이상이어야 생기는 **멀티 고유** 실패다. 멀티로 가면 실패의 종류가 늘어난다는 뜻이다 [13].

**설계 개입으로 얼마나 줄어드나.** 논문은 두 사례 연구에서 설계 개입의 효과를 재었다. ChatDev에서는 역할별 프롬프트 정비(상위 에이전트만 대화를 끝낼 수 있게, 검증자 프롬프트에 경계 사례 추가)로 과업 성공률이 +9.4%p, 토폴로지를 비순환 그래프에서 CTO 에이전트가 검토 완료를 확인할 때만 끝나는 순환 그래프로 바꾸면 +15.6%p 올랐다. AG2 MathChat에서는 검증 절을 둔 구조화 프롬프트와 "검증자만 종료할 수 있는" 3역할 토폴로지가 정확도를 올렸다. 저자들은 토폴로지 변경이 프롬프트 변경보다 효과적이었지만 둘 다 "근본적 개선은 아니며" 구조적 재설계가 필요하다고 보고, "모델 능력을 넘어 시스템 설계가 우선한다(The Primacy of System Design)"는 절 제목으로 결론을 요약한다 [13].

**스케일링 연구가 덧붙인 것.** 아키텍처마다 고유한 실패 양상이 있고(Error Taxonomy Reveals Architecture-specific Failure Modes), 중앙 검증이 없는 구조가 오류를 더 전파한다 [14]. MAFBench는 "형식 실패(formatting failures)가 추론 오류로 오해받는" 유형을 추가로 지적한다 — 스키마 제약 계획 인터페이스에서 약한 모델의 스키마 위반이 84.7%에 이르렀다 [25].

### 7.3 미리 답하자면

- 실패를 보면 먼저 묻는다: "모델이 못 푼 것인가, 사양·역할·종료 조건·검증 설계가 빠진 것인가?" 다수는 후자다 [13].
- 멀티로 갈수록 FC2(통신) 실패가 새로 생긴다. 역할 간 **정보 전달 의무**와 **되묻기 규칙**을 프롬프트에 명시하는 것이 가장 싼 완화책이다 [13].
- 자기 실험(로드맵 4단계)에서 실패 10건에 MAST 라벨을 붙여 보면, 어느 범주가 많은지에 따라 프롬프트(FC1·FC3)·토폴로지(FC2)·검증자 추가(FC3) 중 무엇을 먼저 고칠지 정할 수 있다 [13].

### 7.4 더 보려면
가이드 §13(MAST) · §14(스케일링) · §25(MAFBench)

## 8. 프레임워크 지형

### 8.1 그림 — 2026년 11월 기준 주요 선택지

```
  범용 그래프형        역할·태스크 선언형     벤더 SDK(모델사 제공)                    통합·후속
  ┌──────────┐       ┌──────────┐       ┌───────────────┬──────────┬─────────────┐  ┌──────────────────┐
  │ LangGraph │       │  CrewAI  │       │ OpenAI Agents │ Google   │ Claude Agent │  │ Microsoft Agent  │
  │  [31]    │       │  [32]    │       │ SDK [33]      │ ADK [34] │ SDK [36]    │  │ Framework [35]   │
  └──────────┘       └──────────┘       └───────────────┴──────────┴─────────────┘  │ (AutoGen+SK 후속) │
                                                                                     └──────────────────┘
  (연구용·경량: smolagents, AG2 등은 보조 참고 [37])
```

### 8.2 설명

- **LangGraph** [31]는 에이전트 시스템을 **노드(처리 함수)와 엣지(제어 흐름)의 방향 그래프**로 모델링한다. 상태·재시도·사람 승인을 세밀하게 제어해야 하는 다단계 시스템에 쓰인다. 공식 문서가 docs.langchain.com으로 이전했다(구 주소는 안내 페이지).
- **CrewAI** [32]는 역할을 가진 에이전트들의 "크루(crew)"와 흐름(flows)을 선언해 협업시키는 **역할 기반** 프레임워크다. 공식 문서는 "collaborative AI agents, crews, and flows"를 표방한다.
- **OpenAI Agents SDK** [33]는 에이전트·도구 호출·**handoffs**·guardrails 같은 기본 요소를 제공하고 특정 오케스트레이션 패턴을 강제하지 않는다. 공식 문서 첫 페이지가 "Agents SDK or Responses API?"를 묻는다 — 즉 단순한 경우 SDK 없이 API만 써도 된다는 입장이다.
- **Google ADK** [34]는 Google의 에이전트 개발 키트로, 문서 주소가 adk.dev로 이전했다(이 환경에서 본문 미열람).
- **Microsoft Agent Framework** [35]는 .NET·Python·Go에서 에이전트와 멀티 에이전트 워크플로우를 만드는 틀로, 공식 개요가 "When to use agents vs workflows" 절을 둔다. AutoGen과 Semantic Kernel의 후속이다. 2023년 AutoGen 논문 [9]은 역사적 원류로 읽고, 신규 학습은 이 프레임워크 문서로 한다.
- **Claude Agent SDK** [36]는 "Claude Code를 라이브러리로" 써서 프로덕션 에이전트를 만드는 SDK다. 공식 개요가 다른 Claude 도구와의 비교표를 둔다.

**비교 축 여섯 가지(로드맵 §4.2와 동일).** 상태·제어 흐름 표현 / 핸드오프·위임 / 사람 개입 / 관측 가능성 / 내구성(장기 실행·체크포인트) / 프로토콜 지원(MCP·A2A). 이 여섯 칸을 **공식 문서 URL과 함께** 채우는 것이 3단계의 산출물이다.

**MAFBench의 경고를 기억한다.** 프레임워크 선택은 모델 선택만큼 성능에 영향을 준다 — 같은 모델·같은 과업에서 오케스트레이션 구현 차이만으로 지연이 60배 넘게 벌어졌다 [25]. 다만 그 논문의 측정은 "2+2는?" 같은 trivial 과업에서의 오버헤드 분리 실험이므로, 실제 과업에서의 비율은 직접 재야 한다 [25].

### 8.3 미리 답하자면

- 프레임워크는 "프롬프트와 응답을 추상화 뒤에 숨긴다"는 것이 Anthropic의 경고다. 처음에는 LLM API를 직접 써 보고, 필요가 입증될 때 프레임워크를 들이라고 권한다 [2].
- 2026년 기준 신규 학습 대상은 LangGraph·CrewAI·OpenAI Agents SDK·Google ADK·Microsoft Agent Framework·Claude Agent SDK 여섯 가지로 충분하다. AutoGen은 통합되어 유지보수 단계이므로 원류 논문만 읽는다 [9][35].
- 프레임워크를 고르는 기준은 "유명한가"가 아니라 "내 과업의 상태·제어 흐름을 자연스럽게 표현하는가, 사람 개입과 관측이 내장인가, 프로토콜을 공식 지원하는가"다.

### 8.4 더 보려면
가이드 §31–36(프레임워크 각론) · §25(MAFBench)

## 9. 용어 풀이

| 용어 | 뜻 | 출처 |
|---|---|---|
| **에이전트(agent)** | LLM이 목표를 받아 도구를 부르고 관찰하며 여러 단계를 스스로 진행해 과업을 끝내는 시스템. 흐름을 모델이 정함 | [2] |
| **워크플로우(workflow)** | 미리 정한 코드 경로로 LLM과 도구를 엮은 것. 흐름을 코드가 정함 | [2] |
| **augmented LLM** | 검색·도구·메모리가 붙은 LLM. 모든 패턴의 기본 블록 | [2] |
| **ReAct** | Reasoning + Acting. 추론 흔적과 행동을 번갈아 생성하는 루프의 원형 | [3] |
| **tool / function calling** | 모델이 "이 함수를 이 인자로 불러 달라"는 구조화 출력을 내고 바깥 코드가 실행하는 방식 | [1][22] |
| **ACI (agent-computer interface)** | 에이전트가 쓰는 도구의 정의·설명·형식. 프롬프트만큼 중요한 설계 대상 | [2] |
| **orchestrator / lead agent** | 과업을 쪼개 작업자(worker·subagent)에게 위임하고 종합하는 중앙 에이전트 | [2][12] |
| **handoff** | 한 에이전트가 대화 주도권을 다른 에이전트에게 통째로 넘기는 것. 프레임워크 내부 개념 | [33] |
| **토폴로지(topology)** | 에이전트 간 연결 모양: 중앙집중(hub-and-spoke)·분산(peer mesh)·독립·혼합, 또는 star·chain·tree·graph | [14][24] |
| **pass@k / pass^k** | k회 중 1회 이상 성공 / k회 **모두** 성공. 후자가 일관성(신뢰성) 지표 | [18] |
| **하네스(harness) / scaffold** | 모델을 벤치마크에서 돌리는 에이전트 코드(프롬프트·도구·재시도 정책). 리더보드의 AGENT 열 | [17] |
| **오염(contamination)** | 벤치마크 정답이 학습 데이터나 환경(커밋 이력·설정 파일)에 노출되어 점수가 부풀려지는 것 | [28] |
| **벤치마크 해킹(reward hacking)** | 과업을 풀지 않고 채점기의 허점(공유 프로세스·약한 테스트·정답 파일)을 이용해 점수를 얻는 것 | [28] |
| **오류 증폭(error amplification)** | 한 에이전트의 오류가 시스템 결과에 몇 배로 반영되는가. 독립 구조에서 크고 중앙 검증 구조에서 작음 | [14] |
| **capability-saturation** | 단일 에이전트가 이미 잘하는 과업에서는 멀티 조정의 수익이 체감하는 현상 | [14] |
| **MAST** | Multi-Agent System Failure Taxonomy. 3범주 14유형의 실패 분류 | [13] |
| **LLM-as-a-Judge** | LLM으로 결과·궤적을 채점하는 방법. 사람 주석과의 일치도를 먼저 검증해야 함 | [13][12] |
| **MCP** | Model Context Protocol. 에이전트(호스트/클라이언트) ↔ 도구·데이터(서버). JSON-RPC 2.0, 서버 요소 tools·resources·prompts | [29] |
| **A2A** | Agent2Agent Protocol. 에이전트 ↔ 에이전트. Agent Card로 발견, Task 단위로 위임, Linux Foundation 산하 | [30] |
| **Agent Card** | A2A에서 에이전트의 정체·능력·엔드포인트·스킬·인증을 적은 JSON. `/.well-known/agent-card.json` | [30] |
| **Streamable HTTP / stdio / SSE** | MCP의 두 전송(원격 HTTP, 로컬 프로세스) / 스트리밍에 쓰는 Server-Sent Events | [29][30] |
| **dual-control** | τ²-bench에서 에이전트뿐 아니라 사용자(시뮬레이터)도 도구로 세계 상태를 바꾸는 설정 | [18] |
| **SOP (Standardized Operating Procedure)** | MetaGPT가 프롬프트 순서로 인코딩한 사람 조직의 표준 절차 | [7] |
