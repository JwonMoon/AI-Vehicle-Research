Autoware 재단 스택 지도 — Autoware 2.0 시대의 저장소 157개, 무엇이 무엇이고 로드맵 어디에 있나

작성일: 2026-10-30 · 상태: 초판 배경: Autoware 재단(AWF) GitHub 조직에 vision_pilot, auto_steer, auto_e2e, autoware_latent_drive, autoware-safety-island, autoware-index 같은 낯선 저장소가 급증했고, 2026-10-29에는 Autoware 2.0.0이 공개됐다. 이 보고서는 ① 조직의 저장소 157개를 전수 조사해 10개 묶음으로 분류하고, ② 각 스택이 무엇인지 설명하며, ③ AWF가 공개한 로드맵(다년 로드맵·Architecture 2.0 4단계·POV 4단계·Open AD Kit 사다리) 위에 각 스택을 올려 "지금 어디에 있는지"를 정리한다. "E2E 전환 로드맵이 자율주행 트랙과 ADAS 트랙으로 나뉘고 Vision Pilot은 ADAS 쪽"이라는 질문자의 가설도 공식 자료로 검증한다(§3). 대상 독자: Autoware 1.x 구조(Sensing→Perception→Localization→Planning→Control, Core/Universe)를 아는 엔지니어. 출처 표기 원칙: 모든 사실 문장에 출처 ID를 붙인다. 등급은 💻 저장소 원본(raw 파일·shallow clone으로 직접 확인) · 🔍 1차 페이지(GitHub 릴리스·이슈·토론을 직접 열람) · 📚 이 저장소의 앞선 보고서가 직접 확인한 기록 · 📰 웹 검색 요약 · ⚠️ 추정·미확인. 전체 목록은 출처 기록. 조사 환경 제약: 세션 네트워크 정책으로 autoware.org, docs.autoware.org(=autowarefoundation.github.io), medium.com을 열 수 없었다. 공식 문서는 렌더링 사이트 대신 문서 저장소(autoware-documentation)의 Markdown 원본을 clone해 읽었고(내용은 동일), 재단 홈페이지·블로그 정보는 GitHub와 검색 결과로 대체했다. 0. 세 줄 요약

  1. AWF의 스택은 "로보택시·L4 트랙"과 "ADAS·개인차량(POV) 트랙" 두 줄기로 읽으면 대부분 정리된다. 전자는 autoware(Core/Universe/Launch)와 그 위의 학습 플래너·E2E 모델(Diffusion Planner, auto_e2e, autoware_latent_drive, autoware_oneplanner)이고, 후자는 vision_pilot과 그 부품 모델(auto_steer·auto_speed·auto_drive, AutoSeg 계열, lite_models)이다. 두 트랙은 같은 E2E 진화 철학(학습 플래너→컴포넌트형 E2E→단일 신경망→하이브리드)을 공유하지만, 주체(Software/Robotaxi WG vs ADAS WG)·센서·하드웨어·릴리스 주기가 다른 별개의 코드베이스다. 질문자의 가설은 큰 틀에서 맞고, 세부는 §3.4에 채점했다. (💻 D3·D10·R6·R10 · 🔍 G8·G13)
  2. Autoware 2.0.0(2026-10-29 공개)은 "E2E 완성판"이 아니라 "Generator-Selector 구조를 공식화하고 생성기 하나를 바꿔 끼울 수 있게 한 첫 릴리스"다. 런치 인자 planning_setting으로 규칙 기반 플래너와 Diffusion Planner 중 하나를 고르며, Selector(안전 게이트·랭킹)는 패키지는 있으나 아직 기동하지 않는다. 같이 공개된 것은 모델의 Hugging Face 이관, 커뮤니티 패키지 레지스트리 Autoware Index, 그리고 Vision Pilot을 첫 사례로 하는 Reference Design 개념이다. 버전 체계도 바뀌어 Autoware 2.0.0이 autoware_core 1.10.0을 쓴다. (💻 D1·D9·R1 · 🔍 G2)
  3. 배포·안전 층이 별도 스택으로 자라고 있다. openadkit은 Autoware·Vision Pilot·Safety Island를 "digest로 고정하고 증거(evidence)를 서명해 내보내는" 배포 계층으로 재편 중이며(v2.0 2026-10 말 목표, v2.1에서 Vision Pilot + Euro NCAP 파생 시나리오, Renesas R-Car X5H), autoware-safety-island는 Arm 안전 코어에서 궤적 추종기를 돌리는 구현체다. 로드맵 상 가장 가까운 양산 지향 결합은 "Vision Pilot + Safety Island + Open AD Kit"이고, 로보택시 트랙은 다년 로드맵에서 TRL-6 목표가 3년 차에 놓여 있다. (🔍 G4·G17 · 💻 D10·R13)

2.3 Autoware 1.x와 무엇이 다른가 — 구조 그림으로

1.0은 "Sensing→Map/Localization→Perception→Planning→Control→Vehicle Interface"의 7개 스택을 고정 파이프라인으로 잇는 계층 구조였다(그림 2). 2.0은 파이프라인의 앞부분을 추상화해 "궤적을 내는 무엇이든 Generator, 그것을 검사·선택하는 것이 Selector" 로 바꿨다(그림 3). 공식 문서의 표현은 "우리는 파이프라인의 앞 절반을 추상화했다(abstracted away the front half of the pipeline)"이다. Generator는 규칙 기반·최적화 플래너, 원시 센서를 쓰는 E2E 모델, 학습·샘플링 플래너 어느 것이든 될 수 있고, 여러 개가 병렬로 돌 수 있다. Selector는 안전 검사(규칙 준수·주행가능영역)와 랭킹·선택을 맡는다. (💻 D1·D4)

3. "두 트랙" 가설 검증 — 공식 자료가 말하는 구조

3.1 다년 로드맵: E2E 3년 계단과 ODD별 TRL 계단

AWF 공식 문서의 "Multi-Year Roadmap"은 8개 목표를 3년(Y1~Y3)으로 나눈다. 기술 목표 두 개가 이 보고서의 축이다. (💻 D10. 문서에 기준 연도는 적혀 있지 않다 ⚠️)

목표 Y1 Y2 Y3
Objective 1: AI-first 기술 도입 LiDAR·비전·레이더 컴포넌트형 AI 인식 스택 도입. AI 기반 플래너 초판으로 "완전한 E2E 컴포넌트 기반 스택" 달성(자체 개발 + 회원사 기술 통합) 단일 신경망 E2E 스택 초판(센서→궤적 직접 계산) 완전한 하이브리드 AI 스택: E2E가 주 모드, 컴포넌트형 AI 스택이 병렬 안전층·기반 기술층
Objective 2: 양산 가능(Production-Capable) Autoware Open AD Kit와 결합한 저속 자율주행(LSA)·개인차량(POV, 고속도로 파일럿) 초판, TRL-6 LSA·POV TRL-7. Robobus·오프로드 초판 TRL-6 LSA·POV TRL-8, Robobus·오프로드 TRL-7, Robotaxi 초판 TRL-6
Objective 3: 실차 배치 LSA·POV 앵커 기업 1곳(후보: Eve Autonomy·Whale Dynamic·Robeff / AMD·DeepenAI·AutoCore.ai) 단일 차량 소규모 다차량 + Robobus(ADASTEC)·오프로드(DriveBlocks) 단일 차량 플릿 + Robotaxi 단일 차량(후보: TIER IV)

Objective 4(커뮤니티)의 Y2 항목 "ROS Index 스타일의 Autoware 패키지 목록"과 "GUI 설정 대시보드"는 각각 Autoware Index와 System Designer/launch GUI로 실체화됐다. (💻 D10·R15·R17)

분석. 이 표가 "두 트랙" 가설의 공식 근거다. 기술 축(Objective 1)은 하나의 E2E 계단이고, 제품 축(Objective 2·3)은 ODD별로 계단이 다르다. POV(개인차량)가 LSA와 함께 가장 먼저 TRL-6을 노리고, Robotaxi는 가장 늦다. 즉 "E2E 로드맵이 두 트랙으로 갈린다"기보다 "하나의 E2E 기술 계단을 ODD별 제품 트랙이 각자의 속도로 오른다" 가 정확한 표현이다.

3.2 Architecture 2.0 로드맵의 E2E 4단계

Architecture 2.0 문서의 로드맵 절(roadmap/autonomous-driving-stack-architecture.md)은 Autoware 1.0(전통 로보틱스 스택)에서 Autoware 2.0(데이터 중심 AI 스택)으로의 진화를 4단계로 정의한다. 목표는 "SAE Level 4+"다. (💻 D2·D3)

단계 정의(공식 문서) 맵 옵션 2026-10 현재 대응 스택(자체 해석)
Step 1 Learned Planner HD맵 기준 자차 위치 + 3D 박스·신호등 등 "로컬 월드 표현"을 받아 궤적을 내는 학습 플래너. 병합·끼어들기·양보를 데이터로 배움 HD맵 Diffusion Planner(2.0.0에서 planning_setting:=diffusion_planner), OnePlanner(LiDAR BEV + 벡터맵)
Step 2 Component-based E2E 학습 인식 + 학습 플래너. 둘 사이 인터페이스가 남아 "내성 가능한(introspectable)" E2E A: HD맵 / B: 2D맵 AutoE2E Reactive 모델(카메라→BEV→GRU 플래너, 맵 래스터 옵션), Vision Pilot의 인식축(AutoSeg→AutoSteer)
Step 3 Learned Driving 명시적 인식·계획 모듈 없는 단일 모놀리식 신경망. CNN형(엣지 배포 가능) 또는 VLA형(ViT+LLM+디퓨전 디코더) A/B LatentDrive(V-JEPA 잠재 공간에서 계획), AutoDrive(프레임 2장→거리·곡률), Alpamayo(외부, VLA)
Step 4 Learned Hybrid E2E 주행 모델 + 별도 Safety Perception(LiDAR·레이더·규칙 기반 가능) + Safety Guardian(교차 검증, V2X 활용 가능). "업계가 개발 중" A/B Vision Pilot 1.x의 "하이브리드 E2E"(인식 모델 ∥ E2E 모델 → Safety Guardian), Safety Island

문서가 각 단계마다 "옵션 A(HD맵)"와 "옵션 B(2D 내비 맵)"를 두는 점이 중요하다. 옵션 B의 장점은 "HD맵 구축·유지 없이 2D맵이 있는 곳 어디서나 동작"이고, 옵션 A의 장점은 "HD맵이 비가시선 센서처럼 정적 환경을 알려주는 강건성"이다. (💻 D3) 분석: 옵션 B가 사실상 ADAS·POV 트랙의 전제이고(Vision Pilot은 mapless), 옵션 A가 로보택시 트랙의 전제다. 같은 4단계 그림을 두 트랙이 다른 옵션으로 오르고 있다.

로드맵 폴더의 development-roadmap.md는 본문이 "TBD"뿐이다. 2.0 문서 PR은 "TBD인 로드맵 페이지 4개를 숨긴다"고 적었다. 즉 날짜 박힌 공식 개발 일정표는 아직 없다. (💻 D5·D17)

5. 핵심 스택 상세

5.1 Autoware 2.0 본체 — Core · Universe · Launch

무엇인가. autoware는 소스가 없는 메타 저장소이고, repositories/autoware.repos가 하위 저장소의 태그를 고정한다. 2.0.0의 고정판은 core 그룹 11개(agnocast 2.4.1, autoware_msgs 1.13.0, adapi_msgs 1.9.2, internal_msgs 1.16.0, cmake 1.4.0, utils 1.11.0, lanelet2_extension 1.3.0, autoware_core 1.10.0, rviz_plugins 0.6.0, simple_planning_simulator 1.1.0, system_designer v0.4.2), universe 그룹(autoware_universe 0.53.1 + tier4_autoware_msgs 1.0.0-alpha, bevdet_vendor 0.2.1, cuda_blackboard 0.4.0, managed_transform_buffer 0.3.0, MapIV eagleye 등 외부 커밋), launcher(autoware_launch 0.53.0), sensor_component(tier4 nebula v1.2.0, transport_drivers, ros2_socketcan)다. 도구는 tools.repos(autoware_tools 0.8.0), 시뮬레이터는 simulator.repos(tier4 scenario_simulator_v2 22.0.0)로 따로 받는다. (💻 R1·D8)

Core와 Universe의 역할 분담은 변하지 않았다. Core는 "AWF가 유지하는 엄격한 기준(단위·통합·성능·실차 테스트)의 안정 기반", Universe는 "원저자가 품질 기준을 정하는 커뮤니티 샌드박스"이고, 성숙한 Universe 패키지가 Core로 승격된다. (💻 D6) 다만 2026년에는 Universe를 줄이는 방향이 명시됐다: 2026-05 제안은 "autoware_universe = 레거시, 축소 중"이라 적었고(🔍 G19), 2026-06 재구조화 안내는 Universe 241개 패키지 중 CUDA/TensorRT 관련 약 27개를 autoware_cuda로 모으고 나머지 CUDA 패키지는 Index의 개별 패키지로 보내는 "Universe 슬림화의 기초"라고 설명한다(🔍 G14). 이 재구조화는 TIER IV 측 반대("강한 이유를 모르겠다")와 포크 동기화 사정으로 2026-09 말까지 연기됐다가 10-05 재개됐고, 10-15 전환 목표의 완료 여부는 확인하지 못했다. (🔍 G14 ⚠️)

5.2 Autoware Index와 Reference Design — Universe를 쪼개는 새 유통 구조

Autoware Index는 "Autoware를 확장하는 커뮤니티 ROS 2 패키지의 레지스트리"다. 어떤 패키지가 있고, 소스가 어디 있고, 최신 Autoware 릴리스에 대해 빌드·테스트를 통과하는지를 기록한다. 등록은 distributions/<distro>.yaml에 저장소 하나·ref 하나·패키지 목록을 적는 PR로 하고, 머지되면 CI가 최신 릴리스에 대해 빌드·테스트해 결과를 data 브랜치에 append-only로 쌓는다. branch ref는 매일 재검증, tag/sha는 고정이다. 소비자는 브라우즈 사이트의 Repos builder나 aw-index-cli compose --rosdistro jazzy --packages …로 repositories/autoware-index.repos를 생성해 vcs import한다. (💻 R15·R16·D12)

3층 구조 제안(2026-05, 열린 상태)은 Core(AWF 큐레이션·하드 핀) / Universe(연합 커뮤니티 패키지, "레거시·축소") / Index(레지스트리·CI·사이트·CLI)다. 2.0.0 시점에 Index로 간 패키지는 autoware_livox_tag_filter(Universe에서 제거), autoware_image_diagnostics(2026-10 이동), autoware_pose2twist·autoware_bluetooth_monitor·autoware_component_monitor(등록됐으나 0.53.1에는 아직 포함; 2.0.0 워크스페이스에 중복 추가 금지)이고, RViz 플러그인을 autoware_extra_rviz_plugins로 떼는 제안이 열려 있다. (🔍 G2·G15·G19)

Reference Design은 "배포 프로파일(차량·운행 조건·용도) + 레퍼런스 SW 스택(모듈·모델 버전·파라미터)"의 조합으로, Index 항목에 reference_design: true 마커(리뷰어 승인)를 달아 표시한다. 첫 사례가 Vision Pilot이고, aw-index-cli compose --reference-design이 vision_pilot을 돌려준다. 문서는 POV·LSA(RoboRacer·GoKart 포함)·오프로드(예정)·ITRI 버스 가이드를 나열한다. (💻 D11·R15·D17)

분석. Index는 다년 로드맵 Objective 4-Y2의 "ROS Index 스타일 패키지 목록"의 구현이자, Universe 모노리스를 "한 리뷰 큐에 묶이지 않는" 연합 구조로 바꾸는 장치다. Vision Pilot이 Reference Design의 첫 사례로 등록된 것은 ADAS 트랙이 Autoware 본체와 코드를 공유하지 않으면서도 Autoware 유통 체계 안에 들어오는 접점이다.

5.6 AutoSeg 계열·Lite 모델·보조 모델 — ADAS 트랙의 부품 창고

AutoSeg는 "단일 백본 + 컨텍스트 블록 + 특징 넥 + 다중 분할·검출 헤드"의 실시간 시각 인식 파운데이션 모델이고, Depth 분기(Scene3D), Scene 분기(SceneSeg·DomainSeg·EgoSpace), Path 분기(EgoPath·EgoLanes)로 나뉜다. (💻 P5) 2026-06에 각 모델이 별도 저장소로 떼어졌지만, scene_seg·scene_3d·lite_models·ego_lanes는 README 한 줄뿐인 빈 저장소이고 코드는 아직 vision_pilot(옛 모노레포 경로 autoseg가 같은 페이지로 연결)에 있다. domain_seg만 실체가 있다(ROADWork 데이터셋 mIoU 46.6, RTX 3060 Mobile FP16 23.9 FPS). (💻 R27·R30 · 🔍 G1) Lite 모델은 12번 보고서가 기록한 "SceneSeg/Scene3D/EgoLanes 20–28× 가속(10→87–104 FPS)" 계열이고, 2026-02 회의록은 AEI(Alternative Embedded Innovation)가 "정확도 유지하며 3× 속도"의 경량판을 만들었다고 적었다. (📚 12번 · 🔍 G6) blindspot_detector(측면 어안 사각지대)와 auto_speed_limit(속도제한 표지)은 Phase 2 기능 후보다. (💻 R30 ⚠️ 용도는 추정)

5.7 Open AD Kit와 Safety Island — 배포·안전 층

Open AD Kit(openadkit) 는 "Autoware를 컨테이너화된 클라우드/엣지 SDV 컴포넌트로 배포하는 첫 SOAFEE 블루프린트"다. 컴포넌트 이미지(GHCR), 배포 구성(planning/logging/scenario/carla-simulation, zenoh-bridge), 버전 고정 런타임 번들, CI 메타데이터를 제공하고 openadkit setup --verify && openadkit run planning-simulation 한 줄로 기동한다. (💻 R5)

8. 차량 HPC 관점의 시사점

  1. 두 가지 연산 프로파일이 공존한다. 로보택시 트랙은 TensorRT·GPU 전제이고(Diffusion Planner, OnePlanner RTX PRO 6000 기준 12.7 ms), ADAS 트랙은 3–5 INT8 TOPS 양산 SoC에서 10 FPS를 목표로 한다. 같은 재단의 두 스택이 요구 연산량에서 두 자릿수 차이를 내므로, HPC 설계에서는 "어느 트랙을 올리는가"가 SoC 등급을 결정한다. (💻 R6·R12 · 🔍 G20)
  2. 안전 코어 분리가 구체적 하드웨어 이름으로 내려왔다. Safety Island의 타깃이 NXP S32Z/S32Z2와 Renesas R-Car X5H CR52이고, Reference Design WG가 최소비용(S32Z2/AURIX TC4x/Stellar)과 최대안전(X5H) 분기를 논의한다. 15번 보고서의 ETAS×Elektrobit(ASIL-B 리눅스+미들웨어)과 달리 AWF는 Zephyr/FreeRTOS 안전 코어 + DDS 경계라는 다른 층에서 접근한다. (💻 R13 · 🔍 G16 · 📚 15번)
  3. 배포 단위가 "증거 붙은 OCI 이미지"로 바뀐다. Open AD Kit의 L0~L3 증거 등급, SBOM, in-toto 증명, AutoSD·eSync 배달은 HPC 소프트웨어 플랫폼이 받아들여야 할 입력 포맷이 된다. 쿠버네티스 비채택·Quadlet+BlueChi 채택도 차량 측 컨테이너 런타임 선택에 참고가 된다. (🔍 G4)
  4. 제로카피·GPU 공유가 표준 구성원이 됐다. Agnocast(소스 빌드 포함)와 cuda_blackboard(core/cuda 이동)는 09번 보고서가 예측한 "zero-copy 경로 분화"의 공식화다. HPC 미들웨어 평가 시 이 둘이 기준선이다. (💻 R1 · 📚 09번)
  5. 모델 유통이 Hugging Face로 표준화됐다. artifacts Ansible 역할이 버전 태그로 모델을 받으므로, 차량 측 모델 관리(버전 고정·무결성)도 같은 체계를 전제로 설계할 수 있다. (🔍 G2)
