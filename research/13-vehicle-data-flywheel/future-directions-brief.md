# 데이터 플라이휠의 향후 진화 방향 — 기술 방향과 차량 HPC 요구 사항 정리본

> **작성일**: 2026-10-08 · **성격**: 본 보고서([개조식 판](vehicle-data-flywheel-report.md) 5.6절)의 "향후 진화 방향"만 따로 떼어 읽기 쉽게 다시 쓴 정리본. 사실·수치·근거 등급([원문]·[보도]·[미확인])은 본 보고서와 같고, 원 출처는 [reference/references.md](reference/references.md)에 있음.
> **읽는 순서**: 1장 요약 → 2장 기술 방향 여섯 가지 → 3장 차량 HPC 요구 사항 여덟 가지 → 4장 둘의 대응 관계.

---

## 1. 요약

- 플라이휠의 다음 단계는 "단계를 바꾸는 것"이 아니라 "각 단계의 부품을 큰 모델과 클라우드 시뮬레이션으로 바꾸는 것"임. 9단계 구조(온보드 선별 → 업로드 → 검색 → 라벨링 → 학습 → 시뮬 검증 → 실차 검증 → 안전 관문·OTA → 반복)는 그대로 유지됨.
- 기술 방향은 여섯 가지이며 성숙도가 다름. 로깅의 규제 증거화는 이미 의무이고, 월드모델 검증은 양산에 들어갔으며, 학습된 시뮬레이터 안 학습은 첫 양산 사례가 나왔고, 플릿 간 데이터 공유와 에이전트 운영은 아직 주장 단계임.
- 여섯 방향 가운데 절반 이상이 차 안에 조건을 남김. 9단계 중 다섯 단계(①②⑦⑧⑨)가 차 안에서 돌기 때문임. 차량 HPC 플랫폼이 지금 갖춰야 할 요구 사항은 다섯 가지, 앞으로 더해질 것은 세 가지임.
- 우선순위는 로깅 통합 → 월드모델 검증 → 학습된 시뮬레이터 순임. 이미 의무인 것, 양산에 들어간 것, 다음에 올 것의 순서임.

## 2. 기술 방향 여섯 가지

### 2.1 한눈에 보기

| # | 방향 | 무엇이 바뀌나 | 성숙도(2026-09) | 관문 |
|---|---|---|---|---|
| 1 | 월드모델 기반 검증 | 로그 재생·수작업 시나리오 → 월드모델이 만든 장면으로 시험 | 양산 진입 | 규제가 생성 장면을 증거로 받는가 |
| 2 | 학습된 시뮬레이터 안 학습 | 기록을 흉내 내는 모방학습 → 시뮬레이터 안에서 직접 운전하며 배우는 강화학습 | 초기 양산(1개 사) | 시뮬–실제 격차의 런타임 감시 |
| 3 | 플릿 간 데이터 공유 | 한 회사의 플릿 → 여러 회사·국경 안 데이터 공간 | 실험 | 데이터 주권 규제, 센서·형식 표준화 |
| 4 | 에이전트가 플라이휠을 운영 | 사람이 라벨링·정제·학습·평가를 지시 → AI 에이전트가 수행 | 주장 | 검증된 사례 없음 |
| 5 | 파운데이션 모델이 라벨링을 줄임 | 사람 라벨링 → VLM이 라벨 초깃값·설명을 생성하고 사람은 검수 | 도구 공개 | 검수 인력은 남음 |
| 6 | 로깅이 규제 증거가 됨 | 개발용 트리거와 규제용 기록이 따로 → 한 파이프라인 | 이미 의무 | 변조 방지·시간 동기화 |

### 2.2 방향별 설명

- **방향 1 — 월드모델 기반 검증이 표준이 됨**
  - 내용: 지금까지의 검증은 기록된 로그를 다시 틀거나(재생) 사람이 시나리오 파일을 쓰는 방식이었음. 월드모델은 "이 장면에서 보행자가 뛰어들었다면"처럼 기록에 없는 반사실 장면을 만들어 새 모델을 시험함.
  - 사례: Wayve GAIA-4(주행 모델을 루프 안에 넣고 월드모델이 반응), NVIDIA Cosmos Transfer·NuRec, Waymo World Model(카메라·라이다 동시 생성), XPeng X-World [보도].
  - 왜 중요한가: 1.2절의 "주행 거리로는 안전을 증명할 수 없다"는 한계를 넘는 유일한 수단이 시뮬레이션이고, 월드모델은 그 시뮬레이션의 범위를 플릿이 못 본 상황까지 넓힘.
  - 관문: 규제가 생성 장면을 증거로 받아 주는가임. UN R157 부속서 4는 시뮬레이션 증거를 허용하되 제조사가 도구의 재현 범위·시나리오 유효성·물리 시험과의 상관을 입증하도록 요구함 [보도]. 월드모델 하나마다 이 "도구 검증" 문서가 필요함.
  - 차 안에 남기는 조건: 시뮬 결과를 실차와 대조하려면 기록한 센서 데이터를 실제 제어기에 다시 주입하는 HIL 재생이 필요함(3장 요구 4).
- **방향 2 — 학습된 시뮬레이터 안에서 직접 학습한 모델이 양산차에 실림**
  - 내용: 모방학습은 기록된 운전을 흉내 내므로 모델이 자기 판단의 결과를 경험하지 못함. 학습된 시뮬레이터(월드모델) 안에서 모델이 직접 운전하고 충돌·이탈 결과로 학습하면 이 한계가 사라짐.
  - 사례: comma.ai openpilot 0.11(2026-03)이 "학습된 시뮬레이터로 전량 학습한 모델"을 실제 사용자에게 배포한 첫 공개 사례 [원문]. NVIDIA AlpaGym, Momenta R7, Waymo의 교사-학생 구조가 같은 방향 [보도].
  - 관문: 시뮬레이터 안에서 배운 모델이 실제 도로에서 다르게 행동할 수 있음(시뮬–실제 격차). 배포 뒤에도 이 격차를 감시해야 함.
  - 차 안에 남기는 조건: 차량에 실리는 것은 증류된 학생 모델이며, 그 모델의 실행과 격차 감시 모니터가 온보드 요구가 됨(3장 요구 7).
- **방향 3 — 플릿 간 데이터 공유가 실험 단계를 지남**
  - 내용: 한 회사가 모은 데이터만으로는 롱테일을 다 덮지 못하므로, 여러 회사의 플릿을 합치거나 국경 안에서 데이터 공간을 만들자는 시도임.
  - 사례: TIER IV Co-MLOps(택시 회사·Astemo와 공동 MLOps), Catena-X 중국–유럽 데이터 공간(2026-11 예정), NVIDIA 1,700시간 오픈 데이터, Waymo WOD-E2E 공개 [보도].
  - 관문: 데이터 주권 규제가 국경 밖 공유를 막는 대신 "국경 안 공유"를 밀어 올리는 역설이 있음. 센서 배치·캘리브레이션·시간 기준이 다른 데이터를 합치려면 형식 표준화가 선행돼야 함.
  - 차 안에 남기는 조건: 지역·플릿별로 다른 로깅 정책과 모델 변형을 같은 플랫폼에서 관리해야 함(3장 요구 8).
- **방향 4 — 에이전트가 플라이휠을 돌림**
  - 내용: 사람은 "이 상황을 고쳐라"라는 요구만 내고, 데이터 검색·정제·라벨링·학습·평가는 AI 에이전트가 수행한다는 구상임.
  - 사례: TIER IV의 주장 [보도·미확인], NVIDIA OSMO(코딩 에이전트와 연동해 재구성·큐레이션 자동화) [보도].
  - 성숙도: 주장 단계임. 검증된 양산 사례가 없음. 이 보고서는 이 방향을 투자 판단의 근거로 쓰지 않음.
- **방향 5 — 파운데이션 모델이 라벨링을 줄임**
  - 내용: 시각-언어 모델(VLM)이 차종·치수를 추론해 3D 박스 초깃값을 만들고, 장면 설명과 판단 근거를 글로 생성함. VLM을 "라벨 생성기"로 써서 가벼운 검출기를 학습시키는 방식도 포함됨(본 보고서 3.2절).
  - 사례: NVIDIA Cosmos Reason, Alpamayo-R1의 판단 근거 자동 라벨링(8만 시간 영상에 300만 개), Waymo 교사 모델 [보도·원문].
  - 관문: 자동 라벨은 라벨러 모델의 오류를 물려받으므로 검수 인력은 남음. 드문 물체일수록 검수 비율을 높여야 함.
  - 차 안에 남기는 조건: 직접적인 온보드 요구는 없음. 다만 임베딩·소형 VLM을 차 안에서 돌려 드문 장면을 차 안에서 고르는 방향으로 이어지면 추론 자원이 필요함(3장 요구 6).
- **방향 6 — 로깅이 규제 증거가 됨**
  - 내용: 개발용 트리거(개입·급제동)와 규제용 기록(DSSAD의 켜짐·꺼짐·개입·전환 요구·최소위험기동)이 같은 사건을 찍음. 따로 두면 저장·연산이 중복되므로 한 파이프라인으로 합치는 방향임.
  - 사례: UN R157 DSSAD, EU EDR 의무(2024-07), EU 2022/1426의 L3 이상 데이터 저장, 중국 로그 3년 보관, 한국 접근 기록 의무 [보도].
  - 성숙도: 이미 의무임. 여섯 방향 가운데 유일하게 "할지 말지"가 아니라 "어떻게 합칠지"만 남음.
  - 차 안에 남기는 조건: 규제 기록은 변조 방지 저장과 시간 동기화를 요구함(3장 요구 3).

### 2.3 우선순위

- 방향 6(로깅 통합)은 이미 의무이므로 가장 먼저임. 설계를 미루면 개발용·규제용 로거를 두 번 만들게 됨.
- 방향 1(월드모델 검증)은 양산에 들어갔고 규제 관문만 남았음. 도구 검증 문서를 준비하는 쪽이 앞서감.
- 방향 2(학습된 시뮬레이터)는 방향 1이 자리 잡은 뒤에 옴. 검증에 쓰던 월드모델을 학습에도 쓰는 것이므로 순서가 정해져 있음.
- 방향 5(VLM 라벨링)는 도구가 공개돼 있어 바로 도입 가능하지만 검수 체계가 먼저 필요함.
- 방향 3·4는 관찰 대상임. 투자보다 표준화 동향과 사례 검증을 지켜보는 단계임.

## 3. 차량 HPC 플랫폼 요구 사항 여덟 가지

### 3.1 전제

- 9단계 가운데 온보드 선별(①), 업로드(②), 실차 검증(⑦), 안전 관문·OTA(⑧), 반복(⑨)은 차 안에서 돎. 플라이휠은 클라우드만의 일이 아님.
- 아래 여덟 가지는 이 보고서의 근거(3장 핵심 기술, 5장 병목, 2장 기술 방향)에서 "차 안에 걸리는 것"만 추린 것임. 지금 필요한 다섯 가지는 양산 사례나 규제에서 확인된 것이고, 앞으로 더해질 세 가지는 기술 방향에서 추정한 것([미확인])임.

### 3.2 지금 필요한 다섯 가지

- **요구 1 — 섀도 실행 자원**
  - 내용: 현행 모델과 후보 모델을 같은 센서 입력으로 동시에 실행할 추론 여유.
  - 이유: 두 모델의 판단이 갈리는 순간이 가장 가치 있는 데이터이고(5.2절 병목 ①), 후보 모델을 플릿에서 검증하는 섀도 배포가 배포 전 마지막 관문임(5.3절 병목 ②). 둘 다 후보 모델이 차 안에서 돌아야 성립함.
  - 설계상 의미: 주행에 필요한 연산 외에 모델 하나를 더 돌릴 상시 여유가 있어야 함. Tesla 섀도 모드가 이 방식 [보도].
- **요구 2 — 선별·압축·두 단계 로깅**
  - 내용: 트리거로 순간을 고르고, 요약 로그와 저화질 영상을 먼저 올린 뒤, 서버가 지목한 구간만 원본을 올리는 로깅 구조.
  - 이유: 원본 전량 업로드는 통신·저장 비용 때문에 불가능함(5.4절 병목 ③). 올리지 않은 데이터는 저장·반출·라벨링 비용이 모두 0이므로 온보드 선별이 가장 싼 절감 수단임.
  - 설계상 의미: 온보드 인코더(압축), 요약본과 원본의 분리 저장, 원본 보존·삭제 정책, 서버 요청에 따른 선택 업로드 경로가 필요함. openpilot의 로깅 코드가 공개된 구현 사례 [원문].
- **요구 3 — 규제 기록의 무결성**
  - 내용: DSSAD·EDR 기록과 UN R156의 소프트웨어 버전 식별(RxSWIN)·이력을 변조 방지 저장소에 시간 동기화해 남김.
  - 이유: 로깅이 규제 증거가 되는 방향(2장 방향 6)이 이미 의무이고, 규제 기록은 "무엇을 남길지"를 정함(5.5절 병목 ④).
  - 설계상 의미: 개발용 로거와 같은 사건을 찍되 저장 경로는 변조 방지여야 하고, 센서·버스·시스템 시각이 하나의 기준으로 맞아야 함 [보도].
- **요구 4 — HIL 재생 호환**
  - 내용: 기록한 원시 센서·버스 데이터를 실제 제어기(ECU)에 시간을 맞춰 주입할 수 있는 입력 경로.
  - 이유: 시뮬레이션 결과를 믿으려면 같은 시나리오를 실차나 HIL에서 돌려 대조해야 함(5.3절 병목 ②). 월드모델 검증(방향 1)이 늘수록 대조 수요도 늘어남.
  - 설계상 의미: 플랫폼의 센서 입력 경로가 "실제 센서" 대신 "기록 재생"을 받을 수 있어야 함. dSPACE 리플레이 시스템, 현대모비스 시뮬레이터 60대 계획이 사례 [보도].
- **요구 5 — OTA 관리 프로세스**
  - 내용: UN R156의 소프트웨어 업데이트 관리체계(SUMS) 요건(버전 식별, 무결성, 호환성 확인, 안전 설치, 기록)을 배포 경로에 내장.
  - 이유: 모델 교체 자체가 인증 대상이므로 배포 주기에 하한이 생김(2.3절 차이 4, 5.5절 병목 ④). 요건을 나중에 덧붙이면 배포마다 수작업이 됨.
  - 설계상 의미: OTA 경로가 "파일을 내려받아 교체"가 아니라 "식별·검증·기록이 붙은 관리 프로세스"로 설계돼야 함. EU는 2024-07부터 모든 신차에 적용 [보도].

### 3.3 앞으로 더해질 세 가지

- **요구 6 — 온디바이스 큐레이션 연산** ([미확인] 추정)
  - 내용: 임베딩 모델이나 소형 VLM을 차 안에서 돌려 "이 장면이 드문가"를 차 안에서 판단.
  - 이유: 지금은 요약본을 올린 뒤 클라우드가 검색함. 차 안에서 고르면 업로드 비용이 더 줄고, 월드모델의 예측 실패를 희소 사건 신호로 쓰는 연구(5.2절)도 온보드 실행을 전제로 함.
  - 설계상 의미: 주행 모델·섀도 모델에 더해 검색용 모델이 하나 더 실림. 추론 자원 요구가 요구 1보다 커짐.
- **요구 7 — 증류 모델의 실행과 안전 감시** ([미확인] 추정)
  - 내용: 학습된 시뮬레이터 안에서 배운 학생 모델이 실차에 실릴 때, 시뮬–실제 격차를 런타임에서 감시하는 모니터.
  - 이유: 방향 2가 양산으로 가면 "시뮬레이터에서는 안전했던" 모델이 실제 도로에서 다르게 행동할 가능성을 차 안에서 잡아야 함. Waymo 교사-학생 구조, comma 0.11이 선행 사례 [보도·원문].
  - 설계상 의미: 모델 출력의 이상을 판정하는 감시 로직과, 이상 시 안전 상태로 넘기는 경로가 플랫폼에 있어야 함.
- **요구 8 — 지역별 모델·데이터 변형 관리** ([미확인] 추정)
  - 내용: 데이터 주권 규제로 지역마다 다른 모델·로깅 정책이 실릴 때, 같은 플랫폼에서 변형을 식별·관리.
  - 이유: Tesla는 중국 데이터를 상하이에서만 학습하고, Mercedes CLA는 중국(Momenta)과 미국(NVIDIA)의 공급 구조가 다름 [보도]. 플릿 간 공유(방향 3)가 국경 안으로 제한되면 변형은 더 늘어남.
  - 설계상 의미: 모델 버전 식별(RxSWIN)이 지역·정책 차원까지 구분해야 하고, 로깅 정책도 지역별로 전환 가능해야 함.

## 4. 기술 방향과 HPC 요구 사항의 대응 관계

- 방향 1(월드모델 검증) → 요구 4(HIL 재생). 생성 장면을 믿으려면 실차·HIL 대조가 늘어남.
- 방향 2(학습된 시뮬레이터) → 요구 7(증류 모델 감시). 시뮬레이터에서 배운 모델일수록 실차 감시가 필요함.
- 방향 3(플릿 간 공유) → 요구 8(지역별 변형). 공유가 국경 안으로 제한되면 변형 관리가 늘어남.
- 방향 5(VLM 라벨링) → 요구 6(온디바이스 큐레이션). 라벨링을 줄이는 모델이 차 안으로 내려오면 검색까지 차 안에서 하게 됨.
- 방향 6(로깅 통합) → 요구 3·5(규제 기록, OTA 프로세스). 이미 의무이므로 가장 먼저 설계에 반영됨.
- 방향 4(에이전트 운영)는 클라우드 쪽 변화라 온보드 요구를 직접 만들지 않음.

> **시사점.** 플라이휠의 첫 단계(선별·섀도)와 마지막 단계(OTA·규제 기록)는 차 안에 있음. 지금 필요한 다섯 가지는 양산과 규제에서 이미 확인된 조건이고, 앞으로의 세 가지는 기술 방향이 양산으로 갈 때 따라오는 조건임. 차량 HPC 플랫폼이 이 여덟 가지를 지원하지 않으면 플라이휠의 시작과 끝이 막힘.
