30초 요약

  1. 자율주행이 규칙 코드에서 학습 모델로 바뀌면서, 성능은 코드가 아니라 데이터가 결정하게 됐다. Tesla는 도심 주행 스택을 "30만 줄 이상의 C++ 코드를 대체하는 단일 신경망"으로 바꿨다고 릴리스 노트에 적었다 [보도].
  2. 문제는 드문 상황이다. Waymo가 공개한 롱테일 데이터셋은 일상 주행에서 0.03% 미만으로 일어나는 상황만 모은 것이고, 사고율은 이런 드문 상황에서의 실패가 좌우한다 [보도]. 게다가 도시·날씨·나라가 바뀌면 성능이 떨어지고, 새 모델은 예전에 잘하던 것을 잊기도 한다.
  3. 실도로 주행만으로는 안전을 증명할 수 없다. RAND 연구소는 사람보다 안전하다는 것을 95% 신뢰로 보이려면 무사고 2억 7,500만 마일이 필요하다고 계산했다 [보도]. 그래서 시뮬레이션과 "계속 도는 폐쇄루프"가 필요하다.
  4. 차량 데이터 플라이휠은 LLM 서비스 플라이휠과 여섯 가지가 다르다. 데이터가 차 안에서 생겨 올릴 수 있는 양이 제한되고, 정답이 사람의 개입·사고 같은 물리적 결과이며, 배포 앞에 안전 인증 관문이 있고, 소프트웨어 업데이트 자체가 규제 절차(UN R156)이며, 시뮬레이터가 필수이고, 동의 없는 제3자·위치·지리정보가 얽혀 개인정보·국외 반출 규제를 더 받는다(2.3절).
  5. 2021년의 "데이터 엔진"과 2026년의 플라이휠은 구조는 같지만 구성 기술이 바뀌었다(5.1절). 사람이 짠 트리거·사람 라벨링·로그 재생·연 단위 릴리스에서, 임베딩 검색·파운데이션 모델 자동 라벨링·3D 재구성과 생성형 월드모델·폐루프 강화학습·주 단위 OTA로 옮겨가고 있다.

1. 배경

이 장의 질문

이 장이 답하는 질문은 아래 장 구성과 같다. 장 구성. 데이터 플라이휠의 정의(1.1)와 자율주행에서 데이터 플라이휠이 주목받는 이유(1.2)를 정리한다.

세 줄 답
  1. ①데이터 플라이휠은 운행 중 생성된 데이터로 모델을 개선하고, 개선된 모델이 다시 더 가치 있는 데이터를 만들어 내는 반복 구조이다. 자율주행에서는 수집 → 저장 → 선별 → 라벨링 → 학습 → 시뮬레이션 검증 → 배포의 반복으로 정의된다.
  2. ②주행 소프트웨어가 학습 모델로 바뀌면서 모델은 데이터로만 고칠 수 있게 됐고, 한 번 수집한 데이터로 한 번 학습하는 방식은 롱테일·분포 변화·성능 회귀·실도로 검증 한계의 네 가지 문제를 해결하지 못한다.
  3. ③네 문제를 함께 해결하는 방법은 루프를 계속 반복하는 것이며, 이것이 데이터 플라이휠이다.

1.1 데이터 플라이휠의 정의

  • 정의: 데이터 플라이휠은 서비스(차량)를 운용하면서 생성된 데이터로 모델을 개선하고, 개선된 모델이 다시 더 가치 있는 데이터를 만들어 내는 반복 구조이다. 핵심은 두 가지다. 운용 중 생성된 데이터를 버리지 않고 재학습에 사용하는 것, 그리고 그 과정을 한 번이 아니라 계속 반복하는 것.
  • 자율주행에서의 정의
    • 2024년 학술 서베이는 자율주행의 데이터 플라이휠을 "(1) 데이터 수집 → (2) 저장 → (3) 선별·전처리 → (4) 라벨링 → (5) 모델 학습 → (6) 시뮬레이션·테스트 검증 → (7) 실세계 배포"의 반복으로 정의한다 [원문] (Awesome Data-Centric AD README, 논문 arXiv 2401.12888).
    • 같은 구조를 "데이터 엔진(data engine)" 또는 "폐쇄루프(closed loop)"라고도 부름. 서베이가 산업 사례로 드는 회사는 Tesla·NVIDIA·Momenta·Horizon·Baidu·XPeng·Pony.ai·Amazon 등 아홉 개이다 [원문].
  • LLM 서비스에서의 정의
    • 비교 대상: 이 보고서에서 차량 플라이휠과 대조하는 것은 서버에서 동작하는 LLM 서비스(챗봇, 음성 에이전트, 사내 지식 비서)이다. NVIDIA 블루프린트를 기준으로 삼는 이유는 여섯 단계가 공개 문서에 명시돼 있어 차량 플라이휠과 단계별로 대조할 수 있기 때문이다.
    • NVIDIA 용어집: "상호작용과 프로세스에서 모은 데이터로 AI 모델을 계속 개선하고, 그 모델이 더 좋은 결과와 더 가치 있는 데이터를 낳는 피드백 루프" [보도] (NVIDIA Glossary).
    • NVIDIA 블루프린트 README: "생산 애플리케이션의 데이터 배기가스(LLM 프롬프트·응답 로그, 사용자 피드백, 전문가 라벨)를 사용해 생성형 AI 시스템의 정확도를 높이고 지연·비용을 줄이는 프로세스" [원문] (data-flywheel README).
  • 두 정의의 차이(상세는 2.3절): 데이터가 생기는 곳(서버 로그 / 차 안 센서), 정답의 성격(사용자 피드백·모델 채점 / 운전자 개입·사고 같은 물리적 결과), 배포 절차(서버 모델 교체 / 시뮬레이션 검증·안전 인증·규제)의 세 가지다.
  • 용어 기원: 플라이휠(flywheel)은 한번 돌면 관성으로 계속 도는 무거운 바퀴를 뜻하며, Amazon의 2001년 선순환 모형(가격 인하 → 고객 증가 → 판매자·상품 증가)에서 사업 용어로 굳어졌다 [보도] (retaildogma).
시사점

용어(플라이휠·데이터 엔진·폐쇄루프)는 다르지만 구조는 같는다. "운용 중 생성된 데이터를 다시 학습에 쓰고, 이를 반복한다"가 공통 정의이다.

1.2 데이터 플라이휠이 주목받는 이유

  • 전제: 주행 소프트웨어가 학습 모델이 됨
    • Tesla는 FSD v12(2024-03)에서 도심 주행 스택을 "수백만 개 영상 클립으로 학습한 단일 종단간 신경망"으로 바꾸고 30만 줄 이상의 C++ 코드를 대체했다고 릴리스 노트에 명시한다 [보도] (릴리스 노트 인용). Waymo·Wayve·comma.ai도 같은 방향이다 [보도].
    • 규칙은 사람이 고치지만, 학습 모델은 데이터로만 고칠 수 있다. 모델이 어떤 상황에서 틀렸다면 그 상황의 데이터를 더 모아 다시 학습시키는 것 외에 방법이 없다. 따라서 문제는 "어떤 데이터가, 왜 부족한가"로 바뀜.
  • 한 번 학습하는 방식으로는 풀리지 않는 네 가지 한계: 롱테일, 분포 변화, 성능 회귀, 실도로 검증의 한계. 넷 다 "한 번 수집한 데이터로 한 번 학습해 배포하는" 방식으로는 해결되지 않으며, 이것이 데이터 플라이휠이 주목받는 이유이다.
  • 한계 ① 롱테일 — 드문 상황이 사고율을 결정함
    • 주행의 대부분(직진·차선 유지·앞차 추종)은 모델이 금방 학습한다. 문제는 공사 구간의 작업자, 갑자기 뛰어드는 동물, 비 오는 밤의 역광처럼 각각은 드물지만 종류가 무한히 많은 상황(롱테일)이다.
    • Waymo의 WOD-E2E 데이터셋(2025-10)은 일상 주행에서 발생 빈도 0.03% 미만인 상황만 골라 4,021개 구간(약 12시간)을 모은 것이다. 흔한 상황에서는 모델 간 차이가 없고 드문 상황에서만 차이가 드러나기 때문이다 [보도] (arXiv 2510.26125).
    • 안전 지표 자체가 드문 사건이다. 미국 사람 운전자의 부상 신고 충돌은 100만 마일당 2.80건이므로 [보도] (Waymo 비교 연구), 99.99%를 잘하는 것으로는 부족하고 나머지 0.01%에서의 판단이 사고율을 결정한다.

  • 한계 ③ 성능 회귀 — 재학습한 모델이 예전에 잘하던 것을 잊음
    • 새 데이터에 맞춰 가중치를 바꾸다가 예전 지식이 덮어써지는 현상(파국적 망각)이며, 자율주행의 지속 학습에서도 보호 장치 없이 재학습만 하면 발생한다 [보도] (IEEE).
    • 대응은 회귀 테스트이다. Tesla는 잘못된 예측을 "유닛 테스트"로 남기고 비슷한 예제를 추가해 재학습하는 루프를 운용했고(2021년 기준 트리거 221개) [보도] (발표 요약), Waymo는 새 소프트웨어마다 테스트 트랙·실도로·합성 시나리오 전부를 시뮬레이션에서 재실행한다 [보도] (Waymo CAT).
  • 한계 ④ 실도로 검증의 한계 — 주행 거리로는 안전을 증명할 수 없음
    • RAND(2016)는 자율주행차가 사람보다 사망률이 낮다는 것을 95% 신뢰로 보이려면 무사고 2억 7,500만 마일, "20% 더 안전"을 입증하려면 110억 마일이 필요하다고 계산하고 "주행만으로는 안전에 도달할 수 없다"고 결론지음 [보도] (RAND RR-1478).
    • 세계에서 가장 많이 달린 Waymo도 2026년 3월 기준 무인 누적 2억 2,060만 마일로 첫 번째 문턱을 넘었을 뿐이다. 1억 7,070만 마일 분석에서 사람 대비 중상 이상 충돌 92% 감소를 보고했고 [보도] (Waymo Safety Impact), 독립 기관 IIHS는 부상 충돌 81% 감소로 집계한다 [보도].
    • 따라서 시뮬레이션이 필수이다. Waymo는 실주행 2,000만 마일에 시뮬레이션 200억 마일 이상을 더했고, 자체 시뮬레이터는 하루 800만~1,000만 마일을 주행한다 [보도] (Simulation City). 안전 표준 ISO 21448(SOTIF)도 "모르는 불안전 상황"을 시뮬레이션을 포함한 검증으로 줄이는 반복 과정을 요구한다 [보도] (Ansys SOTIF 해설).
  • 결론: 네 한계는 한 방향을 가리킴

  • 네 가지를 한 번에 해결하는 방법은 하나이다. 차에서 데이터를 모으고, 고치고, 시뮬레이션으로 확인하고, 다시 차에 보내는 루프를 계속 반복하는 것. 그 구조를 2장에서 펼침.
시사점

플라이휠은 선택이 아니라 학습 기반 자율주행의 전제 조건이다. 다음 장은 그 구조를 단계별로 펼침.

2. 차량·클라우드·검증 환경을 연결하는 데이터 플라이휠 생태계

이 장의 질문

이 장이 답하는 질문은 아래 장 구성과 같다. 장 구성. 차량 데이터 플라이휠의 전체 구조(9단계)를 먼저 펼치고(2.1), 비교 기준으로 LLM 서비스 데이터 플라이휠을 소개한 뒤(2.2), 둘의 차이를 여섯 가지로 정리함(2.3). 2021년 데이터 엔진이 2026년 플라이휠로 어떻게 바뀌었는지는 5.1절에서 다룸.

세 줄 답
  1. ①차량 플라이휠은 온보드 선별 → 업로드 → 검색 → 라벨링 → 학습 → 시뮬레이션 검증 → 실차 검증 → 안전 관문·OTA의 9단계이며, 이 중 온보드 선별·시뮬레이션 검증·실차 검증·안전 관문은 LLM 서비스 플라이휠에 없는 단계이다.
  2. ②LLM 서비스 플라이휠은 "생산 로그 → 데이터셋 → 미세조정 → 평가 → 배포"의 루프이며, NVIDIA가 이를 소프트웨어 블루프린트로 공개한다.
  3. ③두 플라이휠의 차이는 데이터 원천, 정답의 성격, 배포 절차에서 비롯되며, 개인정보·데이터 주권 규제도 차량 쪽이 더 넓게 받는다.

2.1 차량 데이터 플라이휠의 전체 구조

차량 플라이휠은 구조는 같지만 단계가 더 많다. 아래 구조는 세 종류의 공개 자료가 공통으로 말하는 것을 합친 것이다. Tesla가 2021년 AI Day에서 설명한 데이터 엔진 [보도] (CleanTechnica), NVIDIA·AWS가 2026년 3월 설명한 "AV 3.0 데이터 파이프라인" [보도] (AWS 블로그, 본문은 요약만 확인·다이어그램은 그림 5), 그리고 Li et al. 2024 서베이(arXiv 2401.12888)의 7단계 폐쇄루프 [원문] (README 3.1절).

단계 장소 역할 대표 사례
① 온보드 선별 차 안 모든 데이터를 올릴 수 없으므로 "트리거"(조건)에 걸린 짧은 클립만 고른다. 새 모델을 몰래 실어 기존 모델·운전자와 비교하는 섀도 모드도 여기서 돈다 Tesla 트리거 221개, 약 10초 클립 [보도]; openpilot은 카메라·CAN·GPS·IMU를 기본 업로드 [원문]
② 업로드·저장 차 → 클라우드 통신비·저장비 예산 안에서 올린다 Mobileye REM은 km당 약 10KB만 보낸다 [보도]; comma는 월 수백 TB 처리 [보도]
③ 검색·큐레이션 클라우드 수백만 클립에서 원하는 상황을 찾고 중복을 없앤다 NVIDIA Cosmos Curator·Dataset Search [보도]
④ 라벨링 클라우드 정답을 붙인다. 사람 또는 오프라인 대형 모델 Tesla 자동 라벨링(주 1만 클립) [보도]
⑤ 학습 클라우드 실데이터 + 합성 데이터로 재학습 Tesla Cortex, NVIDIA DGX [보도]
⑥ 시뮬레이션 검증 클라우드 로그 재생·3D 재구성·생성 시나리오로 폐루프 시험, 회귀 테스트 Waymo 하루 800만~1,000만 시뮬 마일 [보도]
⑦ 실차 검증 시험장·시험 플릿 HIL(하드웨어 인 더 루프)·테스트 트랙·시험 차량 Waymo 테스트 트랙 + 실도로 [보도]
⑧ 안전 관문·OTA 인증 → 차 안전 논증 갱신, 규제(UN R156) 요건 확인 후 단계적 배포 Tesla v14.x 주 단위 OTA [보도]
⑨ 다시 ① 차 안 새 모델이 새 실패를 만든다 —

LLM 서비스 플라이휠의 6단계 중 "로그 수집·데이터셋·학습·평가·배포"는 그대로 있다. 차량에서 새로 생긴 것은 ①(차 안 선별), ⑥(시뮬레이션이 필수), ⑦(실차), ⑧(안전 관문·규제)이다. 세 근거와 단계의 대응은 이렇다. 서베이의 7단계 "(I) 수집 → (II) 저장 → (III) 선별·전처리 → (IV) 라벨링 → (V) 학습 → (VI) 시뮬레이션·테스트 검증 → (VII) 실세계 배포"는 ②③④⑤⑥⑧에 해당한다. ①(온보드 선별·섀도 모드)은 Tesla 데이터 엔진에서, ⑦(실차 검증)은 Waymo 사례에서, ⑧의 안전 관문·UN R156은 규제 자료에서 더한 것이다.

이 파이프라인은 클라우드 안쪽(수집 이후 → 학습 → 시뮬레이션)만 그리고, 차 안 선별·실차 검증·규제 관문은 없다. 그림 4의 ③~⑥을 도구 이름 수준으로 채운 그림으로 보면 된다. 사람(Users)이 검색과 증강 도구에 붙어 있는 점은 "사람이 고르고 만든다"는 3장의 3.2·3.4절 흐름과 같다.

2.2 비교 기준 — LLM 서비스 데이터 플라이휠

비교를 위해 먼저 "일반" 플라이휠을 본다. NVIDIA가 GitHub에 공개한 데이터 플라이휠 블루프린트는 정의를 이렇게 적는다. "데이터 플라이휠은 생산 애플리케이션의 데이터 배기가스(예: LLM 프롬프트·응답 로그, 사용자 피드백, 전문가 라벨)를 사용해 생성형 AI 시스템의 정확도를 높이고 지연·비용을 줄이는 프로세스다" [원문] (data-flywheel README).

같은 문서가 "몇 시간 안에 자동으로 한다"고 설명하는 단계는 여섯 개다 [원문].

  1. 로그 저장소(Elasticsearch)에서 생산 데이터를 가져온다.
  2. 작업(task)별로 묶는다. 에이전트가 여러 일을 하면 노드마다 다른 작업이다.
  3. 중복을 없앤다.
  4. 클래스별 계층화 분할로 평가용·미세조정용 데이터셋을 만들어 데이터 저장소(NeMo Datastore)에 올린다.
  5. 미세조정 서비스(NeMo Customizer)로 작은 모델을 학습시킨다.
  6. 평가 서비스(NeMo Evaluator)가 "LLM-as-judge"(큰 모델이 채점자 역할)로 원래 모델과 비교한다.

승격은 자동이 아니다. README는 "플라이휠은 자동 조종 장치가 아니라 손전등"이라고 쓰고, 제한 사항 문서는 "이 플라이휠은 어떤 모델도 자동으로 승격·배포하지 않으며, 사용자 피드백도 받지 않는다"고 명시한다 [원문] (제한 사항, 구조 문서). 즉 여섯 단계는 후보를 찾아 점수를 매기는 데서 끝나고, 승격은 사람이 결정한다.

효과는 비용이다. README는 "NVIDIA 내부 실험에서 플라이휠로 추론 비용을 최대 98.6% 줄인 사례가 있다"고 쓰되, 바로 뒤에 "이런 사례는 에이전트가 소수의 도구 중 하나를 고르는 단순한 도구 호출 용도에 집중돼 있다"고 단서를 단다 [원문]. 인사 챗봇에서 미세조정한 1B 모델이 70B 모델 정확도의 약 98%를 냈다는 것이 그 사례다. NVIDIA가 사내 지식 비서(직원 3만 명 이상 사용)에 같은 방식을 적용한 논문도 있다. 3개월간 부정 피드백 495건을 모아 라우팅 오류 5.25%를 찾아냈고, 라우터를 70B 모델에서 미세조정한 8B 모델로 바꿔 정확도 96%에 지연 70% 감소를 얻었다 [보도] (arXiv 2510.27051).

2.3 차량 플라이휠과 LLM 서비스 플라이휠의 차이

  • 차이가 생기는 원인: 세 가지다. 데이터가 차 안 센서에서 생성됨, 정답이 물리적 결과임, 배포가 안전 인증과 규제의 대상이다. 아래 여섯 가지 차이는 이 세 원인에서 비롯된다.
# 항목 LLM 서비스(챗봇·에이전트) 자율주행 근거
1 데이터 원천과 업로드 가능량 서버 로그에 자동으로 축적되며 전량 보관 가능 차 안 센서에서 생성됨. 시간당 수십 GB~수 TB라 전량 업로드가 불가능하고, 차 안에서 선별·압축해야 함(3.1절) Tesla HW4 카메라 시간당 약 20GB(커뮤니티 추정 [미확인]); Mobileye REM km당 10KB [보도]
2 정답(라벨)의 성격 사용자 피드백, 대형 모델의 채점 운전자 개입·충돌 같은 물리적 결과. 3D 위치·속도처럼 사람이 만들기 어려운 라벨이 많아 자동 라벨링이 필수(3.2절) Tesla 섀도 모드 [보도]; NHTSA 충돌 보고 의무 [보도] (SGO 2021-01)
3 배포 전 안전 인증 평가 점수가 기준을 넘으면 교체 ISO 26262(고장), ISO 21448(성능 한계로 인한 위험), ISO/PAS 8800(AI 부품 안전)에 따른 안전 논증(안전 케이스)을 갱신해야 함 [보도] (UL 해설)
4 업데이트 절차 교체 시점과 주기를 사업자가 정함. 외부 인증·승인 절차가 없고, 일반 소프트웨어와 같은 점진 배포(섀도 → 일부 트래픽 → 전체)와 롤백으로 교체함. NVIDIA 블루프린트는 후보 모델 생성·평가를 "몇 시간 안에" 수행함 UN R156에 따라 업데이트 관리체계(SUMS) 인증, 버전 식별 번호(RxSWIN) 부여, 인증 기능에 영향 시 재승인, 호환성 확인·안전 설치·기록이 필요함. EU는 2024년 7월부터 모든 신차에 적용. 모델 교체 자체가 인증 대상이므로 배포 주기에 하한이 생김 블루프린트 README [원문]; LLM 점진 배포 해설 [보도] (tianpan.co); R156 [보도] (요약)
5 검증 수단 실제 사용자 대상 A/B 테스트 위험 상황을 실차로 반복할 수 없고 주행 거리로는 안전을 증명할 수 없으므로(1.2절) 시뮬레이션이 주 수단 Waymo 실주행 2,000만 vs 시뮬 200억 마일 [보도]
6 개인정보·데이터 주권 개인정보 규제(GDPR 등)를 받지만, 데이터 주체는 약관에 동의한 서비스 이용자이고 데이터는 글·클릭임 같은 규제에 더해 ① 동의하지 않은 제3자(보행자·다른 차량·번호판)가 촬영되고 ② 위치·이동 경로가 항상 결합되며 ③ 도로·지형 영상이 지리정보로 취급돼 국외 반출 규제를 받음 EDPB 가이드라인 [보도] (1/2020); Tesla 상하이 데이터센터 [보도] (Electrek 2026-02); 한국 샌드박스·국외 이전 심사 [보도] (국내 보도, 머니투데이 2026-08)
  • 차이 6 보충 — 개인정보 규제의 범위
    • 얼굴·번호판 같은 개인정보는 LLM 서비스 데이터에도 포함되며 GDPR 등 규제도 동일하게 적용된다. 차량이 다른 점은 데이터 종류가 아니라 동의 구조·위치 결합·지리정보 규제 세 가지다.
    • 동의 구조: 서비스 이용자는 약관에 동의한 당사자이지만, 차량이 촬영하는 보행자·다른 운전자는 동의한 적이 없다. EU 개인정보 감독기구(EDPB)는 차량 외부의 사람·번호판을 별도 항목으로 다루고 차내 처리를 권고한다 [보도].
    • 위치 결합: 주행 영상은 시각·위치와 함께 기록되므로 얼굴을 가려도 이동 경로가 개인정보가 된다.
    • 지리정보 규제: 도로·건물 영상은 지도 데이터와 같은 취급을 받는다. 중국은 차량 운행 정보의 국외 반출을 원칙적으로 금지하고 [보도], 한국은 자율주행 영상의 국외 이전을 개인정보위 심사 대상으로 둠 [보도].
    • 결과: 얼굴·번호판을 가리면 인식 학습에 필요한 정보가 사라지는 문제가 생김. 한국이 안전 조치를 조건으로 원본 영상 학습을 규제 샌드박스로 허용한 배경임(5.5절).
시사점

LLM 서비스 플라이휠의 과제는 반복 속도이고, 차량 플라이휠의 과제는 안전 인증·규제 관문을 통과하면서 반복을 유지하는 것이다.

이 장의 질문

2장이 보여 준 9단계 안에서 실제로 어떤 기술이 사용되고, 각 기술의 원리·도구·사례는 무엇인가. 장 구성. 2장이 플라이휠의 전체 구조(9단계)를 보여 줬다면, 이 장은 그 안에서 실제로 쓰이는 핵심 기술을 네 묶음으로 나눠 정리한다. ① 데이터 수집·선별(차 안, 단계 ①②) ② 검색·라벨링(클라우드, 단계 ③④) ③ 학습·합성 데이터(클라우드, 단계 ⑤) ④ 검증·배포(단계 ⑥⑦⑧). 각 절은 배경 → 관련 기술 → 도구 → 사례 순서로 구성하며, 도구의 세부 설정은 생략하고 원리 위주로 적는다.

세 줄 답
  1. ①차 안에서는 트리거(규칙·모델 점수·사람)로 업로드할 순간을 고르고, 요약본을 먼저 올린 뒤 원본은 서버가 지정할 때만 올림.
  2. ②클라우드에서는 임베딩 검색으로 유사 장면을 수백~수천 개 모으고, 차 안 모델보다 큰 모델이 미래 프레임까지 참고해 정답을 사후에 붙이다.
  3. ③부족한 장면은 재생·재구성·생성 세 방식의 합성 데이터로 보충하고, 시뮬레이터 안에서 모델이 직접 주행하며 학습하는 폐루프 학습으로 이행 중이다.
  4. ④검증은 단일 지표가 아니라 개루프 → 폐루프 → 사람 선호 → 회귀 세트 → 실차 → 섀도 → 단계적 OTA로 이어지는 단계적 검증이며, 마지막 단계(OTA)는 규제 절차이다.

가상 사례. 밤 10시, 비가 오는 편도 2차선 도로. 공사 구간이라 콘이 차선을 막고 있고, 콘 옆에 형광 조끼를 입은 작업자가 서 있다. 차의 모델은 콘은 일찍 봤지만 작업자를 늦게 인식했고, 운전자가 브레이크를 밟아 개입했다. 사고는 없었다.

  • 각 절의 "사례" 끝에 이 클립이 해당 기술을 거치는 과정을 적는다.

3.1 데이터 수집·선별 (차 안) — 단계 ①②

  • 배경
    • 차량 1대가 생성하는 원본 데이터는 하루 수 TB 수준이다. Intel은 2016년 차량당 하루 약 4TB로 추정했고 [보도] (Intel 2016), 최근 업계 추정은 시간당 1~5TB이다 [보도·미확인] (Siemens 블로그).
    • 통신 요금과 저장 비용 때문에 전량 업로드는 불가능하다. 따라서 차 안에서 업로드할 순간을 선별하고, 선별한 데이터도 압축해 전송해야 한다.
    • 관련 기술은 세 가지다. 트리거(어느 순간을 선별할지), 섀도 모드(새 모델을 안전하게 시험하면서 선별할지), 두 단계 업로드(선별한 데이터를 얼마나 적은 비용으로 올릴지).
  • 관련 기술 1 — 트리거
    • 정의: 차 안에서 "이 순간의 데이터를 저장·업로드하라"고 판단하는 조건.
    • 작동: 센서 데이터가 연속으로 생성되는 동안 조건이 충족된 순간의 앞뒤 몇 초를 잘라 보관·업로드 대상으로 표시한다. Tesla는 약 10초 단위 클립을 사용한다 [보도].
    • 한계: 사전에 정한 조건만 포착한다. 정의되지 않은 상황은 포착하지 못하므로 클라우드의 검색(3.2절)이 이를 보완한다.
    • 종류: 세 가지.
종류 트리거 조건 사례
규칙 운전자 개입, 급제동, 충돌, 시스템 오류 UN R157의 기록 장치(DSSAD)도 시스템 켜짐·꺼짐·개입을 기록하도록 요구 [보도] (해설)
모델 점수 차 안의 소형 모델이 "드문 장면" 점수를 산출하거나, 두 모델의 판단이 불일치할 때 Tesla 트리거 221개(2021) [보도] (Karpathy CVPR'21 요약); NVIDIA는 모델 앙상블의 불일치로 선별한 데이터가 수동 선별보다 야간 보행자 검출을 3배 개선 [보도] (NVIDIA 블로그)

  • 관련 기술 2 — 섀도 모드
    • 정의: 새 후보 모델을 차량에 탑재하되 제어권은 주지 않고, 판단만 기록해 현행 모델·운전자와 비교하는 방식.
    • 작동: 현행 모델과 후보 모델이 같은 센서 입력을 받아 각각 판단한다. 두 판단이 불일치하거나 후보 모델이 운전자와 다르게 판단한 순간을 기록한다.
    • 역할: 두 가지. 판단 불일치 순간이 가치 있는 데이터의 신호이므로 트리거의 한 종류이고, 새 모델을 실제 도로에서 위험 없이 시험하므로 검증(3.4절)의 한 단계이기도 한다.
    • 전제: 현행 모델과 후보 모델을 동시에 실행할 추론 자원이 차량에 있어야 함(5.6절).
  • 관련 기술 3 — 두 단계 업로드
    • 원리: 선별한 순간이라도 원본(고화질 영상 + 전체 로그)은 용량이 크므로, 소용량 요약본을 먼저 올리고 원본은 서버가 지정할 때만 올림.
    • 1단계: 요약본(핵심 신호 + 저화질 영상)을 모든 구간에 대해 업로드한다. 서버는 요약본으로 흥미로운 구간을 검색한다.
    • 2단계: 서버가 특정 구간의 원본을 요청하면 차량에 보관 중인 원본을 업로드한다. 요청되지 않은 원본은 저장 공간이 부족해질 때 삭제한다.
    • 효과: 업로드하지 않은 데이터는 통신·저장·라벨링 비용이 발생하지 않는다. 요약본은 검색용, 원본은 학습용으로 역할이 구분된다.
  • 도구 — 오픈소스 openpilot의 로깅 코드. 양산차에 탑재돼 매일 운용되는 오픈소스이므로 두 단계 업로드의 실제 구현을 코드로 확인할 수 있다 [원문] (commaai/openpilot, 커밋 521db4c, 2026-09-20).

  • 도구에서 확인된 설계 원칙

    • 운전자 북마크는 사람 트리거이면서 삭제 정책의 예외이다. 사람이 표시한 순간이 가장 오래 보존된다.

3.2 검색·라벨링 (클라우드) — 단계 ③④

  • 배경
    • 클립 하나로는 모델을 개선할 수 없다. 플릿 전체에서 유사 장면을 수백~수천 개 수집해야 한다.
    • 수집한 장면마다 정답(물체 위치·차선·궤적)을 부여해야 학습에 사용할 수 있다.
    • 관련 기술은 세 가지다. 임베딩 검색(유사 장면 검색), 자동 라벨링(정답 부여), 사람 검수(품질 확인).
  • 관련 기술 1 — 임베딩 검색
    • 정의: 영상(또는 글)의 내용을 요약한 숫자 목록(임베딩)을 생성해 두고, 숫자가 가까운 항목을 찾는 검색.
    • 작동: 의미가 유사한 영상은 숫자도 유사하게 나오도록 모델을 학습시켜 둠. "비 오는 밤 공사 구간의 작업자"라는 글을 같은 방식으로 숫자로 변환하면, 숫자가 가까운 영상이 검색된다.
    • 효과: 조건을 사전에 코드로 정의할 필요가 없고, 트리거에 포착되지 않았던 위험 근접 장면까지 회수할 수 있다.
  • 관련 기술 2 — 자동 라벨링
    • 정의: 클라우드의 대형 모델이 수집된 영상에 정답(라벨)을 자동으로 부여하는 기술. 사람은 라벨을 만드는 대신 결과를 검수한다.
    • 원리: 차 안 모델은 현재 프레임까지만 보고 소형 모델로 즉시 판단해야 한다. 클라우드의 라벨러는 미래 프레임을 참고하고, 같은 장소를 지난 여러 차량의 주행을 합치고, 차에 실을 수 없는 크기의 모델을 사용한다. 이 세 가지 이점으로 차 안 모델보다 정확한 정답을 사후에 만듦.
    • 작동 방식: 네 가지가 쓰인다.
      • 시퀀스 단위 정밀화: 프레임마다 물체를 검출한 뒤 추적기로 연결하고, 물체 하나의 전체 구간 관측을 모아 크기·방향·궤적을 다시 추정한다. 뒤쪽 프레임에서 명확히 보인 물체를 앞쪽 프레임까지 거슬러 라벨링할 수 있다. Waymo의 3D 자동 라벨링이 이 방식이며, 사람 라벨과 동등한 품질을 보고한다 [보도] (arXiv 2103.05073).
      • 다중 주행 재구성: 같은 장소를 지난 여러 차량의 영상과 주행 기록을 하나의 3D 공간에 정합해 차선·도로 구조를 복원한 뒤, 각 클립에 되돌려 투영한다. 라이다 없이 카메라만으로 3D 정답을 만드는 방법이며, Tesla가 AI Day 2022에서 공개한다 [보도] (요약).
      • 오픈 어휘 모델 조합: 글로 물체를 지정하면 박스를 생성하는 모델(Grounding DINO)과, 박스나 점을 주면 영상 전체에서 윤곽을 추적하는 모델(SAM 2)을 이어 붙여, 미리 정한 클래스 목록에 없는 물체도 라벨링한다 [원문].
      • 시각-언어 모델(VLM) 설명 생성: VLM이 장면의 상황과 운전 판단의 근거를 글로 생성하고, 규칙과 사람 검수로 보정한다. 추론형 주행 모델의 학습 데이터와 검색용 설명에 쓰인다. NVIDIA는 8만 시간 영상에 300만 개의 판단 근거(Chain of Causation)를 VLM 자동 라벨링과 사람 주석의 혼합으로 생성했다고 밝힘 [보도] (arXiv 2511.00088).
    • 한계: 자동 라벨은 라벨러 모델의 오류를 그대로 물려받는다. 빈도가 높은 물체는 정확도가 높아도 드문 물체는 낮을 수 있고, 라이다가 없는 플릿은 3D 박스 정확도가 재구성 품질에 좌우된다.
  • 자동 라벨링의 대상: 무엇을 라벨링하는지는 학습할 모델이 정한다. 자율주행에서 자동 생성되는 주요 라벨은 아래 표와 같다.

3.3 학습·합성 데이터 (클라우드) — 단계 ⑤

  • 배경
    • 첫 번째 방법은 수집한 장면의 학습 비중을 높이는 것(오버샘플링)이다. Tesla FSD v14.3 릴리스 노트는 "강화학습 단계를 업그레이드해 어려운 예에 집중"했다고 명시한다 [보도·미확인] (릴리스 노트 인용).
    • 그러나 "작업자가 콘 뒤에서 나오는" 변형이나 "강우 강도가 더 높은" 변형은 플릿 데이터에 없다. 따라서 합성 데이터가 필요하다.
    • 관련 기술은 세 가지다. 합성 데이터(없는 장면 생성), 폐루프 학습(판단 결과를 반영한 학습), 교사-학생 증류(대형 모델로 학습하고 소형 모델을 탑재).
  • 관련 기술 1 — 합성 데이터
    • 정의: 실제 주행 데이터에 없는 장면을 재생·재구성·생성 세 방식으로 만드는 기술.
    • 방식별 비교: 아래 표. 오른쪽으로 갈수록 없던 상황을 만들 수 있지만 현실과의 격차 검증이 필요하다.
방식 내용 장점·한계
재생(replay) 기록된 로그를 그대로 재생하고 새 모델을 실행함. 다른 차량은 기록대로만 움직임 비용이 가장 낮고 정확하지만, 자차가 다르게 움직여도 주변 차량이 반응하지 않음 [보도] (분석)
재구성(reconstruction) 실제 로그를 3D 장면으로 복원해 다른 궤적·시점에서 다시 렌더링함 실제 장면 기반이라 현실성이 높고 반사실 궤적("그때 왼쪽으로 조향했다면")을 확인할 수 있음. 기록 범위 밖은 품질 저하
생성(generation) 조건(지도·라이다·날씨)을 주고 없던 영상을 생성함 존재하지 않는 조합을 만들 수 있는 유일한 방식. 현실과의 격차 검증이 필수
  • 관련 기술 2 — 폐루프 학습
    • 문제: 기록을 모방하는 학습(모방학습)만 하면 모델은 자기 판단의 결과를 경험하지 못한다.
    • 정의: 시뮬레이터 안에서 모델이 직접 주행하고 그 결과(충돌·이탈)로 학습하는 강화학습. 시뮬레이터 자체를 학습된 월드모델로 구성하면 "학습된 시뮬레이터"가 된다.
  • 관련 기술 3 — 교사-학생 증류
    • 정의: 클라우드에서 크기 제한 없는 "교사" 모델을 학습시키고, 차량에는 실시간 실행이 가능한 소형 "학생" 모델을 탑재한다. 학생은 교사의 출력을 따라 학습한다.
    • 역할: 클라우드의 대형 모델과 차량의 소형 모델을 연결하는 수단이다.

4. 기업별 데이터 플라이휠 전략과 최근 산업 동향

이 장의 질문

회사마다 플라이휠이 실제로 어떻게 도는가. 데이터가 누구 차에서 생겨 어느 단계까지 누가 처리하고, 어떤 단계를 남에게 맡기며, 무엇이 되어 돌아가는가.

세 줄 답
  1. ①어느 회사도 9단계를 전부 남에게 맡기지 않는다. 온보드 선별(①)·학습(⑤)·배포 책임(⑧)은 예외 없이 자체로 쥐고, 검색·라벨링·시뮬 도구(③④⑥)는 사거나 열어 쓴다.
  2. ②차이는 "데이터가 누구 차에서 생겨 누구에게 돌아가는가"에서 갈린다. 자기 양산차(Tesla·XPeng·현대차 계획), 자기 로보택시(Waymo·Baidu), 남의 양산차에서 공급자에게 회수(Momenta·Mobileye), 지역별로 갈라진 회수(Mercedes·BMW)의 네 갈래가 있고, 데이터 주권 규제가 회수 경로를 국경 안으로 제한한다.
  3. ③2026년의 공통 이동은 시뮬레이션(⑥)을 월드모델로 바꾸고 그 월드모델 안에서 학습(⑤)까지 하려는 것이다. 이 장의 수치는 대부분 기업 발표이므로 "공개 주장"으로 읽어야 한다.

4.1 플라이휠 운영 유형 — 플릿과 모델의 보유 주체에 따른 분류

  • 분류 기준: 기준은 한 가지다. 플라이휠에 데이터를 공급하는 플릿을 누가 보유하고, 플라이휠이 만든 모델을 누가 배포하는가. 두 질문의 답으로 네 유형이 나옴. 파운데이션 모델·월드모델은 기술 선택이지 운영 주체가 아니므로 유형에 넣지 않고, 네 유형 모두에 걸친 공통 이동으로 4.9절에서 다룸.
유형 플릿 보유 / 모델 배포 데이터 특성 강점 약점 대표 기업
유형 1 자사 양산 플릿 운영형 자사 양산차 / 자사 수십만~수백만 대, 카메라 위주. 섀도 모드로 플릿에서 후보 모델 검증 데이터 양이 많고, 수집·검증·배포 대상이 같은 플릿이라 한 바퀴가 빠름 센서 구성이 단순해 3D 정답을 재구성으로 만들어야 함. 플릿이 형성될 때까지 시간이 걸림 Tesla, XPeng, comma.ai(사용자 차량), 현대차그룹(계획)

유형 3 파트너 플릿 기반 모델 공급형 파트너 OEM의 양산차 / OEM이 배포, 모델은 공급자가 제작 회수 범위가 OEM 계약과 지역 규제에 좌우됨 여러 OEM·지역의 플릿을 합쳐 규모를 확보하고 한 모델을 재사용 회수권과 배포 시점을 OEM이 쥐어 한 바퀴가 OEM 프로그램 주기에 묶임 Momenta, Mobileye, Wayve(Nissan 등)
유형 4 도구·플랫폼 공급형 보유 플릿 없음 / 고객 고객 플릿의 데이터를 도구로 처리 특정 단계(③④⑥⑦)를 여러 고객에게 공급해 규모 확보 플릿·배포 책임이 없어 폐루프를 직접 완성하지 못함 NVIDIA, Applied Intuition, Voxel51, Foretellix, TIER IV
  • 유형이 정하는 것과 정하지 않는 것
    • 플릿 종류(유형 1·2)가 라벨링 방식(④)과 시뮬레이션 비중(⑥)을 정한다. 양산 플릿은 라이다가 없어 카메라 다중 주행 재구성으로 정답을 만들고, 로보택시 플릿은 라이다로 3D 정답을 만들되 시뮬레이션 마일을 수십억 단위로 쌓는다.
    • 모델 배포 주체가 배포 주기를 정한다. 자사 배포(유형 1·2)는 주 단위 OTA가 가능하고(Tesla), OEM 배포(유형 3)는 OEM 프로그램 주기에 맞춤(Momenta 세대 연 1회) [보도].
    • 파운데이션 모델·월드모델은 유형을 가리지 않는다. XPeng X-World(유형 1), Waymo Foundation Model·World Model(유형 2), Momenta R7·Wayve GAIA(유형 3), NVIDIA Cosmos(유형 4)가 모두 채택함(4.9절 공통점 3).
    • 경계 사례: Mobileye는 칩(유형 4)과 REM 지도·주행 모델(유형 3)을 함께 공급한다. 데이터를 회수해 산출물을 만드는 주된 플라이휠이 유형 3이므로 유형 3에 둔다. NVIDIA는 Uber 등과 플릿 계획을 발표했으나 2026-09 기준 자사 플릿이 없어 유형 4에 둔다 [보도].

4.2 분석 틀 — 9단계 담당 주체

4.3 Tesla — 양산 플릿 기반 전 단계 자체 운영

Tesla는 9단계를 전부 한 조직 안에서 돌린다. 단계별 운영 방식은 다음과 같다.

단계 운영 방식 근거
① 온보드 선별 FSD를 켜지 않은 차에서도 백그라운드 판단을 실제 운전과 비교하는 섀도 모드. 2021년 기준 트리거 221개 [보도] (Karpathy CVPR'21 요약)
② 업로드·저장 약 10초 클립 업로드. 2021년 첫 데이터셋 100만 클립·1.5PB, 2026년 FSD 누적 140억 마일 [보도·미확인] (Electrek)
③④ 검색·라벨링 여러 차의 주행을 합쳐 4D(3D + 시간)로 재구성한 뒤 자동 라벨링. 1만 주행 기준 "수작업 500만 시간 → 12시간" 주장. 2022년 자체 라벨팀 감원 [보도·미확인]
⑤ 학습 학습 클러스터 Cortex(2026년 1분기 "H100 상당 10만 장 이상", Cortex 2 추가). v14.3 릴리스 노트에 "강화학습 단계" 명시 [보도·미확인] (TechCrunch)
⑥ 시뮬 검증 비공개. 2026년 보도는 "실도로 데이터 → 자동 라벨링 → 신경망 시뮬레이터 → 강화학습 → 새 모델 → 플릿 검증" 루프를 전한다 [보도·미확인] (Not a Tesla App)
⑦⑧ 실차·배포 여러 라운드 섀도 후 활성화 → 플릿 0.1% 미만 → 약 10% → 광역. 대형 버전 약 10개월(v13 → v14), 포인트 릴리스 1~2주 [보도·미확인]

구조의 특징은 세 가지다.

  • 플릿이 ①·②·⑦을 동시에 맡는다. 같은 양산차가 데이터 수집기이자 섀도 검증 장치이자 단계적 배포 대상이다. 로보택시형과 가장 다른 점이다.
  • 라이다가 없으므로 정답(④)을 카메라 다중 주행 재구성으로 만들어야 한다. 자동 라벨링에 GPU 4,000장을 따로 둔 이유다(2022) [보도·미확인].
  • 데이터 주권이 플라이휠을 지역별로 분리한다. 중국 도로 데이터를 미국으로 못 보내 상하이 데이터센터와 중국 내 학습 인프라를 따로 두었고, 중국 당국의 데이터 안전 검사를 외자 기업 최초로 통과했다 [보도] (Electrek 2026-02, 이투데이).

한계도 분명하다. 충돌 집계 방식이 정부 데이터와 달라 안전 통계의 독립 검증이 없고 [보도·미확인], 데이터·시뮬레이터·모델이 모두 비공개라 외부가 검증할 수 없다.

4.4 Waymo — 단일 파운데이션 모델로 운전·시뮬레이션·평가를 통합

단계 운영 방식 근거
①② 수집·저장 로보택시 플릿(2026년 3월 무인 누적 2억 2,060만 마일, 주 400만 마일 이상)의 카메라·라이다·레이더 로그 [보도] (Waymo)
③ 검색·큐레이션 "ML Factory" 슬라이드(그림 6): 센서 로그 → 데이터 마이닝·능동학습으로 선별 [보도]
④ 라벨링 라이다 시퀀스 전체를 쓰는 3D 자동 라벨링(CVPR 2021)이 사람 라벨과 대등. 초기 사람 라벨링에서 자동 라벨링으로 이동 [보도] (Scale 블로그)
⑤ 학습 Waymo Foundation Model(Gemini 계열 기반)을 크기 제한 없는 "교사"로 학습시키고, 차에 실을 "학생" 모델로 증류 [보도] (Waymo 블로그 2025-12)
⑥ 시뮬 검증 같은 파운데이션 모델이 시뮬레이터(Genie 3 기반 Waymo World Model, 카메라·라이다 동시 생성)와 평가자(Critic)의 바탕. Carcraft 하루 800만~1,000만 마일, 새 소프트웨어마다 전체 시나리오 재실행, 사고 시나리오 fuzzing [보도]
⑦⑧ 실차·배포 테스트 트랙 + 실도로 → 도시 단위 롤아웃. 플릿 통계를 안전 허브와 동료 심사 논문으로 공개(중상·사망 충돌 94% 감소 등) [보도]

구조의 특징은 세 가지다.

  • "운전자·시뮬레이터·평가자가 같은 모델"이라는 설계다. 한 모델이 좋아지면 ⑤·⑥·⑧의 평가가 함께 좋아지며, Waymo는 이를 "지속적 선순환(flywheel)"이라고 부른다 [보도].
  • 플릿은 작지만 센서 밀도가 높다. 라이다가 있어 3D 정답을 만들기 쉽고, 플릿 규모(Tesla의 1/60 수준)는 시뮬레이션(실주행 2,000만 vs 시뮬 200억 마일)으로 보충한다 [보도].
  • 공개도가 가장 높다. Waymo Open Dataset·WOD-E2E·안전 케이스 백서·안전 허브를 냈고 [보도], 2026년 8월에는 한국 사고·사건 장면을 가명 처리해 국외로 가져가는 절차를 개인정보위에 문의했다 [보도] (머니투데이 2026-08).

4.5 현대차그룹 — 그룹 내 분업과 이중 트랙

2026년 9월 11일 미디어데이에서 현대차그룹은 "차량에서 실제 주행 데이터를 확보하고 이를 AI 모델 학습과 검증에 활용한 뒤, 개선된 AI 모델을 다시 차량에 적용해 새로운 데이터를 확보하는 선순환 구조"를 자율주행 전략의 핵심 엔진으로 선언했다 [보도] (현대차그룹, 오토일렉트로닉스, 네이트 뉴스). 공개된 범위에서 단계별 운영 방식은 다음과 같다.

단계 운영 방식(공개된 범위) 담당 근거

구조의 특징은 세 가지다.

  • 단계별로 담당 주체가 다른 "그룹 내 분업"이다. 42dot은 모델·선별, 현대모비스는 센서·HIL 검증, NVIDIA는 양산 플랫폼·검증 도구, Motional은 로보택시 데이터의 별도 루프를 맡는다. Tesla처럼 한 조직이 9단계를 쥔 구조가 아니다.
  • 플라이휠이 두 개 병렬로 돈다(NVIDIA 트랙 2028, Atria 트랙 2029). 두 트랙의 데이터가 한 저장소로 합쳐지는지, 라벨링·검색 도구가 자체인지 외부인지는 공개 자료에 없다 [미확인].
  • 출발 시점이 다르다. 현재 수집 차량은 테스트 차량 위주이고 양산차 탑재는 2026년 말부터다. 700만 대 판매망은 "잠재력"이지 아직 플릿이 아니며, 국내 원본 영상 학습은 규제 샌드박스 승인에 묶여 있다(5.5절).

5. 데이터 플라이휠의 진화, 병목과 해법, 향후 진화 방향

이 장의 질문

플라이휠은 지금까지 어떻게 바뀌어 왔고, 지금은 어디서 막히며, 그 병목을 회사들은 어떻게 풀고 있고, 다음 5년은 어디로 가나.

세 줄 답
  1. ①2021년과 2026년의 플라이휠은 단계는 같고 부품이 바뀌었다. 사람이 짠 트리거는 임베딩 검색으로, 사람 라벨링은 파운데이션 모델 자동 라벨링으로, 로그 재생은 3D 재구성과 생성형 월드모델로, 모방학습은 폐루프 강화학습으로, 연 단위 릴리스는 주 단위 OTA로.
  2. ②병목은 네 곳이고 각각 해법이 있지만 완전한 해법은 없다. 데이터 발견(검색·생성으로도 "모르는 것을 모르는" 영역은 못 잡는다), 검증(시뮬레이터 자체를 검증해야 한다), 비용(온보드 선별 → 자동 라벨링 → 현지 학습 순), 규제(수집·배포·기록 세 단계를 직접 건드린다).
  3. ③방향은 월드모델 기반 검증의 규제 증거화, 학습된 시뮬레이터 안에서의 학습, 국경 안 데이터 공유, 에이전트형 개발, 파운데이션 모델 라벨링, "증거로서의 로깅"이고, 이 중 온보드에 걸리는 것이 차량 HPC 플랫폼의 설계 조건이 된다.

5.1 데이터 플라이휠의 진화 — 2021년 데이터 엔진에서 2026년 플라이휠로

플라이휠의 역사는 세 시기로 나눌 수 있다. 2010년대 후반에는 사람이 규칙을 쓰고, 학습 모델은 인지 일부에만 쓰였으며, 데이터셋은 한 번 모아 사람이 라벨링해 학습했다. 1.2절의 네 가지 한계(롱테일·분포 변화·성능 회귀·검증 한계)가 여기서 드러났다(이 시기 구분은 이 보고서의 요약이며 별도 출처는 없다 [미확인]). 2021년 전후에 루프가 생겼다. 사람이 조건을 코드로 쓴 트리거가 차에서 돌고, 걸린 클립을 올려 오프라인에서 자동 라벨링하고, 재학습해 섀도 모드로 배포한다. 2025~2026년에는 루프의 모양은 같지만 각 단계의 부품이 큰 모델과 클라우드 시뮬레이션으로 바뀌었다.

2021년 전후의 교과서는 Tesla AI Day의 데이터 엔진이다. 사람이 쓴 트리거가 차에서 돌고(①), 걸리면 약 10초 클립을 올리고(②), 오프라인에서 자동 라벨링하고(④), 다시 학습해(⑤) 섀도 모드로 내보낸다(⑦⑧). 당시 수치는 누적 100만 클립, 60억 개 객체 라벨, 1.5PB, 주당 1만 클립 자동 라벨링이었다 [보도] (CleanTechnica, Electrek).

2026년의 플라이휠은 단계는 같고 부품이 바뀌었다. 아래 표의 "단계" 열은 2.2절의 번호(①~⑨)이고, 각 행은 그 단계에서 쓰는 부품이 어떻게 바뀌었는지다.

2.2절 단계 역할 2021년 전후 2025~2026년 변화
①③ 고칠 상황 찾기 플릿이 겪은 수백만 장면 중 모델이 틀린 상황과 그 비슷한 장면을 찾아내는 일 사람이 조건을 코드로 쓴 트리거(Tesla 221개)로 차 안에서 걸러 낸다 [보도] 임베딩 검색: 영상마다 내용을 요약한 숫자 목록(임베딩)을 붙여 두면 뜻이 비슷한 영상은 숫자도 비슷해진다. "비 오는 밤 공사 구간" 같은 글을 같은 방식으로 숫자로 바꿔 가까운 영상을 찾는다. NVIDIA Cosmos Dataset Search는 약 800만 영상으로 학습한 영상-텍스트 임베딩 모델(Cosmos-Embed1)을 쓴다 [보도]; Voxel51 FiftyOne [보도] 무엇을 찾을지 미리 코드로 정해 두지 않아도 되고, 트리거에 안 걸린 장면도 나중에 찾을 수 있다
④ 라벨링 영상에 정답(물체 위치·차선·궤적)을 붙이는 일 사람 라벨링 회사(Scale AI, 인력 24만 명) [보도]; Tesla는 2022년 자체 라벨팀 감원 [보도] 파운데이션 모델 자동 라벨링: NVIDIA Cosmos Curator가 "처리·주석·필터·중복 제거"를 맡고 [원문] (Cosmos README), Cosmos Reason 같은 시각언어모델이 "왜 이렇게 운전했나"까지 글로 붙인다 [보도] 라벨 비용이 사람 수가 아니라 GPU 시간에 비례
⑥ 장면 재현 기록된 상황을 다시 돌려 새 모델을 시험하는 일 로그 재생 + HIL(dSPACE 리플레이 시스템) [보도] 3D 재구성: Waymo Block-NeRF는 사진 280만 장으로 샌프란시스코 한 구역(0.5km²)을 35개 신경 모델로 재구성 [보도] (arXiv 2202.05263); NVIDIA NuRec은 3D 가우시안 스플래팅으로 주행 로그를 다시 걸어 다닐 수 있는 3D 장면으로 만든다 [보도] 기록된 그대로만이 아니라 "그때 왼쪽으로 꺾었다면"을 볼 수 있다
⑤⑥ 장면 생성 겪어 본 적 없는 상황을 만들어 학습·시험에 쓰는 일 사람이 시나리오 파일(OpenSCENARIO)을 작성 [보도] 생성형 월드모델: Wayve GAIA-3(150억 파라미터, 10배 데이터) [보도] (Wayve); Waymo World Model(Genie 3 기반) [보도]; NVIDIA Cosmos [보도] 본 적 없는 상황을 영상으로 만들어 낸다
⑤ 학습 모델을 고치는 일 기록된 주행을 흉내 내는 모방학습(개루프) 폐루프 강화학습·학습된 시뮬레이터: NVIDIA AlpaGym은 시뮬레이터 안에서 정책이 스스로 운전하며 배운다 [보도]; openpilot 0.11은 "학습된 시뮬레이터로 전량 학습" [원문] 모델이 자기 실수의 결과를 겪으며 배운다
⑥ 평가 새 모델이 좋아졌는지 재는 일 기록 궤적과의 거리(ADE/FDE 같은 규칙 지표) 사람 선호 지표: Waymo WOD-E2E의 RFS [보도]; LLM-as-judge(LLM 서비스 플라이휠) [원문] "기록과 같은가"에서 "사람이 보기에 좋은가"로
⑧ 배포 새 모델을 차에 내보내는 일 연 단위 대형 릴리스(Tesla v13 → v14까지 약 1년) [보도] 주 단위 OTA(v14.x는 1~2주 간격) [보도] (보도) 루프 한 바퀴가 짧아짐

바뀐 부품들의 공통점은 하나다. 사람이 하던 일(트리거 작성, 라벨링, 시나리오 작성)을 큰 모델이 대신하고, 실차로만 하던 일(재현, 검증)을 클라우드가 대신한다. 그래서 한 바퀴의 병목이 "인력"에서 "GPU와 데이터 파이프라인, 그리고 시뮬레이션을 얼마나 믿을 수 있는가"로 옮겨갔다. 플라이휠을 평가하는 기준은 세 변수로 요약된다 — 한 바퀴를 얼마나 자주(주기), 얼마나 싸게(바퀴당 비용), 얼마나 믿을 수 있게(검증 신뢰도) 돌리느냐. 다음 네 절의 병목은 이 세 변수 중 하나 이상을 막는 곳이고, 각 해법도 같은 기준로 평가하면 된다.

5.2 병목 ① 데이터 발견 — 무엇이 필요한지 모른다

정의. 가장 어려운 데이터는 "아직 본 적 없어서 찾을 줄도 모르는" 데이터다. ISO 21448(SOTIF)은 이를 "모르는 불안전 시나리오(영역 3)"라고 부르고, 이 영역을 합리적 노력으로 최대한 줄이는 것을 표준의 핵심으로 둔다 [보도] (TÜV SÜD 백서).

원인. 희소성은 숫자로 드러난다. Waymo는 수억 마일 플릿에서 발생 빈도 0.03% 미만 상황을 골랐는데 12시간 분량이었다 [보도]. 플릿이 아무리 커도 드문 조합은 몇 번 안 나온다. 트리거는 "미리 정한 조건"이므로 정하지 않은 상황은 걸리지 않고, 불확실성 기반 능동학습도 초기 라벨 집합에 아예 없는 클래스("unknown unknown")를 잡지 못한다 [보도] (해설).

해법 대상 비용·조건 한계
임베딩·자연어 검색(3.2절) "알지만 못 찾은" 장면 — 트리거에 안 걸렸지만 비슷한 장면 플릿 영상 전체를 임베딩해 두는 GPU 비용(Cosmos Curator 기준 2,000만 시간에 Blackwell 14일 [보도]) 검색어를 아는 상황만 찾는다

생성형 월드모델(3.3절) "본 적 없는" 조합 — 플릿이 못 본 상황을 만들어 시험 월드모델 학습·추론 비용, 만든 장면의 현실성 검증(5.3절) 무엇을 만들지는 여전히 사람이 정한다

기업 사례. Tesla는 트리거 221개와 섀도 모드에 더해 틀린 사례를 단위 테스트로 남기고 비슷한 사례를 플릿에서 회수(boost)한다 [보도]. NVIDIA는 모델 앙상블의 불일치로 고른 데이터가 수동 선별보다 야간 보행자 3배·자전거 4.4배 개선됐다고 보고했고(연구), Cosmos Dataset Search로 글 검색을 제공한다 [보도·원문]. 현대차그룹은 Hard Example Mining으로 오인식·판단 곤란 상황을 자동 선별한다 [보도]. Waymo는 World Model의 목적에 "플릿이 직접 관찰한 적 없는 상황 탐색"을 명시하고, WOD-E2E로 0.03% 미만 상황만 모은 데이터셋을 공개했다 [보도]. Voxel51은 페타바이트급 플릿 로그에서 임베딩·자연어 검색으로 엣지 케이스를 캐는 도구를 판다 [보도].

요약하면 검색은 "알지만 못 찾은" 데이터를, 생성은 "본 적 없는" 데이터를 겨냥한다. 둘 다 "무엇을 모르는지 모르는" 영역은 못 잡으므로, 월드모델의 놀람 신호 같은 발견 기법이 다음 과제다. 온보드에서 후보 모델을 같이 돌리는 섀도·불일치 트리거는 차량 HPC 자원에 걸린다(5.6절).

5.3 병목 ② 검증 — 시뮬레이션을 얼마나 믿을 수 있나

정의. 시뮬레이션이 검증의 주 수단이 됐지만(2.3절 차이 5), 시뮬레이션에서 좋은 점수가 도로에서의 안전으로 이어진다는 보장이 없다. 시뮬레이터 자체를 검증해야 하는 문제다.

원인. 개루프 점수는 허약하다. nuScenes 개루프 평가에서 카메라·라이다 없이 과거 궤적만 외삽해도 최신 모델을 이기는 사례가 보고됐다 [보도]. 정적 데이터셋 점수가 도로 안전과 다른 것을 재고 있다는 뜻이다. 재구성·생성 장면은 기록 범위 밖에서 품질이 떨어지고, 생성 장면은 물리적으로 그럴듯한지 따로 확인해야 한다(3.3절). 그리고 2026년 5월 Bench2Drive-Robust는 프레임 드롭·GPS 잡음·추론 지연 같은 "배포 교란"이 폐루프 성능을 크게 떨어뜨리는데 기존 이미지 손상 평가로는 잡히지 않는다고 보고했다 [보도] (arXiv 2605.18059).

규제는 시뮬레이션 증거를 조건부로 받는다. UN R157(자동 차선 유지) 부속서 4는 시험장·실도로에서 재현하기 어려운 시나리오에 시뮬레이션 사용을 허용하되, 제조사가 도구의 범위·해당 시나리오의 유효성·물리 시험과의 상관을 입증하도록 한다 [보도] (TÜV SÜD 해설). EU의 완전자동화차량 형식승인 규정 2022/1426은 시나리오 기반 평가와 가상 시험을 허용하고 "시뮬레이션 기반 시험의 신뢰성 평가" 지침을 담는다(조문 원문 미확인 [미확인]) [보도]. 미국은 2026년에 AV 프레임워크 갱신·FMVSS 개정안·Zoox 면제로 "규제 장벽 제거" 방향이다 [보도].

기업 사례. Waymo는 새 소프트웨어마다 전체 시나리오를 재실행하고 사고 시나리오를 fuzzing하며, 기준 모델(NIEON) 대비 회피율을 비교하고, 플릿 통계(안전 허브)로 시뮬 결과를 실도로 결과와 맞춘다 [보도]. Tesla는 여러 라운드의 섀도 배포로 시뮬 대신 실제 운전자·환경에서 대조하고 플릿 0.1% 미만부터 단계적으로 확대한다 [보도·미확인]. Wayve는 GAIA-3를 검증용으로 외부에 제공해 시뮬레이터 자체를 검증받는 방향이고 "합성 테스트 기각률 5배 감소"를 주장한다 [보도·미확인]. 현대차그룹·모비스는 실주행 데이터를 3D로 재구성해 위험 상황을 재현하고 모비스 HIL(60대 계획)로 실차 센서 데이터와 대조한다 [보도·미확인]. NVIDIA는 AlpaSim(센서 렌더러·정책·물리·평가 분리)과 Cosmos Evaluator(물리 정확성 자동 점수)로 생성 장면의 현실성을 채점한다 [보도·원문]. 학계의 2025년 12월 자율주행 테스트 서베이는 "코너 케이스 다양성, 시뮬–실제 격차, 체계적 기준 부재, 파운데이션 모델 테스트 비용"을 미해결로 지목한다 [보도] (arXiv 2512.11887).

요약하면 시뮬레이션은 증거가 될 수 있지만, 시뮬레이터 자체를 검증했다는 증거를 함께 내야 한다. 월드모델 기반 검증이 규제 증거로 인정받으려면 R157 부속서 4의 "도구 검증" 요건이 관문이다(5.6절).

원인. 원본 데이터 양이 통신·저장 비용을 밀어 올리고(3.1절), 라벨링은 사람 수에 비례했으며, 클라우드에서 데이터를 꺼낼 때마다 반출비가 붙는다. 데이터 주권 규제(5.5절)는 지역별로 인프라를 중복시킨다.

해법과 절감 순서. 첫째, 온보드 선별(3.1절)이다. 올리지 않은 데이터는 저장·반출·라벨링 비용이 모두 0이므로 가장 싼 절감이다(openpilot 두 단계 업로드 [원문], Mobileye km당 10KB [보도]). 둘째, 자동 라벨링(3.2절)이다. 라벨링이 사람 수에서 GPU 시간으로 옮겨가며, Bosch의 "3D 박스당 최대 70% 절감" 주장이 맞다면 남는 비용은 검수 인력과 GPU다 [보도·미확인]. 셋째, 반출 최소화·현지 학습이다. 1PB 반출이 약 9만 달러이므로 데이터가 있는 곳에서 학습하면 반출비와 규제 비용을 함께 줄인다 [보도] (CloudZero). 넷째, 증류·재구성으로 GPU 효율화다. 교사 모델은 한 번 학습하고 학생만 자주 학습하며, InstantNuRec은 장면 재구성을 약 1.5초로 줄였다 [원문·보도].

기업 사례. comma.ai는 요약 로그·저화질 영상을 우선 올리고 원본은 서버 지목 시에만 올려 마일당 $0.003 미만으로 서비스 비용을 맞춘다 [원문·보도]. Mobileye는 원본 영상을 올리지 않고 의미 정보만 km당 10KB로 전송한다 [보도]. Tesla는 2022년 사람 라벨팀을 감원하고 자동 라벨링(GPU 4,000장)으로 옮겼으며, 중국 데이터는 상하이에서 현지 학습한다 [보도·미확인]. 비용 최적화의 순서는 온보드 선별 → 자동 라벨링 → 반출 최소화(현지 학습)다. 이는 3.1절의 두 단계 업로드와 5.5절의 데이터 주권 대응과 같은 방향이며, 첫 항목은 차량 HPC 플랫폼의 로깅·압축 설계에 걸린다(5.6절).

    • 원인: 드문 상황은 플릿이 커도 몇 번 나오지 않고, 트리거는 미리 정한 조건만 포착한다.
    • 해법: 알지만 못 찾은 장면은 임베딩 검색으로 회수하고, 본 적 없는 장면은 월드모델로 생성하며, 두 모델의 판단이 갈리는 순간은 섀도·불일치 트리거로 포착한다.
    • 남는 과제: 무엇을 모르는지 모르는 영역. 월드모델의 예측 실패를 희소 사건의 신호로 쓰는 연구가 진행 중이다.
    • 대표 사례: Tesla 트리거·섀도 모드, 현대차그룹 Hard Example Mining, NVIDIA 앙상블 불일치 선별, Waymo WOD-E2E.
  • 병목 ② 검증(5.3절)
    • 문제: 시뮬레이션 점수가 높아도 도로에서 안전하다는 보장이 없다. 시뮬레이터 자체를 검증해야 한다.
    • 원인: 개루프 점수는 안전과 다른 것을 재고, 재구성·생성 장면은 기록 범위 밖에서 품질이 떨어지며, 프레이다 드롭·추론 지연 같은 배포 교란이 성능을 떨어뜨림.
    • 해법: 단계적 검증(개루프 → 폐루프 → 사람 선호 → 회귀 세트 → HIL → 섀도 → 단계적 OTA), 시뮬 결과와 실차·HIL 결과의 대조, 시뮬레이터의 재현 범위·유효성 입증.
    • 규제: UN R157은 시뮬레이션 증거를 허용하되 도구 검증을 요구한다. 월드모델 검증이 규제 증거가 되려면 이 관문을 통과해야 한다.
    • 대표 사례: Waymo 전체 시나리오 재실행·사고 재구성 fuzzing, Tesla 단계적 섀도 배포, 현대모비스 HIL 60대 계획, NVIDIA AlpaSim·Cosmos Evaluator.
  • 병목 ③ 비용(5.4절)
    • 문제: 통신·저장·반출·라벨링·GPU 비용의 합이 한 바퀴의 비용이다. 1PB 반출에 약 9만 달러, 교차로 프레이다 라벨 하나에 약 4.84달러.
    • 원인: 원본 데이터 양이 통신·저장비를 올리고, 라벨링은 사람 수에 비례하며, 데이터 주권 규제가 인프라를 지역별로 중복시킴.
    • 해법(절감 순서): 온보드 선별(올리지 않은 데이터는 비용 0) → 자동 라벨링(사람 → GPU) → 반출 최소화·현지 학습 → 증류·재구성으로 GPU 효율화.
    • 대표 사례: comma.ai 요약본 우선 업로드(마일당 0.003달러 미만), Mobileye km당 10KB, Tesla 자동 라벨링·상하이 현지 학습. 반대 사례는 VW·Bosch의 15억 유로 투자 후 종료.
  • 병목 ④ 규제와 데이터 주권(5.5절)
    • 문제: 규제가 수집(개인정보·국외 반출), 배포(UN R156 SUMS), 기록(R157 DSSAD·EDR)의 세 단계를 직접 제약한다.
    • 원인: 얼굴·번호판을 가리면 학습 정보가 사라지고, 국경을 넘지 못하면 지역마다 인프라가 필요하며, 업데이트마다 인증 절차가 붙는다.
    • 지역별 요지: EU는 Data Act·AI Act(2028-08로 연기), UNECE는 R155·R156·R157, 중국은 국외 이전 가이드라인(2026-01), 한국은 원본 영상 규제 샌드박스(2026-01), 미국은 배포 장벽 완화.
    • 해법: 차내 처리·요약 전송, 샌드박스·법제화, 지역별 인프라, SUMS 프로세스 내장, 개발용·규제용 로깅 통합.
    • 대표 사례: Tesla 상하이 데이터센터, Mercedes·BMW 지역별 공급 분할, Mobileye REM, 한국 9개사 샌드박스 신청.
  • 네 병목의 공통점: 해법이 모두 차 안 설계에 걸림. 섀도·불일치 트리거(①), HIL 재생(②), 온보드 선별(③), 규제 기록·OTA 관리(④)는 차량 HPC 플랫폼의 요구 사항이다.
  • 향후 방향(5.6절) — 성숙도 순
    • 이미 의무: 로깅의 규제 증거화. 개입·전환 요구 같은 사건을 개발용 트리거와 규제용 기록이 함께 기록한다.
    • 양산 진입: 월드모델 기반 검증(Wayve GAIA-4, Waymo World Model, XPeng X-World). 규제 증거가 되려면 도구 검증이 필요한다.
    • 초기 양산: 학습된 시뮬레이터 안에서 직접 학습한 모델의 배포. comma.ai 0.11이 첫 공개 사례이고 NVIDIA AlpaGym·Momenta R7·Waymo 교사-학생 구조가 뒤따른다.
    • 도구 공개: 파운데이션 모델의 라벨링 대체(VLM 자동 라벨링). 검수 인력은 남는다.
    • 실험·주장 단계: 플릿 간 데이터 공유(TIER IV Co-MLOps, Catena-X), AI 에이전트의 플라이휠 운영.
    • 우선순위: 로깅 통합 → 월드모델 검증 → 학습된 시뮬레이터 순.
  • 차량 HPC 플랫폼에 필요한 것(5.6.2절)
    • 지금: 섀도 실행 자원, 선별·압축·두 단계 로깅, 규제 기록의 무결성, HIL 재생 호환, OTA 관리 프로세스.
    • 앞으로: 온디바이스 큐레이션 연산, 증류 모델의 실행과 안전 감시, 지역별 모델·데이터 변형 관리.
시사점

네 병목은 서로 다른 문제처럼 보이지만 해법의 위치는 같는다. 차 안에서 무엇을 고르고, 무엇을 기록하고, 무엇을 내보낼지를 정하는 온보드 설계가 플라이휠의 시작과 끝을 결정한다.

용어 풀이

  • 데이터 플라이휠: 서비스를 쓰면서 나온 데이터로 모델을 고치고, 고친 모델이 더 좋은 데이터를 만드는 반복 구조. 자율주행에서는 "데이터 엔진", "폐쇄루프"라고도 부른다.
  • 종단간(end-to-end, E2E): 카메라 영상이 들어가면 조향·제동이 바로 나오는 하나의 학습 모델. 중간에 사람이 짠 규칙이 없다.
  • 롱테일(long tail): 각각은 드물지만 종류가 무한히 많은 예외 상황. 빈도 그래프의 긴 꼬리.
  • 분포 변화(distribution shift): 학습할 때 본 상황의 분포와 실제로 만나는 상황의 분포가 다른 것. 도시·날씨·나라가 바뀌면 생긴다.
  • 파국적 망각(catastrophic forgetting): 새 데이터로 다시 학습한 모델이 예전에 잘하던 것을 잊는 현상.
  • 트리거(trigger): 차 안에서 "이 순간의 데이터를 저장·업로드하라"고 판단하는 조건. 규칙, 모델 점수, 사람 버튼이 있다.
  • 섀도 모드(shadow mode): 새 모델을 차에 싣되 제어권은 주지 않고, 그 판단을 기록해 현행 모델·운전자와 비교하는 방식.
  • 자동 라벨링(auto-labeling): 클라우드의 큰 모델이 미래 프레임과 여러 주행을 합쳐 정답(3D 박스·차선·점유·궤적·장면 설명)을 만드는 것. 사람은 검수만 맡는다.
  • LLM 서비스: 대형 언어 모델(LLM)을 서버에서 돌려 제공하는 챗봇·음성 에이전트·사내 지식 비서 같은 서비스. 이 보고서에서 차량 플라이휠의 비교 대상.
  • 임베딩(embedding) / 임베딩 검색: 영상이나 글의 내용을 요약한 숫자 목록. 뜻이 비슷하면 숫자도 비슷하게 나오도록 학습해 두므로, 글로 검색어를 넣어 숫자가 가까운 영상을 찾을 수 있다.
  • Hard Example Mining: 모델이 틀리거나 판단을 어려워한 상황을 자동으로 골라 우선 학습에 쓰는 기법. 현대차그룹이 플라이휠의 선별 기술로 명시했다.
  • 교사-학생 증류(distillation): 크기 제한 없는 큰 모델(교사)을 먼저 학습시키고, 차에 실을 작은 모델(학생)이 그 출력을 따라 배우게 하는 방법.
  • SUMS / UN R156: 소프트웨어 업데이트 관리체계. 제조사가 업데이트 관리 체계를 인증받고, 버전마다 식별 번호(RxSWIN)를 붙이며, 호환성 확인·안전 설치·기록을 요구하는 UN 규정.
  • 재생 / 재구성 / 생성: 합성 데이터의 세 갈래. 기록을 그대로 틀기 / 기록을 3D로 복원해 다른 시점에서 보기 / 조건을 주고 없던 영상을 만들기.
  • 3D 가우시안 스플래팅(3DGS): 장면을 수백만 개의 작은 타원체(가우시안)로 표현해 빠르게 다시 그리는 3D 재구성 기법.
  • 월드모델(world model): 지금 장면과 행동을 주면 다음 장면을 예측·생성하는 모델. 시뮬레이터로 쓰인다.
  • 개루프 / 폐루프 평가: 기록 궤적과의 거리만 재기 / 시뮬레이터 안에서 실제로 운전시켜 결과를 재기.
  • PDMS / RFS: NAVSIM의 유사 폐루프 점수 / Waymo의 사람 평가자 선호 점수.
  • HIL(Hardware-in-the-Loop): 실제 제어기(ECU)에 기록·합성 센서 데이터를 주입해 시험하는 방법.
  • OTA(Over-the-Air): 무선으로 차량 소프트웨어를 갱신하는 것. UN R156이 관리 방식을 규정한다.
  • DSSAD / EDR: 자율주행 시스템의 켜짐·꺼짐·개입을 기록하는 장치 / 사고 순간 데이터를 기록하는 장치.
  • SOTIF(ISO 21448): 고장이 없어도 기능의 한계 때문에 생기는 위험을 다루는 안전 표준.
  • RxSWIN: UN R156이 요구하는 형식승인 관련 소프트웨어 식별 번호.

규제·표준 용어 — 2.3절 차이 3·4·6, 3.4절, 5.3절, 5.5절에 나오는 규정과 표준.

  • 형식승인(type approval): 차량이나 시스템이 규정 요건을 충족함을 당국이 승인하는 절차. UNECE 협정 체약국(64개국)은 UN 규정을 공통으로 적용한다. 소프트웨어 업데이트가 인증 기능에 영향을 주면 재승인 대상.
  • UN R155 / CSMS: 차량 사이버보안 관리체계 규정. 제조사가 사이버보안 관리 체계를 인증받아야 하며 2024-07부터 EU 신차 전체에 적용. R156과 함께 OTA 경로의 보안 조건이 된다.
  • UN R157 / ALKS: 자동 차선 유지 시스템(레벨 3) 규정. 자율주행 기록 장치(DSSAD) 탑재를 의무화하고, 부속서 4에서 시험장·실도로로 재현하기 어려운 시나리오에 시뮬레이션 사용을 허용하되 제조사가 도구의 재현 범위·시나리오 유효성·물리 시험과의 상관을 입증하도록 요구함("도구 검증").
  • ISO 26262: 자동차 기능 안전 표준. 전기·전자 부품의 고장으로 생기는 위험을 다룸. 성능 한계로 생기는 위험(SOTIF)이나 AI 부품(ISO/PAS 8800)은 별도 표준이 맡는다.
  • ISO/PAS 8800: AI 부품을 포함한 도로 차량의 안전 표준(2024). 학습 데이터·모델·검증을 안전 논증에 포함하도록 요구한다. 모델을 교체하면 안전 논증을 갱신해야 하는 근거.
  • UL 4600: 자율주행 제품의 안전 케이스 표준. 분석·시뮬레이션·시험장·공도 시험을 조합해 안전을 논증하고, 업데이트마다 논증을 갱신하도록 한다.
  • 안전 케이스(safety case): "이 시스템은 이 조건에서 충분히 안전하다"를 근거와 함께 문서로 논증한 것. 배포 전 안전 인증의 산출물이며, 모델 교체마다 갱신 대상.
  • EU 2022/1426: EU 완전자동화차량(레벨 4) 형식승인 규정. 시나리오 기반 평가와 가상 시험을 허용하고 레벨 3 이상의 데이터 저장을 요구함(조문 원문 미확인 [미확인]).
  • EU Data Act: EU 데이터법. 2025-09-12 적용, 2026-09-12부터 설계 의무. 차량 사용자가 자기 차의 데이터에 접근하고 제3자에게 제공할 수 있도록 제조사에 의무를 지움.
  • EU AI Act 부속서 I: EU 인공지능법 가운데 형식승인 대상 안전 부품의 AI를 고위험으로 분류하는 부분. 해당 의무의 적용은 2028-08-02로 12개월 연기된다.
  • GDPR / EDPB 가이드라인 1/2020: EU 개인정보보호규정 / EU 개인정보 감독기구(EDPB)의 커넥티드카 가이드라인. 차량 데이터 대부분을 개인정보로 보고, 차량 외부의 사람·번호판을 별도 항목으로 다루며 차내 처리를 권고한다.
  • NHTSA SGO 2021-01: 미국 도로교통안전국의 상시 일반 명령. 자동화 시스템 작동 중 충돌을 보고하도록 의무화. 배포 장벽이 완화돼도 유지되는 의무.
  • FMVSS: 미국 연방 자동차 안전 기준. 핸들·페달 같은 장치를 전제로 하므로 핸들 없는 차량은 면제나 개정이 필요함(2026-03 개정안, 2026-07 Zoox 면제).
  • 중국 자동차 데이터 국외 이전 보안 가이드라인(2026판): 2026-01-30 8개 부처 시행. 연구개발·자율주행·소프트웨어 업그레이드 시나리오별로 중요 데이터를 식별하고, 국외 이전 시 보안 평가·표준 계약·인증을 요구하며 로그를 3년 보관하도록 한다.

종합 시사점

  • 플라이휠은 선택이 아니라 전제 조건임
    • 주행 소프트웨어가 학습 모델이 된 순간, 모델은 데이터로만 고칠 수 있다. 롱테일·분포 변화·성능 회귀·실도로 검증 한계는 한 번 수집해 한 번 학습하는 방식으로는 풀리지 않음(1장).
    • 용어(플라이휠·데이터 엔진·폐쇄루프)는 달라도 구조는 같는다. "운용 중 생성된 데이터를 다시 학습에 쓰고, 이를 반복한다"가 공통 정의다.
  • 차량 플라이휠의 과제는 속도가 아니라 관문 통과임
    • LLM 서비스 플라이휠의 과제는 반복 속도이지만, 차량 플라이휠은 안전 인증·규제 관문을 통과하면서 반복을 유지해야 함(2장). 차량 고유 단계 네 개(온보드 선별·시뮬레이션 검증·실차 검증·안전 관문)는 모두 관문이다.
    • 따라서 LLM 서비스의 "98.6% 비용 절감" 같은 수치를 자율주행에 그대로 옮길 수 없다.
  • 핵심 기술의 공통 방향은 "사람이 하던 일을 큰 모델이, 실차로 하던 일을 클라우드가" 대신하는 것임
    • 온보드 선별은 가장 싼 비용 절감 수단이다. 올리지 않은 데이터는 저장·반출·라벨링 비용이 모두 0임(3.1절).
    • 라벨링 비용은 인력에서 GPU 시간으로 이동하되 검수 인력은 남는다. 드문 물체일수록 검수 비율을 높여야 함(3.2절).
    • 합성 데이터는 재생 → 재구성 → 생성으로 갈수록 없던 상황을 만들 수 있지만 현실과의 격차 검증 부담이 커진다(3.3절).
    • 검증은 단계적으로 범위를 넓혀야 하며, 마지막 단계(OTA)는 규제 절차이므로 개발 파이프라인과 인증 산출물을 함께 설계해야 함(3.4절).
    • 단계별 처리량은 공개돼 있으나 한 바퀴의 소요 시간은 어느 회사도 공개하지 않는다. 자사 플라이휠을 설계할 때는 이 "한 바퀴 시간"을 직접 측정해야 함(3.5절).
  • 기업 간 차이는 유형이 아니라 "누가 어느 단계를 쥐는가"에서 드러남
    • 어느 회사도 온보드 선별·학습·배포 책임을 외부에 맡기지 않고, 검색·라벨링·시뮬 도구는 사거나 열어 씀(4장).
    • 운영 유형(자사 양산 플릿 / 자사 로보택시 / 파트너 플릿 기반 모델 공급 / 도구·플랫폼 공급)은 출발점이고, 데이터가 누구 차에서 생겨 누구에게 돌아가는가가 라벨링 방식·시뮬레이션 비중·배포 주기를 정한다.
    • 후발 주자의 선택지는 셋이다. 플릿을 빨리 키우거나, 센서를 두껍게 하고 시뮬레이션으로 보충하거나, 공급자의 플라이휠에 플릿을 제공하고 모델을 받는 것.
    • 2026년 동향의 무게중심은 월드모델, 데이터 주권 규제, 규제 관문의 변화 세 곳이다.
  • 병목은 네 곳이고, 해법의 위치는 모두 차 안임
    • 플라이휠을 평가하는 기준은 한 바퀴를 얼마나 자주, 얼마나 싸게, 얼마나 믿을 수 있게 돌리느냐의 세 변수임(5.1절).
    • 데이터 발견: 검색은 "알지만 못 찾은" 데이터를, 생성은 "본 적 없는" 데이터를 겨냥한다. "무엇을 모르는지 모르는" 영역은 미해결 과제임(5.2절).
    • 검증: 시뮬레이션은 증거가 될 수 있지만 시뮬레이터 자체를 검증했다는 증거를 함께 내야 한다. UN R157 부속서 4의 도구 검증 요건이 관문임(5.3절).
    • 비용: 절감 순서는 온보드 선별 → 자동 라벨링 → 반출 최소화·현지 학습임(5.4절).
    • 규제: 사후 대응이 아니라 아키텍처 조건이다. 수집 단계는 무엇을 차 밖으로 내보낼지, 배포 단계는 얼마나 자주 바꿀 수 있는지, 기록 단계는 무엇을 남길지를 정함(5.5절).
  • 향후 방향의 우선순위는 로깅 통합 → 월드모델 검증 → 학습된 시뮬레이터 순임
    • 로깅의 규제 증거화는 이미 의무이고, 월드모델 검증은 양산에 들어갔으며, 학습된 시뮬레이터 안 학습은 첫 양산 사례가 나왔다. 플릿 간 공유와 에이전트 운영은 아직 주장 단계임(5.6절).
  • 플라이휠은 클라우드만의 일이 아님
    • 첫 단계(선별·섀도)와 마지막 단계(OTA·규제 기록)는 차 안에 있다. 차량 HPC 플랫폼은 지금 다섯 가지(섀도 실행 자원, 두 단계 로깅, 규제 기록 무결성, HIL 재생 호환, OTA 관리 프로세스)를 갖춰야 하고, 앞으로 세 가지(온디바이스 큐레이션, 증류 모델 감시, 지역별 변형 관리)가 더해짐(5.6절). 이를 지원하지 않으면 플라이휠의 시작과 끝이 막힘.
  • 이 보고서의 한계
    • 기업 수치는 대부분 공개 주장이며, 원문 접근이 막힌 사실은 검색 요약([보도]) 기준이다. 미확인 항목 20개는 부록 B에 모아 두었는다. 한 바퀴 소요 시간, 라벨 검수 비율, 각 사의 데이터 회수 범위는 공개 자료로 확인되지 않는다.
