1. 배경

왜 중앙집중형 HPC가 필수가 됐나

레벨AI 연산 요구 (업계 통용 추정치)비고
L2< 10 TOPS실질 2–2.5 TOPS 사례도
L320–30 TOPSeyes-off 진입
L4200–320+ TOPS도심 무인 주행
2025+ 플래그십500–2,000+ TOPS도심 NOA + E2E/VLA 헤드룸

데이터 중력

E2E/BEV 모델은 전 센서 raw 데이터를 한 곳에서 시간 동기화해 융합해야 성능이 나온다. 레이더 raw 중앙화 시 5대 합산 ~540MB/s.

E2E 모델의 단일성

단일 신경망은 기능 분산이 불가능 — 모델 하나가 하나의 큰 가속기 메모리 공간을 요구 (FSD v13 주행 모델 추정 ~7.5GB).

L3 법적 책임 → 이중화

eyes-off부터 제동·조향·전원·컴퓨트 이중화가 인증 요건. "고성능 컴퓨터 2계통"에서만 비용이 성립.

⚠️ TOPS는 필요조건이지 충분조건이 아님 — Mobileye EyeQ6H는 34 TOPS 칩 2개로 hands-off(SuperVision) 전체 스택을 구동. 아키텍처 효율과 활용률이 실성능을 결정.

출처: Huawei MDC, Nevsemi 2025, NVIDIA Centralized Radar Processing, Mercedes-Benz redundancy, Mobileye benchmark — 상세 링크는 material.md

3. 모델 트렌드

BEV → Occupancy → End-to-End

BEV + Transformer

멀티카메라를 통합 BEV 표현으로. BEVFormer 기본 ~130ms → TensorRT FP16 ~90ms. deformable attention의 불규칙 메모리 접근은 NPU 비친화적 — HW 지향 재설계 연구 존재(HotBEV, Fast-BEV).

Occupancy Network

비정형 장애물을 3D voxel 점유로 표현. Tesla FSD 컴퓨터에서 ~10ms 실시간 추론. dense 3D 출력 → 메모리 사용량이 큼.

End-to-End

UniAD(CVPR 2023 Best Paper): 전 태스크를 단일 query 기반 Transformer로. Tesla FSD v12: 규칙 기반 C++ ~30만 줄 제거. v13: 모델 3× · 데이터 4.2× · 학습 컴퓨트 5×, 주행 모델 ~2.3GB → ~7.5GB(추정) — HW3 실행 불가 격차 발생.

💡 중국 OEM은 E2E 전면 전환 단계 — Momenta가 city-NOA 솔루션 60% 공급(2024), BMW 차세대 iX3(2026)에 E2E 대모델 탑재 예정. 모델 세대교체 주기가 하드웨어 수명보다 짧다 → 헤드룸 설계 필수.

출처: arXiv:2203.17270, arXiv:2303.01212, arXiv:2212.10156, Creative Strategies(FSD v13), Recode China AI

3. 모델 트렌드

VLA / World Model — "fast + slow" 이중 시스템이 표준

  • DriveVLM-Dual (Li Auto 실차): VLM 추론 평균 410ms → 10Hz 제어 루프에 못 들어가므로 slow-path로 격리. speculative decoding으로 decode 2.7× 가속.
  • XPeng VLA 2.0: 30B 파라미터 VLA를 로컬 실행 — Turing 칩 3개(2,250 TOPS). Volkswagen 라이선스 채택.
  • 노선 분화: VLA(XPeng·Li Auto) vs World Model(Huawei ADS 4.0 WEWA, MDC 1000). Waymo EMMA(Gemini 기반)는 연산 비용 과다로 아직 연구 단계.

출처: arXiv:2402.12289, XPeng 공식(2025-11), EEWorld(Huawei ADS 4.0), Waymo Blog(2024-10)

병목이 대역폭임을 보여주는 실리콘 방증

CNN perception

conv 커널 재사용률이 높아 arithmetic intensity(OPS/byte)가 높음 → MAC array(TOPS)가 병목.

LLM/VLA decode

batch-1 autoregressive: 매 토큰마다 전체 weight + KV cache를 DRAM에서 스트리밍 → 연산기가 놀고 step time이 대역폭으로 결정. attention은 matrix-vector 위주로 본질적 memory-bound.

💡 차기 플랫폼의 1차 차별화 요소는 TOPS가 아니라 DRAM 대역폭 · 온칩 SRAM · KV cache 처리 능력 · FP8/FP4 datapath.

4. 온보드 최적화

양자화 — 저정밀 포맷 전쟁: INT8 vs FP8 vs FP4

기법/포맷효과주의점
LiDAR-PTQ (ICLR 2024)INT8 PTQ, FP32 동급 정확도 + 3× 가속QAT 대비 30× 빠른 양자화 비용
Q-PETR8-bit PTQ <1% 열화, 2× 속도, 3× 메모리↓positional encoding 재설계 필요했음
NVFP4 (Blackwell)<1% 손실, FP8 대비 ~3× 처리량, 트래픽 절반FP4 네이티브 가속 없으면 dequant 병목으로 이득 소멸
W4A8처리량 최상위대형 모델 최대 22% 품질 손실 사례 — 태스크별 검증 필수
⚠️ Qualcomm AI Research: 전용 하드웨어에서 FP8 MAC은 INT8 대비 면적/에너지 효율 50–180% 열세 — NPU 진영(INT 중심) vs GPU 진영(FP 중심) 구도의 이론적 배경. 포맷 선택이 곧 실리콘 벤더 선택(lock-in)이 된다.
💡 이원화 진행 중: INT8 = 인지 모델의 안전한 기본값, FP8/FP4 = Transformer/LLM 워크로드의 새 기본값. DriveOS LLM SDK 레시피: weight/GEMM은 FP8·NVFP4, LayerNorm·KV cache·attention은 FP16 유지.

출처: arXiv:2401.15865, arXiv:2303.17951, NVIDIA NVFP4, arXiv:2508.16712

4. 온보드 최적화

구조적 희소성 · 지식 증류 · 효율적 아키텍처

2:4 Structured Sparsity

이론 2× — 실측은 LLM 1.40–1.44×, CNN sparse+INT8 ~1.7×. Orin DLA도 channel 2:4 sparsity를 HW 지원(105 TOPS INT8 sparse). "이론 2×, 실측 1.3–1.7×"로 보수적으로 계획할 것.

지식 증류 (KD)

LiDAR teacher → camera student: DistillBEV +3.9% mAP, SimDistill +4.8% — 센서 BOM 절감이 동기. Minitron: 15B→8B/4B pruning+증류, 학습 토큰 40× 절감. DeepSeek 증류 모델이 Geely·BYD 등 cockpit에 양산 탑재(2025).

Deployable by Design

Fast-BEV++: custom CUDA plugin 제거 → TensorRT-native 설계. Token pruning: FastDriveVLA가 visual token 3,249→812로 연산 ~7.5× 절감(주행 특화 — 일반 VLM용 pruning은 주행 시나리오에서 성능 저하). 실무 NAS = "타깃 NPU 지원 연산자 집합 안에서의 설계".

출처: LLMCBench, NVIDIA DLA SW, ICCV 2023 DistillBEV, arXiv:2407.14679, arXiv:2512.08237, arXiv:2507.23318

4. 온보드 최적화

온디바이스 LLM 추론 최적화와 컴파일러 스택

DriveOS LLM SDK (DriveOS 7)

  • TensorRT 기반 순수 C++ 경량 런타임
  • FP16/FP8/INT4(AWQ)/NVFP4
  • speculative decoding (TensorRT-LLM ~3×, EAGLE-3 최대 4.79×), KV caching, LoRA, dynamic batching
  • Li Auto 실차: OrinX에서 EAGLE 2.7× decode 가속

컴파일러가 실리콘 가치를 결정

  • ONNX Runtime + 벤더 EP = 공통 배포 계층 (자동 partitioning, CPU fallback)
  • Qualcomm SNPE → QNN/QAIRT 세대교체
  • Horizon: BPU + 자체 컴파일러 + 알고리즘 3축
  • XPeng: 자체 칩에 자체 컴파일러 재개발
💡 "모델 최적화의 절반은 컴파일러 문제" — 연산자 커버리지·양자화 툴체인 없는 NPU TOPS는 무의미. speculative decoding은 "작은+큰 모델 동시 상주"를, token pruning은 동적 텐서 shape 지원을 하드웨어·컴파일러에 요구한다. Thor는 MIG로 ADAS/cockpit 도메인 격리(FFI).

출처: NVIDIA DriveOS LLM SDK, Red Hat(EAGLE-3), Qualcomm docs, Horizon, NVIDIA Thor 블로그

6. 결론

HPC 설계 시사점 — 그리고 토론

  • ① memory-bound 시대: 사양의 1차 축은 TOPS가 아닌 DRAM 대역폭·온칩 SRAM·KV cache·FP8/FP4 datapath. 용량(모델 상주) + 대역폭(decode) + 연산(prefill)의 3축 균형.
  • ② 포맷 로드맵 = 워크로드 믹스: CNN 인지 중심 → INT8+INT4 / VLA·LLM 중심 → FP8/FP4 필수. per-block scaling 지원이 관건.
  • ③ Sparsity는 실측 1.3–1.7×로 보수적으로 반영.
  • ④ 이중 시간 스케일이 표준: 10Hz+ fast path + 1–2Hz slow path — 파티셔닝·QoS·격리 설계. 메모리 QoS로 LLM의 대역폭 폭식이 인지 deadline을 침해하지 않게.
  • ⑤ I/O 프런트엔드: 카메라 10대+ ×2Gbps + radar raw 4Gbps급 인입 흡수 (SerDes/이더넷 + ISP).
  • ⑥ p99 결정성 + mixed-criticality — 2회차(플랫폼·기능안전)에서 상세.
  • ⑦ 컴파일러 접점을 1일차부터: ONNX Runtime EP 등 표준 계층과의 통합 계획.
