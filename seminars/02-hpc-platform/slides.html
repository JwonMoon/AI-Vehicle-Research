3. SW 플랫폼

중앙 컴퓨트 위의 소프트웨어 — 혼합 스택이 현실

실무 스택 구도

  • Safety/vehicle-motion 파티션 → AUTOSAR Adaptive (POSIX·SOA·OTA 전제)
  • Zonal MCU → AUTOSAR Classic (정적 스케줄, 하드 RT)
  • IVI → AAOS/Linux
  • AD 스택 → 전용 미들웨어 (DriveOS, Apex.Grace 등)

ROS 2의 양산 경로

  • Apex.Grace: ROS 2 fork를 TÜV Nord ISO 26262 ASIL-D SEooC 인증, zero-copy(iceoryx)
  • Autoware Open AD Kit: SOAFEE 첫 blueprint — 컨테이너 기반 cloud-native
  • 단, 컨테이너는 배포 단위이지 safety isolation 단위가 아님

통신 미들웨어 3파전

  • SOME/IP: AUTOSAR 표준, 기능 최소주의
  • DDS: 풍부한 QoS+보안 — ROS 2/AP 채택
  • zenoh: discovery 최속, WAN 우위 — Woven by Toyota 채택 (2024 Eclipse 정식화)

출처: AUTOSAR, Apex.AI, SOAFEE, arXiv:2505.02734(성능 비교) — material.md 참조

3. SW 플랫폼 — 핵심

하이퍼바이저와 Mixed-Criticality: FFI가 1급 설계 목표

단일 SoC에서 QM(IVI, LLM)과 ASIL(주행) 워크로드가 공존하려면 ISO 26262의 FFI(Freedom From Interference) 3축을 하드웨어+SW로 입증해야 한다.

축위협메커니즘
SpatialQM 워크로드의 메모리 오염MMU + stage-2 translation, IOMMU/SMMU(DMA 격리), ECC
Temporal실행시간 침해·스로틀링코어 정적 할당, 실행 버짓, watchdog, cache partitioning(MPAM류) + 메모리 대역폭 regulation
Communication메시지 오염E2E protection(CRC/시퀀스), MACsec/CANsec, TSN policing
⚠️ IOMMU는 접근 영역만 제한할 뿐 대역폭은 제어하지 못한다 — 공유 자원(DRAM 컨트롤러·LLC·NoC)의 QoS/regulator가 FFI 입증의 최대 난점. SoC 후보 평가 시 "대역폭 regulator 유무"를 반드시 확인. 1회차의 "LLM 대역폭 폭식 vs 인지 deadline" 문제와 직결.

하이퍼바이저: QNX Safety 8(점유율 27%+, ASIL-D) · DriveOS 내장(파티션-코어 바인딩) · 오픈소스 수렴(AGL+Xen dom0less+Zephyr) — 출처: arXiv:2506.05822 외

4. 기능안전

ASIL-D 달성 패턴 — "doer + checker"

  • ASIL Decomposition(ISO 26262-9): D → B(D)+B(D) 등 — 단, "충분히 독립"(공통원인 배제, DFA) 입증이 전제
  • 표준 스택: 26262(고장) + SOTIF 21448(성능한계) + ISO/PAS 8800(AI, 2024-12 발행) + TS 5083(ADS) + 21434(보안)
  • ISO/PAS 8800: AI 가속기의 random fault → AI 출력 오류 경로가 관리 대상 — NPU 진단·모니터링이 안전 논증의 일부

출처: Promwad, NVIDIA FSI 문서, ISO 8800, SGS-Geely(세계 최초 8800 인증, 2025-08)

4. 규제

UNECE 규제가 HPC에 직접 거는 요구

R157 (ALKS, L3)

  • Transition Demand 10초 + MRM — 단일 고장 후에도 유지 → fail-operational 컴퓨트/전원
  • 운전자 가용성 모니터링 → DMS 컴퓨트가 규제 필수
  • DSSAD: 변조 방지 로깅(±1s, SW 버전 식별)

R171 (DCAS, L2+)

  • 2024-09 발효, 02 시리즈(2027)는 고속도로 hands-off 허용
  • L2+임에도 DMS 상시 실행 + 시판 후 모니터링 텔레메트리(연 1회+ 보고)

R155 / R156 (보안·OTA)

  • CSMS/SUMS 인증, TARA(ISO 21434)
  • HSM · secure boot · 서명 OTA(A/B) · RXSWIN 추적 · IDS 상주가 플랫폼 기본 요건

양산 리던던시 사례

  • Mercedes DRIVE PILOT: 제동·조향·전원·연산까지 이중화, 95km/h 승인(2024-12) — OTA 업그레이드로 확대(R156 실례)
  • Waymo: 컴퓨트 "독립 엔진 2개" — 평시 병렬, fault 시 seamless 인수
  • 지역: EU 2022/1426 · 미국 NHTSA AV Framework(2025) · 중국 최초 승용 L3 허가(2025-12) · 한국 L4 성능인증제(2027 목표)
⚠️ 열·전력도 규제만큼 단단한 제약: L4급 400–600W(주행거리 7–10% 잠식), 열부하 1–4kW → 수랭 연동이 프리미엄 HPC 기본값화(Mercedes CLA 양산 사례). TDP는 통합 후 동시성 시나리오로 산정, 열 스로틀링이 temporal FFI를 침해하지 않게 파티션별 버짓 분리.
5. 종합

우리 팀 HPC 설계 체크리스트

#항목체크 포인트
1ASIL 배분decomposition 채널 분할 + 독립성 입증. SoC random fault 등급(B)과 시스템 클레임 갭은 외장 MCU/듀얼 SoC로
2Safety islandDCLS 코어, 독립 전원/클록, fault aggregator, safe-state 강제 권한
3FFI정적 파티셔닝 + 메모리/캐시/NoC QoS + DFA. 대역폭 regulator 유무 확인
4Fail-operationalR157 "TD 10초+MRM" = 최소 유지시간 스펙. degraded 경로 + 전원 2계통
5메모리용량(모델 상주)+대역폭(300–500 GB/s급)+ECC(DLEP) — 1회차 결론 연결
6I/OMulti-Gig TSN 다포트 + SerDes + PCIe/NVLink + CAN 게이트웨이 (인입 3–40 Gbps)
7규제 데이터 경로DSSAD 변조 방지 로깅, R171 텔레메트리
8보안HSM/secure boot/서명 OTA/RXSWIN/IDS (R155·156)
9AI 안전 보증ISO 8800 라이프사이클 + 가속기 진단(BIST/ECC/monitor) + SOTIF 기록/리플레이
10열/전력동시성 시나리오 TDP, 수랭 검토, 파티션별 버짓, 48V/eFuse 전원트리
